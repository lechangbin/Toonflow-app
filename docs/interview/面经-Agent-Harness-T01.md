# Agent Harness T01 面经：可复现基线

> 对应已关闭 Issue #57。回答应依据冻结报告的 2026-09-20 历史验证，不把那次结果说成当前所有 T 分支的全量验收。本文只准备面试问题与证据，不提供简历 bullet；个人 ownership 须按提交记录确认。

## 项目背景

在 Agent Harness 迭代前，App 与 Web 已有原项目功能修复、生成代码和嵌入式前端 bundle。如果不冻结双仓源修订、依赖、数据库初始化和产物，后续评测差异可能只是环境或页面不一致。T01 把一组已合并修复变成可复现起点，而非新增 Agent 功能。

## 主问与追问

1. 问：T01 的交付到底是什么？答：是一份可按精确 App/Web commit、Node/Yarn、锁文件、数据库初始化和 bundle 哈希复现的源与产物基线。它还明确哪些 Issue/PR 已合并、哪个被拒绝提交不在接受祖先里，并记录当时的测试、类型和构建门禁。这样后续 T02 评测与 T04 Runtime 有明确起点；不能说 T01 已实现 Agent Harness 控制面。追问：为什么不只写“main 最新版”？答：分支会移动，精确提交不会。
2. 问：为什么要同时冻结 App 和 Web？答：这个项目 App 后端仓库还嵌入 Web 构建文件，页面来源和服务端源码属于不同 Git 仓库。若只固定 App，无法确定 `data/web` 是否由预期 Web 修订生成，也无法判断 UI 行为是前端还是后端变更引起。报告分别列两仓最终 commit，再核对 Web `dist` 与 App `data/web` 相对文件及哈希。追问：这能证明部署服务器运行了它吗？答：不能，报告是源码与构建基线，不是部署证明。
3. 问：为何从干净 worktree 验证，而不是在长期开发目录直接跑？答：长期目录可能残留忽略的类型声明、已安装依赖或历史 bundle，使构建“碰巧能过”。干净检出迫使代码只依赖受控文件与锁定安装，结果暴露了 Web 首次 type-check 对生成声明的隐式依赖。报告记录了物理 `yarn install --frozen-lockfile` 和具体 gate；不应把这当成当前分支重复运行过。追问：为什么物理安装重要？答：跨 worktree 链接依赖可能掩盖环境差异。
4. 问：Web 的生成类型声明为什么要提交到仓库？答：若声明只在 Vite 运行后出现在本机，干净检出时先执行 `type-check` 就缺类型；开发者机器已跑过生成器时看不出问题。基线把受生成器管理的声明纳入版本控制，并在构建时检查它们被跟踪且内容无漂移。代价是生成器升级需要同步更新声明；好处是首次检查可复现。追问：为何不能在 type-check 前总跑一次 Vite？答：那会保留隐式先后依赖，难以单独验证类型契约。
5. 问：Windows 换行变化为何影响哈希和 Git 状态？答：仓库 Git blob 的 LF 内容与 Windows checkout 的 CRLF 可能不同，直接比较工作树字节会把平台转换误报为源码变化。报告把“canonical SHA-256”定义为冻结提交中 Git blob 原始字节，并通过 `.gitattributes` 约束生成声明的换行。这样既保留真实产物漂移检测，也不让环境换行噪声污染基线。追问：这会忽略实际工作树错误吗？答：不会，构建后仍检查语义/生成文件是否有差异。
6. 问：为何记录 `package.json` 与 `yarn.lock` 的哈希？答：工具链版本只固定 Node/Yarn，依赖图还受声明与 lockfile 内容影响。两者的 Git blob 哈希可说明当时装的是哪套依赖，便于后来判断失败来自代码还是安装输入变化。哈希不能保证远端包永远可用，也不能替代锁文件安装与测试；它提供身份和审计入口。追问：只记 `packageManager` 够吗？答：不够，Web 当时甚至没有声明该字段，验证时须明确 Yarn 版本。
7. 问：数据库没有传统编号迁移目录，如何冻结 schema 来源？答：报告记录代码拥有的初始化/修复文件 `src/lib/initDB.ts`、`src/lib/fixDB.ts` 以及 `src/database/readiness.ts` 的 Git blob 哈希。这样后来比较 schema 行为时能定位到当时执行的初始化逻辑，而不是假定存在一套迁移文件。哈希只是来源身份，真实旧库升级还需要另做数据迁移与恢复测试。追问：能据此证明所有用户数据库已安全升级吗？答：不能。
8. 问：如何证明 App 中的前端资源来自指定 Web 构建？答：先在冻结 Web commit 上构建，再按相对文件名核对 `dist` 的六个文件与 App `data/web` 中版本的 SHA-256。重复构建的 `index.html` 哈希稳定，且 App commit 包含相同字节。这个链条说明仓库中的嵌入产物来源一致，不说明任意实际部署已更新缓存或浏览器已加载。追问：为何不只看文件名？答：带 hash 的文件名也不足以确认所有内容字节一致。
9. 问：App 的后端 bundle 为什么也要单独记录？答：在这个项目里 `data/serve/app.js` 是构建产物，若改源码却保留旧 bundle，运行结果会与审查的代码不一致。报告记录从 App 权威源码重建后的 artifact 哈希，并区分它与数据库/路由等源码输入。后续修改应从源码重新生成和核对，而不能直接在 bundle 上补丁。追问：相同源码就一定相同 bundle 吗？答：还需工具链、依赖和构建确定性。
10. 问：如何证明被拒绝的 #32 没混入已接受基线？答：报告对 #32 的提交与接受后的 App merge commit 使用 `git merge-base --is-ancestor`，结果退出码为 1，表明该提交不是目标提交的祖先。这是提交图上的明确证据，比“PR 没合并”的口头说法强；但它不排除有人后来独立复制了相似代码，所以仍需审查实际 diff。追问：若 cherry-pick 呢？答：新提交身份不同，祖先检查不足以证明语义没有复制。
11. 问：基线的 App `406/406`、Web `89/89` 可以怎样准确表述？答：只能说冻结修订在报告所记环境与命令下，App 全套测试、类型与构建，以及 Web 合约测试、类型与构建曾通过；Web 的 i18n 检查退出 0，但有未使用/硬编码清单和两个缺失 key 仍待处理。这些数据是历史验证分母，不是线上成功率，更不是后续 T 分支的测试结果。追问：现在要重新说“全绿”吗？答：需要在当前冻结修订重新跑相应门禁后才可这样说。
12. 问：为何报告把“权威输入”和“生成输出”分开？答：App/Web 源码、Vendor adapter 和生成规则才是维护时该改的对象；bundle 与声明是检验输出。若直接修改输出文件，下一次构建可能覆盖它，且审查者无法从源码复现行为。分开记录使后续 Issue 变更可以沿源码→构建→哈希追踪，代价是每次涉及生成内容都要额外比对。追问：生成声明被提交会不会变成权威输入？答：它是版本化验证产物，不能取代其生成来源。
13. 问：为什么 T01 已做过全量测试，而当前约定要把全量留到 T21？答：T01 当时的目标是冻结可复现基线，完整 gate 是其验收条件，所以历史报告记录了完整运行。后续多阶段开发时，用户明确要求每阶段只做相关单元测试，最终全部实现收敛后再做全量、构建、浏览器和真实边界验收。两者对象与时间点不同；不能用旧基线 gate 给新堆叠代码背书。追问：阶段测试发现跨模块风险怎么办？答：记录风险并加定向验证，最终统一验收仍不能省。
14. 问：基线报告如何支持后续 Eval 的因果归因？答：T02 及之后的 baseline/candidate 若连 App/Web 版本、Schema、工具链和产物都不一致，比较结果可能混入环境差异。T01 把起点提交、依赖、构建与数据库初始化身份写清楚，后续可在此之上明确记录每阶段改了什么。它只是必要条件，不会自动固定 Project 数据、模型随机性或真实 Provider 行为；T11 还需更细的成对冻结与结果级证据。追问：两个版本 hash 相同就能证明质量相同吗？答：不能。
15. 问：T01 的完成结论与整个 Agent Harness 完成结论有何不同？答：Issue #57 的范围是可复现原项目基座，报告有精确 commit 和门禁记录，可以按其验收范围标为完成。Agent Harness 的 Run、Trace、Context、Skill、迁移、Eval 和最终 T21 都是后续独立阶段；当前开放 Issue 不能被 T01 的完成状态覆盖。面试时会以“已经冻结一个可核查起点”描述 T01，不把它包装成系统上线或全流程稳定。追问：最重要的证据是什么？答：双仓源身份、干净检出 gate、生成产物哈希和复现命令。
