# Agent Harness T07 面经：受控只读 Tool

> 本文只用于技术追问准备，不生成简历摘要或 bullet。第一人称回答须以当前分支源码和测试为证据；不要据此声称旧 Script Agent 已迁移、真实用户采用或线上指标改善。

## 主题一：Tool 契约与权限

### 1. 为什么已有 Script Agent 工具还要再建受控 Tool Runtime？

**第一人口播：** 我先检查了旧工具实现，发现小说读取函数把模型工具声明、数据库查询和 Socket thinking 回调放在一起，调用时依赖会话对象里的项目 ID。T07 要让持久化 Agent Run 拥有可重连、可检查的调用证据，因此我建立一个单一执行入口：模型只给工具名、操作 ID 和严格参数，Runtime 从已持久化的 Run 查项目、核对租约，再调用内部领域适配器。结果是新只读 Run 的两种读取已有 ToolReceipt 和 Trace；旧 Script Agent 会话仍保留原实现，不能说所有 Agent 工具都完成了迁移。

**追问 1：为什么不直接给模型一个数据库查询工具？**

**第一人口播：** 模型生成的 SQL、表名或 Project ID 都是非可信输入；若把数据库句柄交给模型，它就可能绕过业务归属、字段最小化和输出限制，测试也难以证明每次查询都走同一授权过程。我让模型只能选两个固定名称，并传入一个正整数章节 ID；真正的查询藏在服务端适配器中，且查询必须同时过滤 Run 的 Project。受控 Runtime 在适配器执行之前完成授权，测试用别的 Project 的章节 ID 验证适配器调用数为零。这一边界保护当前两个读工具，未来新增工具仍需逐项声明权限和风险。

**追问 2：Socket 回调为什么不适合作为工具的权威执行上下文？**

**第一人口播：** Socket 连接会因页面刷新、网络切换或应用重启消失，而 Agent Run 和 ToolReceipt 需要继续可检查。旧工具中的 thinking 消息适合即时展示，却不能证明某次读取的授权、参数、结果或失败已经持久提交。我让 Tool Runtime 接受 Run ID、Project ID、operation ID 和带 fence 的租约，适配器只收到冻结的 Run/Project 最小上下文；它不接收 Socket、响应对象或原始数据库句柄。模型结果最终来自数据库收据和安全 Trace。当前只读 Run 已接线，旧 Socket 工具迁移仍是后续工作。断线也不会成为工具授权的依据。

### 2. ToolDefinition 为什么需要固定 revision 和契约哈希？

**第一人口播：** 同名工具若在部署间悄悄改变输入字段、输出结构或授权策略，旧收据重放时会被新代码错误解释，面试里很难说清“同一次操作”究竟按哪个契约执行。我为每个工具定义固定 revision，包含严格输入/输出 schema、风险和执行策略、适配器身份，并计算契约哈希。首次执行把 revision 与哈希存入不可更新、不可删除的定义表；之后同名同 revision 的哈希若变化就拒绝调用。单元测试验证定义记录不能普通更新或删除，数据库升级保留历史 Run。若确需改约，应显式发布新 revision。

**追问 1：只把 revision 写成字符串为什么不够？**

**第一人口播：** 版本字符串由开发者维护，最容易发生“代码改了却忘记升版本”的情况。比如把事件上限从二十改成五十，仍叫 v1，旧收据的内容和新 schema 可能被混读。我让运行时根据两侧 JSON schema、策略和适配器身份计算确定性哈希，并同数据库中已登记的同 revision 记录比较。哈希不替代代码评审，也不证明来源真实性，但能在本地发现同名修订的静默漂移。测试还覆盖收据读取时重新校验输出内容和哈希，避免只凭 TypeScript 类型信任磁盘记录。

**追问 2：这两个 ToolDefinition 声明了哪些风险维度？**

**第一人口播：** 我没有用一个笼统的“低风险”标签，而是明确声明它们不修改生产资产、不产生外部费用、同步完成，并限定能力、Run role/scope、审批、幂等身份、重试、超时、取消、并发、提交、核对、补偿、脱敏和上下文投影。当前读取无需人工审批，五秒超时，同一 Run/operation 只允许一个持久收据；失败后用新 operation ID 显式重试。这些是 T07 两个读工具的策略，不代表未来写工具或收费工具可以照抄；后者需要更严格的预览、审批与效果核对。

### 3. 模型传来章节 ID，怎样判断它有权读取？

**第一人口播：** 我把章节 ID 当成待授权资源标识，而不是权限证明。执行前先按 Run ID 和请求 Project ID 查找 running Run，核对其 role/scope 与当前 worker 的 owner、epoch、fence、有效期，再用数据库查询确认这条 Novel 的 `projectId` 与 Run 的 Project 一致。只有两步都通过才提交 pending 收据并进入适配器；跨项目或不存在的 ID 会留下枚举化授权失败收据与 Trace，不执行数据库读取适配器。单元测试还把 Run 的 role 改成不允许的角色，确认同样拒绝。这里的项目隔离是工具层防线，上层用户身份授权仍需整体检查。

**追问 1：为什么不能相信请求体里的 projectId？**

**第一人口播：** 请求体和模型输出都可以被调用者构造，若把其中的 projectId 当作查询范围，攻击者只要知道另一个 Project 的数字就能改变授权范围。我的实现把传入 Project ID 只用于定位同一范围的已持久 Run，真正的资源归属以数据库中的 Run.projectId 和 Novel.projectId 为准；两者必须一致。跨项目测试既检查返回安全拒绝，也检查没有生成受害 Run 的收据、适配器没有执行。这个测试不能替代完整的 HTTP 用户认证，但能证明模型参数不能越过工具内部的资源归属检查。

**追问 2：如果 Novel 在授权后、适配器查询前被删除或改项目怎么办？**

**第一人口播：** 授权和实际读取之间存在时间窗口，所以适配器查询本身也再次加上 Novel ID 与 Project ID 的联合条件。若记录消失或项目归属变化，适配器拿不到内容，只返回内部失败，由 Runtime 转成不含原始异常的安全诊断；不会用单独的章节 ID 再查一次。读工具没有本地业务写入，无法依靠同一长事务锁住整段模型调用，我选择双重 Project 过滤与失败收敛。受控单元测试验证常见越权输入；真实多连接并发变更需要最终验收进一步覆盖。

## 主题二：去重与持久证据

### 4. 同一工具调用如何去重？

**第一人口播：** 模型 Tool Calling 可能因上层重试或传输问题重复进入，不能每次都当作新操作。我用 `(runId, operationId)` 唯一约束标识一次逻辑调用，再把工具名、revision 和规范化参数计算成输入指纹。第一次合法调用先在短事务中写 pending 收据和 started Trace，之后才执行适配器；重复请求如果指纹相同，返回当前权威收据，若改了参数则抛身份冲突。测试把适配器停在 Promise 上，第二个并发请求只看到 pending，适配器调用次数仍是一；完成后的重复请求复用同一输出，没有增加第二条收据或 Trace。

**追问 1：operationId 应该由谁生成，为什么不能每次随机重建？**

**第一人口播：** 在当前 Agent Run 接线中，我使用模型 Tool Calling 给出的 toolCallId 作为 operationId，它代表一次模型提出的逻辑工具调用。若网络层重发同一调用，应保留这个 ID，服务端才能识别为重试；若每次都新生成 ID，唯一约束无法阻止重复执行。相反，用户或模型确实要发起另一项读取，应产生新 ID，而不是复用旧 ID 偷换参数。收据把 ID 与输入指纹绑定，测试确认复用 ID 更换章节会被拒绝。跨模型重试的 ID 稳定性还需在真实 SDK 流程中最终验收。

**追问 2：为什么 pending 收据要先于适配器提交？**

**第一人口播：** 若先执行适配器再写收据，两个并发调用都可能在数据库里看不到记录，于是同时启动读取；进程在中间退出也没有证据说明曾经开始过。我让授权和 pending 收据在一个短事务内提交，适配器在事务外运行，第二个请求能立即看到 pending 并停止重复执行。读工具没有外部费用，但这个机制为后续有成本或变更的工具建立统一因果顺序。代价是中断时可能留下 pending，所以就绪恢复会在失去有效租约后把它安全地收敛成失败。

### 5. ToolReceipt 和 Agent Trace 各保存什么？

**第一人口播：** ToolReceipt 用于同一操作的结果重放，因此保存工具修订、输入哈希、状态、受限的类型化输出、输出哈希或安全诊断；它绑定 Run 与 operation ID。Agent Trace 用于解释调用过程和因果顺序，只保存收据 ID、started/succeeded/failed 事件及结构化诊断，不复制小说正文。两者都在相应的数据库事务中一起提交，避免结果与解释分离。测试检查 Trace 序号连续、每个事件指向同一收据，并验证 Trace JSON 不含原文。收据正文属于项目数据，后续访问控制和保留策略仍需单独处理。

**追问 1：为什么 Receipt 要保存输出，不能只保存哈希？**

**第一人口播：** 同一 operation 在模型调用或客户端重试时需要看到一致结果；若收据只保存哈希，重复请求只能再次读数据库，而章节内容可能已经被编辑，返回值就不再对应原来的调用。T07 的只读输出被严格限制长度、结构和敏感内容后存进 Receipt，再以哈希校验，重复请求直接读取已提交结果。这样增加了项目内容副本，所以 Trace 不再复制正文，定义了固定上限，并在读收据时重新检查 schema 和安全门禁。当前没有独立保留周期或加密机制，不能把它描述成完整数据治理方案。

**追问 2：收据内容被手工篡改怎么办？**

**第一人口播：** 我不会因为数据库列的 TypeScript 类型正确就直接投影。读取已有 Receipt 时先确认工具名和 revision 仍受支持，再重新计算输出 JSON 的 SHA-256，与持久化 outputHash 比较；随后解析 JSON、按该 revision 的严格输出 schema 校验，并重新过敏感内容门禁。任何一步失败都会拒绝返回旧结果，避免把坏数据当作可靠证据。定向测试先完成一次原文读取，再把 outputJson 改成空对象但保留原 hash，重复调用得到证据损坏错误。哈希用于发现非一致修改，不是防恶意管理员的签名。

### 6. ToolReceipt 与 Agent Checkpoint 有什么不同？

**第一人口播：** T05 的 Agent Checkpoint 证明 Run 的一个提交边界，例如调用模型的意图或最终 Output 已原子提交；它参与重启后的效果分类。ToolReceipt 则证明某一次具体 Tool operation 的输入身份、授权结果、受限输出或失败，适合去重和追溯。T07 的只读工具在模型调用过程中可以产生多个 Receipt，但这不意味着整个 Model Step 已成功，后续模型仍可能失败。因此我把 Receipt 通过 Trace 关联到 Run，却不伪造新的 Run Checkpoint。面试中必须区分“工具读取成功”和“Agent 最终答案成功”两个不同事实。两者在恢复判断中不能互换。

**追问 1：工具成功但模型终态提交失败，系统保留什么？**

**第一人口播：** 工具读取可能已经成功提交 ToolReceipt 和 Trace，但模型的最终文字还没有写入 Agent Run Output。若模型终态事务失败，T05 的调用意图已存在，Run 会按未知模型效果等待核对，不能因为 ToolReceipt 成功就声称整次 Run 成功或重放 Provider。工具收据仍是可信的局部事实，可以帮助解释模型在失败前读了哪个章节、得到什么受限结果；但它不替代最终 Output Checkpoint。当前定向测试验证工具事件位于 run.started 与 run.succeeded 之间，复杂的终态失败叠加工具调用可在最终故障注入验收中继续扩展。

**追问 2：为什么不把每次工具读取都写成 Checkpoint？**

**第一人口播：** Checkpoint 的语义是 Run 恢复状态的显式提交边界，受 Run version、Attempt 和哈希链约束；每次普通读取若都塞进那条链，会把局部观测与模型外部效果的恢复边界混在一起，也让并发 Tool Calling 难以维护有序修订。ToolReceipt 有自己的 operation identity 和结果哈希，Trace 负责因果串联，足以证明读工具的局部提交。只有未来某种工具影响 Run 的可恢复进度或生产资产时，才应在设计该阶段明确它与 Checkpoint 的关系。T07 没有擅自扩展 T05 的 Checkpoint kind。否则会让原本清晰的模型调用意图边界变得含混。

## 主题三：输出、超时与恢复

### 7. 为什么输出也要严格校验，适配器不是自己写的吗？

**第一人口播：** 适配器虽是服务端代码，但它读取的数据库内容可能为空、过长、被旧版本写成异常结构，未来实现也可能回归。如果只校验模型传入的参数，返回路径仍可能把超长正文、敏感内容或错误字段塞给模型和收据。我让每个 ToolDefinition 同时声明严格输入和输出 schema，适配器返回后再检查字段、字符串上限、数组数量与敏感内容门禁；失败只写 `invalidOutput` 诊断，不保存原始结果。测试注入超过上限的正文和抛出包含私密字样的异常，收据与 Trace 都不泄漏这段原文。

**追问 1：章节正文超过一万六千字符怎么办？**

**第一人口播：** 当前 v1 契约选择拒绝超长正文，返回安全的输出不合规诊断，而不是悄悄截断后让模型误以为拿到了完整原文。这个取舍保持一次 ToolReceipt 的语义明确，也避免截断位置影响事件理解；代价是长章节暂时不能直接通过此工具读完。后续若确有需求，应发布带分段游标和明确完整性标志的新 revision，并设计每段授权与去重，不应在同名 v1 下默默改变上限。当前单元测试验证超长输入不会进入持久输出，实际章节长度分布尚待测量。

**追问 2：事件超过二十个为什么返回 truncated，而不是直接失败？**

**第一人口播：** 事件列表天然适合稳定分页式观察，前二十条已经能提供有用的有限上下文；但只返回二十条而不标注，会让模型错误推断“本章只有这些事件”。所以适配器按事件 ID 排序，读取二十一条用于判断是否超出上限，再只输出前二十条并设置 `truncated=true`。严格输出 schema 保证标志始终存在。单元测试准备二十二条关联事件，验证输出恰好二十条、顺序稳定且标志为真。当前没有下一页接口，模型不能把截断列表当作完整章节事件。

### 8. 读取工具超时后会发生什么？

**第一人口播：** ToolDefinition v1 把单次读取限制为五秒。Runtime 在适配器 Promise 和超时 Promise 之间竞争，若超时先到，会把 Receipt 收敛为 failed，写入 `timeout` 的安全诊断与因果 Trace，并提示显式新 operation 才可重试。它不会把底层 SQLite 查询物理杀掉，所以迟到的 Promise 仍可能完成，但已经没有通道把它写成这次收据的成功输出。定向测试用永不返回的假适配器等到五秒，确认失败收据和 Trace 关联。真实数据库锁等待与进程暂停行为仍需最终验收。超时只是执行合同，不是底层强制中断。

**追问 1：为什么读工具也要去重和超时，读取没有副作用？**

**第一人口播：** 只读不代表没有资源成本或状态可见性问题。重复读取可能占用数据库连接和模型上下文，若章节在两次读取间被修改，模型会拿到两个相互矛盾的结果；没有超时则一次卡住的查询会拖住整个模型调用。我用 operation identity 固定同一调用的结果，五秒后给出明确失败，而不是无限等待。当前风险维度声明无生产资产变更和外部费用，所以失败后可以用新 ID 安全重试；不能把这种策略直接迁移到收费图像生成或生产写入工具。

**追问 2：如果超时后底层查询才成功，为什么不会覆盖失败 Receipt？**

**第一人口播：** `Promise.race` 只决定受控 Runtime 等待哪一个结果；超时 Promise 胜出后，当前执行流程就进入失败收敛事务，把 Receipt 从 pending 改为 failed，并追加 Trace。底层读取即使晚些返回，也没有另一个回调负责更新 Receipt；输出 Promise 的结果被忽略。终态更新本身还检查相同 worker 租约和 `pending` 前态，避免旧 worker 或重复收敛覆盖。这个保证限定于本地记录，不表示底层数据库请求已被取消，也不表示完全没有资源消耗。若未来适配器支持主动取消，可再把信号向下传递。

### 9. 进程在 pending Receipt 后退出，重启如何处理？

**第一人口播：** 第一次调用会先提交 pending Receipt，再在事务外读数据库，因此进程恰好退出时可能留下未完成记录。我把恢复接入现有数据库就绪阶段：对仍有有效 Run 租约的 pending 保持不动，避免维护扫描误伤活跃 worker；对租约已经失效或清除的 pending，逐条短事务收敛为 failed，并追加 `tool.interrupted` 的安全 Trace。重复执行恢复不会再次追加事件。单元测试先在有效租约前扫描，再模拟旧租约消失并扫描两次，确认只生成一条中断 Trace。它不会自动重用同一 operation 调用适配器。

**追问 1：为什么重启后不直接用原 operation ID 再读一次？**

**第一人口播：** 原 operation ID 已经对应一次明确的 pending 调用，自动复用会让收据历史里看不出中断与重试，也可能在章节被编辑后返回不同内容。虽然读工具没有外部副作用，我仍选择把旧调用收敛为失败，由调用方明确使用新 ID 重新请求，这与 ToolDefinition 中的重试策略一致。恢复器仅确认旧租约失效，不猜测旧适配器到底读到了什么。单元测试释放中断前的迟到结果后，旧执行不能把失败收据改回成功。未来若需要自动读取重试，应增加有序 Attempt 证据和上限策略。

**追问 2：启动恢复与活跃 worker 同时发生会不会误判？**

**第一人口播：** 数据库就绪和维护验证可能与 worker 同时访问持久库，因此恢复逻辑不能简单扫描全部 pending 并标失败。我的查询先找无租约或已到期的 Run，事务里再重读当前 Receipt 与租约到期时间，只有仍为 pending 且所有权确实失效才收敛；有效租约不被修改。T06 的 Run 恢复也采用相同到期边界，先处理 Run，再处理 ToolReceipt。这个设计偏向避免误杀，代价是旧租约到期之前 pending 可能暂时保留。定向测试覆盖有效期前后和重复调用；多进程争用仍留待最终压力验收。

## 主题四：Agent 接线与版本演进

### 10. 两种工具怎样真正接入 Agent Run 的模型调用？

**第一人口播：** 我没有只写一个独立工具库就宣布 Agent 已具备能力。现有只读 Agent Run 在提交 `model-call-intent` 后调用已配置文本模型，我在这次模型调用的 `tools` 选项中仅注册原文读取和事件读取，使用严格 Zod 输入 schema。每个执行回调把 SDK 的 toolCallId、当前 Run、Project 和租约交给受控 Runtime，再只把成功的类型化输出或安全失败类别送回模型。调用意图指纹也纳入两种 ToolDefinition 的 revision 与契约哈希。集成单元测试让假模型真的调用读取回调，确认正文来自授权适配器、收据与 Trace 已写入，最终 Run 仍成功提交。

**追问 1：为什么把 ToolDefinition 哈希放进模型调用意图指纹？**

**第一人口播：** `model-call-intent` 是 Provider 调用前的本地事实，记录这次 invocation 的稳定身份。引入 Tool Calling 后，消息文本相同但工具 schema、权限策略或适配器版本不同，模型可执行的动作其实已经变化；若指纹仍只覆盖消息与模型目标，恢复和审计会漏掉这个差异。我把工具名称、revision 和契约哈希加入 invocation fingerprint，使同一输入在工具合同变化时不再被误认为完全相同的调用。它不把工具内容复制进 Checkpoint，也不证明 Provider 一定用了工具；只是准确描述本地提交的调用配置。

**追问 2：模型工具调用失败时给模型什么信息？**

**第一人口播：** 我不会把数据库异常、跨项目资源是否存在的细节、原始 Novel 内容或内部堆栈交给模型。受控 Runtime 返回失败 Receipt 的安全诊断类别，例如授权失败、输出无效、适配器失败或超时；Agent 接线将其投影为固定的 `unavailable` 状态与稳定 kind。模型因此知道这次读取不可用，可以说明信息不足，而不会获得越权内容或调试秘密。定向测试检查适配器抛出的私密异常文字没有进入 Receipt 和 Trace。真实模型面对失败类别的回答质量还没有做端到端评估。

### 11. 为什么输入用 Novel 数据库 ID，不沿用旧工具的 chapterIndex？

**第一人口播：** 旧 Socket 工具按章节序号读取，序号只在项目上下文中有意义，而且旧实现通过会话对象注入 Project。T07 要在持久 Run 的授权路径中先验证具体资源归属，所以我选择 Novel 记录 ID 作为 Tool 输入：它可以与 Run 的 Project ID 联合查询，不存在或跨项目都不进入适配器。模型只能看到当前项目上下文提供的合法 ID，不能靠猜测序号扩大范围。这个选择让当前 Agent Run 的工具合同明确，但旧 Script Agent 迁移时需要适配现有调用方式；不能说两个接口已经无缝兼容。

**追问 1：知道一个合法 Novel ID 就能读取吗？**

**第一人口播：** 不能。Novel ID 只是资源标识，受控 Runtime 还要求请求绑定一个处于 running 的 Run，其 Project、role、scope 与定义策略一致，并且执行者持有有效 owner/epoch/fence 的租约。随后数据库确认该 Novel 的 Project 等于 Run Project，适配器查询时再次带同样的 Project 条件。测试把 Novel ID 换成另一个项目的真实记录，结果仍是授权失败且适配器调用数为零；把 Run role 改错也被拒绝。上层用户权限仍需应用认证层保证，不能把这些条件夸大成完整零信任体系。资源 ID 永远不能单独充当访问令牌。

**追问 2：如果多个章节有相同 chapterIndex，ID 方案解决了什么？**

**第一人口播：** chapterIndex 是展示顺序或章节编号，不保证全局唯一；不同 Project 可以有相同编号，同一 Project 的导入或重排也可能出现重复。若模型只说“第 1 章”，后端需要额外规则才能确定读取哪条记录。我让工具输入数据库记录 ID，授权查询直接定位一条 Novel，再在输出里带回 chapterIndex 和标题，方便模型核对上下文。当前项目事实提示列出按章节编号排序的前二十个可读记录 ID；超过二十章时明确标记只列前二十。后续 ContextBundle 阶段可设计分页或更完整的资源目录，不能让模型猜测未提供的 ID。

### 12. 新旧数据库如何兼容 ToolReceipt 和 Trace 关联？

**第一人口播：** T07 在新库初始化路径创建 ToolDefinition 和 ToolReceipt 表，Trace 增加可空的 ToolReceipt ID；旧库升级时通过现有 `fixDB` 给 Trace 增量加列，`initDB` 负责补建新表。历史 Run、Trace 和 Output 不会被虚构出工具调用记录，可空关联表示旧事件没有 ToolReceipt。定义表另有数据库触发器禁止普通更新和删除，避免同名 revision 被原地改写。升级测试模拟缺表和缺列，再执行初始化/升级，确认旧 Run 的状态与版本保持不变。生成的数据库类型声明也与新 schema 同步，但正式生产迁移规模仍待最终验收。

**追问 1：为什么历史 Trace 的关联列要允许空值？**

**第一人口播：** T04-T06 的 Agent Trace 记录了 Run 创建、模型意图、成功、取消与恢复，它们本来就没有对应 ToolReceipt。若强制新列非空，升级时必须给旧事件伪造收据或重写历史，这会破坏证据可信度。我把关联列设计为可空：工具事件填写 Receipt ID，其他事件保持空；读取时根据事件类型解释。单元测试确认新工具 Trace 的 ID 指向同一收据，升级测试确认旧 Run 不被改动。后续证据抽屉应清楚展示“无工具关联”与“关联丢失”的差别，不能仅靠空值猜测损坏。

**追问 2：定义表触发器能防数据库管理员恶意改写吗？**

**第一人口播：** 不能把普通 SQLite 触发器说成防恶意管理员的安全签名。它约束应用和一般 SQL 更新/删除，帮助保持 ToolDefinition revision 不被无意重写；拥有文件权限的人仍可关闭约束、复制数据库或直接替换文件。我还在运行时用持久的 contractHash 对比当前代码定义，重复读取 Receipt 时校验输出哈希和 schema，用于检测非一致改动。若目标升级为对抗恶意管理员，需要外部签名、访问控制和备份审计。本阶段的证据边界是应用级完整性和 fail closed 行为。

## 主题五：测试、责任与后续

### 13. 你如何证明工具授权和去重不是只在正常路径成立？

**第一人口播：** 我把单元用例放在最容易出错的分支：真实存在但属于另一 Project 的 Novel ID、错误 Run Project、错误 Agent role、复用 operation ID 更换参数、适配器执行中又来同一请求、超长输出、适配器抛异常、五秒超时、收据内容篡改和重启留下 pending。测试不仅看返回值，还检查适配器实际调用次数、Receipt 行数、Trace 序号、诊断中是否包含私密错误文字，并用假模型调用 Agent Run 注册的 Tool 回调。聚焦测试能证明这些可控状态，尚不能代替真实 Provider SDK、浏览器和多进程竞态验收。

**追问 1：为什么测试跨项目时还要数适配器调用次数？**

**第一人口播：** 只断言 HTTP 或 Runtime 返回“拒绝”，无法证明越权读取真的没有发生；代码可能先查出别的项目正文，再在响应阶段丢弃，这时敏感内容已经穿过了不该穿过的执行层。我给适配器注入一个会计数的假实现，传入另一个 Project 的真实 Novel ID，断言授权失败 Receipt 和 Trace 已落盘，同时计数严格为零。请求 Run Project 不匹配时连受害 Run 的收据都不创建。这个负面证据直接对应“授权必须早于适配器”，比只看最终文案更能说明边界是否有效。

**追问 2：这些测试是否证明了真实模型只会调用两种工具？**

**第一人口播：** 聚焦测试证明当前 Agent Run 构建的模型调用参数里只注册了两个固定名称，且假模型通过其中一个回调能写出授权 Receipt；它还验证严格输入拒绝额外字段。但真实 Provider 的工具选择、toolCallId 稳定性和模型面对失败结果的行为，仍要在最后的受控 smoke test 与跨仓浏览器流程中验证。我会把这两层证据分开陈述：本阶段是 TypeScript 接线和数据库合同，最终验收才覆盖真实模型网络调用。旧 Script Agent 的工具集合也没有被这一改动替换。

### 14. 这一阶段哪些结果可以核验，哪些不能写成成果？

**第一人口播：** 能核验的是当前分支的 ToolDefinition、受控 Runtime、授权查询、收据表、Trace 关联、恢复器、Agent Run 工具接线，以及聚焦单元测试输出；这些足以说明本地控制面的行为。还不能写成成果的是线上越权事件下降、成本节省、用户体验改善、所有 Agent 完成迁移或真实模型调用稳定，因为没有对应上线和测量证据。我会用 Issue、提交、PR 与版本化报告说明自己的具体修改，不会把原项目的旧功能当成这次深化的个人成果。若面试官追问数字，我给出待测指标与采集方法，而不是编造百分比。

**追问 1：如何现场演示最有说服力的一条证据链？**

**第一人口播：** 我会先展示一个合法 Run 的 Project 与租约，再发起读取本项目 Novel 的操作，检查返回类型化正文、Receipt 的输入/输出哈希和指向该 Receipt 的 Trace；接着改用另一个 Project 的真实 Novel ID，检查授权失败、适配器调用数为零且诊断不泄漏内容。最后重复同一 operation ID，展示没有第二次适配器执行；改参数则报身份冲突。这个演示覆盖校验、授权、执行、持久化与去重的完整路径。它使用本地 SQLite 和假适配器，真实模型与浏览器仍要另行验收。

**追问 2：没有线上数据时怎么谈收益？**

**第一人口播：** 我会区分架构变化与量化收益：本阶段可以说“工具调用从会话内直接读取转为有 Project 授权、稳定操作身份和持久收据的控制面”，因为源码和测试可查；不能说“安全事故减少了多少”或“响应更快”。若要量化，可在最终验收或试运行中记录跨项目请求触发适配器的次数、重复 operation 的额外执行次数、超时率、受限输出拒绝率、Trace 内容泄漏检查和数据库锁等待。当前这些指标没有真实流量样本，只能列为测量计划，不应当成已达成结果。

### 15. T07 之后最重要的技术债和下一步是什么？

**第一人口播：** T07 只覆盖两种当前项目小说读取，旧 Script Agent 的 Socket 工具仍在原路径，生产写入和收费图像工具也没有受控接入。下一步应在明确审批、外部成本、不可重放效果和原子持久化规则后，逐类扩展 Tool Runtime；同时让后续 Script Agent 迁移改用这一受控入口。ToolReceipt 目前可通过内部操作读取，没有面向用户的证据抽屉，后续 Trace 阶段应补可视化和保留策略。最终统一验收还要跑完整仓库测试、App/Web 构建、浏览器 E2E、真实模型 Tool Calling 与多进程故障场景。

**追问 1：为什么写工具不能直接复用读工具的超时重试规则？**

**第一人口播：** 读工具超时后重试，最坏主要是重复读取与资源消耗；写工具可能已经修改数据库、调用远端生成或产生费用，即使本地收据还是 pending，也不能推断外部没有效果。若直接套用“新 operation ID 再来一次”，可能重复资产、重复扣费或覆盖用户选择。写工具需要在执行前冻结操作意图，按风险申请授权，数据库本地变更与 Receipt 同事务提交；远端不可原子效果则需要可查询的任务 ID、reconcile 或人工裁决。T07 明确把风险声明为无变更、无外部费用，不能把它当作所有工具的默认政策。

**追问 2：最后验收最可能暴露哪类问题？**

**第一人口播：** 我会重点检查真实模型工具协议与本地测试之间的差异：toolCallId 是否稳定、一次模型响应是否并发调用多个工具、失败结果是否被模型正确处理、长章节和多事件在真实项目中出现多频繁、SQLite 维护与五秒超时是否相互影响、进程强杀后 pending 收据是否确实收敛。还要确认 Web 刷新、Project 授权和旧数据库升级的跨模块行为。当前定向单元测试把最关键的本地边界固定住，但不能提前宣布全量 App/Web 或 Provider 端到端已通过；这些要等所有阶段结束后统一验收。
