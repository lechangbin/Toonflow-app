# Agent Harness T08 面经：审批、幂等与原子写入

> 本文只用于技术追问准备，不生成简历摘要或 bullet。回答以本阶段源码和定向测试为证据；不得把旧生产 Agent 说成已迁移，也不得宣称全量验收、上线采用或线上指标改善。

## 主题一：问题界定与权限边界

### Q1. 为什么一个写工具不能像只读工具一样直接执行？

**第一人口播：** 原有生产 Agent 已能通过会话工具写入资产，但模型给出的目标 ID 和内容不能等同于用户授权；一次误判会直接改变项目资料，而且断线后很难解释用户究竟批准过什么。我负责把首个衍生资产写入拆成“合法提案”和“人工决定”两段：前段校验项目、父子资产、剧本、版本和变化契约，后段展示服务端生成的效果预览并要求显式确认。定向测试证明未经批准不会产生资产写入；旧会话工具仍是独立路径，不能声称整个系统已统一受控。

**追问 1A：审批是否意味着用户以后都能写这个项目？**

**第一人口播：** 我把审批理解为一次性能力，而不是给模型或会话发放可复用的项目写权限。审批记录固定工具修订、规范化参数哈希、目标身份和版本、效果预览及到期时间；决定命令还携带审批 ID 和运行版本。真正落库时我再次核对项目所有者与当下目标，任何内容变化或旧命令都会停在安全状态。测试覆盖相同命令重放不重复写，以及换载荷复用请求身份被拒绝；这只能证明当前本地写工具的边界。

### Q2. 你怎样防止只读 Agent 获得写权限？

**第一人口播：** T07 的只读 Agent Run 可以读取小说原文和事件，它的角色、范围和工具策略都固定为读能力。如果直接把资产写工具放进同一个工具集合，模型只要选择名称就可能越过原先的产品承诺。我在 T08 为生产 Agent 建立独立写范围，写工具也声明修改项目工件和逐操作审批；只读模型调用仍只注册两种读取工具。源码和测试能检查这些静态、运行时边界，旧生产会话的直接写入口要在后续迁移阶段再收敛。

**追问 2A：模型传一个别的项目的资产 ID 会怎样？**

**第一人口播：** 我不把模型提供的整数 ID 当成权限凭证。提案进入时，服务端先用已认证用户身份找当前项目所有者，再要求剧本和父资产都属于同一项目；更新时目标衍生资产还必须挂在那个父资产下，类型和剧本归属也要匹配。任何条件不成立都在创建 Run 和审批前拒绝。负面测试用跨项目父资产及错误项目所有者验证数据库里没有留下提案，也没有生产资产修改。这个校验还覆盖列表、详情和决定入口，不能只守住创建请求。

### Q3. 为什么还要校验变化契约，而不仅仅让用户看名称和描述？

**第一人口播：** 这个项目的衍生资产不是简单复制一条展示记录，后续图像生成依赖可组合的视觉状态维度、保留项、允许变化和排除项。名称与描述不足以约束生成行为，若审批只展示它们，会出现用户以为批准换装而模型实际上提交另一类变化。我重用既有领域契约校验，要求新版结构、非空剧本证据，以及视觉维度与父资产规范类型兼容；提案和提交前都查等价状态。测试对空证据和错误目标版本做了前置拒绝。

## 主题二：精确审批与并发控制

### Q4. 审批究竟绑定了哪些内容？

**第一人口播：** 在用户可能稍后才点击批准的场景中，只保存一个“同意”布尔值会失去语义，因为工具定义、目标资料或模型参数都可能已变化。我让服务端把严格解析后的载荷写成确定的 JSON 并计算哈希，同时保存工具修订及契约哈希、目标状态哈希、到期时间和受限效果预览；数据库触发器阻止修改这些绑定字段。批准事务重新计算并核对它们，界面显示持久预览而非临时浏览器请求。篡改负面测试证明不发生资产写入。

**追问 4A：为什么不直接让浏览器把预览重新提交回来？**

**第一人口播：** 浏览器上的文本适合呈现，不适合作为写入依据：页面可能过期，参数可以被改，断线重连后内存也不可靠。我让浏览器只提交运行 ID、审批 ID、命令 ID、预期版本和批准或拒绝的选择；具体载荷与预览从数据库中取回并验证。前端按钮也仅根据后端给的允许动作显示，遇到冲突只刷新列表，不把旧表单自动重放。这样可以把人为确认和最终效果准确关联，尚需最终浏览器验收验证交互细节。

### Q5. 已有 revision，为什么还要目标状态哈希？

**第一人口播：** 目标的变化契约有单调修订号，但仓库里仍存在旧生产会话写路径，它可能修改资产名称、描述或父子关系而没有同步增加契约修订。如果只比较 revision，用户批准时看见的对象与落库时的对象可能不同。我在提案时计算父资产身份、目标资产关键字段和契约内容的状态哈希；批准时重读同一项目的记录并重算。目标变化负面测试使审批转为冲突且资产不写入；哈希是本地并发检查，不是防恶意数据库管理员的签名。

**追问 5A：新建资产没有目标版本时怎么处理？**

**第一人口播：** 新建提案明确要求目标 ID 为空、预期版本为零，而不是把缺失目标当作任意版本。服务端仍然固定父资产、所属项目和剧本，并在提交时复核父资产类型与归属；同一父资产下的等价视觉状态也要再次查找，防止用户审批期间别人创建了相同状态。批准成功后才在一个事务里插入资产和第一版变化契约。单元测试确认新建结果的版本为一，重复审批不再插入第二条资产。

### Q6. 审批过期、目标冲突和证据损坏有何区别？

**第一人口播：** 这三种情况都不能继续写，但排查含义不同。过期表示用户在授权期限外决定；目标冲突表示项目状态或预期修订已变，应重新提案；证据损坏表示持久载荷、哈希或工具契约不可信，不能依赖原预览。我给审批保留不同的安全状态，收据只存受控诊断，Run 只允许检查，不开放重试按钮。局部测试覆盖过期、资产变化和审批载荷被改的情况；仍没有做真实进程与浏览器的完整联调验收。

## 主题三：幂等与事务边界

### Q7. 这里为何需要三个不同的幂等 ID？

**第一人口播：** 一次生产写入跨越创建 Run、登记工具操作和用户审批命令，三个动作都可能因网络重试而重复，但它们不是同一层语义。我用客户端请求 ID 防止创建多个相同 Run，用 Run 内操作 ID 固定一份工具提案与收据，再用命令 ID 固定用户的一次批准或拒绝。相同身份重试返回持久结果，身份相同却换载荷或决定则报冲突。测试核对重复批准只产生一条资产记录，避免把“收到两次 HTTP 请求”误说成“两次业务效果”。

**追问 7A：同一命令 ID 先批准后拒绝，会怎样？**

**第一人口播：** 命令 ID 的含义必须稳定，所以我在审批记录中保存决定类型、发命令时的 Run 版本和决策时间。重复调用若命令 ID 相同，但决定从批准改成拒绝，或者预期版本不同，就不能复用成功结果，而是作为冲突拒绝；若完全相同则返回先前的权威快照，不再次触碰资产。这比仅依赖按钮禁用更可靠，因为页面刷新或网络重发可以绕开本地按钮状态。前端遇到冲突会重新读取而不自动重试。

### Q8. 你说“原子写入”，具体哪些东西在一个事务里？

**第一人口播：** 我把“资产写了、证据没写”视为最危险的局部成功，因此批准路径在同一个 SQLite 事务内完成最后一次目标校验、资产新增或更新、变化契约版本递增、工具收据终态、可展示输出、运行状态、哈希链检查点和因果 Trace。任一步抛错都会回滚这次决定，不会留下部分已写的生产记录。测试在变化契约插入处注入数据库失败，断言新增资产、终态收据和检查点都没有落下；它不替代跨进程锁竞争验收。

**追问 8A：发生数据库异常后，审批是否被当成已成功？**

**第一人口播：** 不会。数据库事务异常会向上返回错误，整个批准事务回滚；此前单独提交的 waiting Run、pending 收据和审批提案还在，可供用户重新检查，但没有任何“已提交资产”的输出或终态检查点。我不会把异常自动当作失败后重放，因为还需要看错误究竟来自事务内部还是外部依赖；当前工具完全是本地数据库写入，没有收费供应商副作用。单元故障注入证明本地部分提交为零，真实断电场景留在最终验收。

### Q9. 为什么检查点和收据不能互相替代？

**第一人口播：** 收据描述一项工具操作的输入身份、结果或安全失败；检查点证明整个 Agent Run 某个提交边界及其前后因果链。只存收据，无法判断 Run 的步骤、最终输出和版本是否与之一起完成；只存检查点，则缺少工具级别的审批与结果身份。我在提案时写初始检查点，在成功批准时把输出、收据和提交检查点一起落库，再由共享 Run 检查器在“重启后”的全新实例里重建 waiting 或 succeeded 快照。测试覆盖这条恢复投影链。

## 主题四：界面与恢复

### Q10. 为什么审批 UI 放在现有聊天侧栏？

**第一人口播：** 用户当前就在生产 Agent 聊天中发起资产工作，另建管理后台会让一次简单批准跨页面查找，还扩大了本阶段的产品范围。我沿用现有侧栏，加入最多三张近期审批卡，展示父资产、目标、目标版本、工具修订、载荷哈希前缀和到期时间，批准与拒绝前再次弹出确认。后端列表仍保留当前项目最近二十条供后续细节展示。Web 的局部测试覆盖动作映射和安全状态文案，但还没有浏览器交互截图或全流程 E2E 证据。

**追问 10A：页面断线后还能找到待批操作吗？**

**第一人口播：** 审批不是存于聊天消息或组件内存；提案、Run、收据和决定状态都已经写进本地数据库。侧栏挂载、项目切换、连接恢复以及定时刷新都会重新请求当前项目的持久审批列表，再用后端返回的允许动作决定按钮。即使界面暂时断线，刷新后也能投影同一审批 ID 和版本，不会据聊天流猜测审批是否完成。当前定向测试覆盖服务端重建与前端映射，实际浏览器重连仍要在最终验收中跑。

### Q11. 为什么 409 冲突不能在前端自动重试？

**第一人口播：** 409 表示审批或目标已经变化，用户原先确认的是旧效果预览；自动重试可能悄悄批准了新版本资料，破坏人工授权的精确性。我让 Web 捕获决定失败后只刷新权威列表，并提示用户核对最新状态，不生成新的批准命令。若是重复发送同一命令，后端可幂等返回既有结果；如果确实目标冲突，必须重新建立提案让用户再看一次。Web 单元测试证明按钮由后端允许动作控制，但真实双击和网络延迟需要后续浏览器验收。

**追问 11A：为什么不从 `status=pending` 直接推断可以批准？**

**第一人口播：** `pending` 只描述审批记录还没有正常终态，不代表当前用户仍有批准权限；到期、项目所有权变化、证据损坏或后端策略调整都可能让相同状态暂时不能批准。因此前端只看后端投影的允许动作，不根据本地时钟、状态文案或 HTTP 错误码自行授予按钮权限。当前实现还会在异常证据时把预览替换成安全占位并仅开放检查，避免坏数据通过 UI 暴露。定向测试固定了这种动作映射。由服务端统一计算动作也便于后续增加审批策略。

### Q12. 进程重启后 waiting Run 会不会被误当成可重放模型调用？

**第一人口播：** 这条写入链与可能收费的模型调用不同：提案时没有生产修改，Run 的等待原因是人工审批，资产效果只发生在用户决定事务里。数据库就绪恢复器对 waiting Run 不做自动 Provider 重放，审批卡从持久记录重新加载；成功结果由收据和终态检查点解释。测试用新建的 Run 检查器读取先前写入的 waiting 和 succeeded 两种状态，验证无模型调度。真正强杀进程、跨连接并发和浏览器重连仍待最终统一验收；因此我不把本地重建测试说成完整灾难恢复演练。

## 主题五：证据边界与演进

### Q13. 这个阶段有哪些你绝不会宣称的结果？

**第一人口播：** 我能核验的是源码中的受限 Tool 定义、审批绑定、项目所有者校验、事务提交、持久收据、Web 卡片，以及局部单元测试断言。不能据此声称旧 Production Agent 全部迁移、线上误写率下降、用户已采用、端到端运行稳定或收费模型成本降低，因为还没有对应的集成与运营证据。我在版本化报告里列出 App/Web 起点、局部测试和未运行的全量验收项目；面试官追问量化收益时，我只给出待采集指标和方法，不编造百分比。

**追问 13A：如何证明“重复命令不会重复创建资产”？**

**第一人口播：** 我用一条可观察的外部行为测试，而不只看函数是否被调用。先创建提案并批准，记录资产表、变化契约、收据和检查点的数量；再以相同命令 ID、相同预期版本重发批准，断言返回的快照完全相同且资产数量不变；提案本身用相同客户端请求 ID 重试，也应返回已完成的同一 Run。这个证据证明当前 SQLite 边界内的幂等结果，不把它夸成第三方系统的全局 exactly-once 保证。更换决定内容则必须报冲突，而不是借原命令再执行一次。

### Q14. 旧 Production Agent 工具还会直接写库，这是否让新设计没有意义？

**第一人口播：** 这是明确的过渡风险，而不是可以隐藏的事实。T08 的目标是先证明一个受审批写入切片的合同、事务和界面能成立，旧会话工具仍服务现有用户工作流，不在本阶段骤然替换，以免把既有生产功能一起破坏。我在架构说明和报告中把两条路径区分，且状态哈希会检测旧路径对目标的未版本化修改。后续生产 Agent 迁移必须把模型写入统一转到新 Runtime，并以跨路径回归测试证明旧入口可以撤除。

**追问 14A：那现在模型是否已经通过新写工具执行？**

**第一人口播：** 还没有把旧生产 Agent 的模型工具调用整体改接到新 Runtime；T08 交付的是可由生产 Agent 迁移阶段调用的受控写能力，以及用户可以通过现有侧栏批准的新 HTTP 提案。旧 Socket 工具仍直接工作，新审批卡只会显示走新提案入口的操作。我会直说这个边界，不把“已提供后端写工具”和“所有模型写入都受审批”混为一谈。迁移验收还需验证模型参数、聊天兼容、重连和真实生产路径；在此之前不能关闭旧入口或声称统一治理完成。

### Q15. 下一阶段与最终验收最该关注什么？

**第一人口播：** T08 证明的是本地监督写入的最小闭环；下一阶段应把收费图像生成纳入可恢复的效果记录，不能把本地事务的 exactly-once 假设套到外部供应商。最终统一验收要跑完整仓库测试、App/Web 构建、浏览器刷新与重复点击、真实模型工具协议、跨进程锁竞争和断电恢复，并记录准确的 App/Web 提交及 bundle 哈希。我会特别检查旧生产会话与新审批路径的并存行为，避免局部单元测试通过却在真实入口绕过控制面。

## 交接边界

- 技术事实：本地 SQLite 写入可通过严格提案、一次性审批、目标乐观并发校验和同事务证据提交实现；只读 Agent 仍无写权限。
- 高风险 Claim：主导全系统架构、所有 Agent 已迁移、线上可靠性或成本改善、真实模型端到端成功均未被本阶段证明；若面试使用这些表述，必须另补证据。
