# Agent Harness T21 面经：最终验收与证据索引（准备阶段）

> 对应开放 Issue #77。仅有验收索引契约和定向单测，七类真实验收均 pending；不提供简历 bullet、不报未测收益。第一人称 ownership 须用户按提交记录确认。

## 项目背景

T01–T20 产生了跨 App/Web、数据库、Agent Runtime、受控 Tool、评测和 Vendor 的阶段性证据。定向测试不等于这些组件在同一修订组合中可用。T21 要在全部实现收敛后冻结组合、执行七类验收、整理失败与残余风险；现阶段只能准备证据索引，不能发布完成结论。

## 主问与追问

1. 问：项目已经通过最终验收了吗？答：没有。当前 `finalAcceptanceIndex.ts` 只定义了索引字段、七类固定验收项和独立核验接口，报告明确所有项目仍 pending。既没有最终修订清单、结果哈希或验收命令，也没有真正执行跨仓/浏览器/恢复完整套件。把准备文件当完成报告会让后续风险失去可见性。追问：那现在可以讲什么？答：可讲索引契约及其定向测试，不讲整体可用或上线收益。
2. 问：七类验收分别是什么，为什么不能只跑全量单测？答：functional 看业务行为，compatibility 看新旧入口与协议，recovery 看进程中断和持久状态，security 看越权/泄密/副作用边界，evaluation 看冻结分母与结果，build 看源与产物，browser 看真实用户操作。单测可覆盖某些规则，却不能替代页面、构建、进程与外部网络的组合风险。Issue #77 因此把七项作为固定分母；当前全部未执行。追问：某项失败可否标部分通过？答：应记录失败和缺口，不把它标 passed。
3. 问：为何阶段定向测试通过不足以说明 Harness 可用？答：这些测试通常注入假 Model/Vendor、临时数据库和受控时钟，适合证明一个函数或事务边界，但未覆盖 App 与 Web bundle 配套、浏览器重连、真实进程租约接管、Provider 未知结果以及旧 Socket 并行路径。最终必须在一组冻结修订上跨边界执行并记录命令与产物。追问：是否否定阶段测试？答：不否定，它们是必要的局部证据，只是分母不同。
4. 问：为什么最终索引要冻结十三类修订？答：App、Web、schema、bundle、Runtime、Tool、Context、Memory、Skill、Topology、Model、Vendor 和 case 都会影响行为或解释。若只记 App commit，却拿旧 Web、不同模型或更新后的 Skill 共同宣称一次验收，失败或收益无法归因。清单先固定组合身份，再让每项证据对应该组合；代码层目前只做单项来源匹配，真正联合检查仍待实现。追问：hash 相同可否说明同一实验？答：仍需数据、命令和环境证据。
5. 问：某项标 `passed` 至少需要哪些字段？答：schema 要求非空仓库内 evidenceRefs、testCommand、SHA-256 resultHash、sourceComponent 和 sourceRevision，且七项按固定顺序齐全；非 passed 不得填结果哈希。这样能挡住“只写一句通过”的自述，也限制路径穿越式引用。但字段存在只是证据目录，不证明文件内容或命令实际执行过。追问：结果哈希有什么用？答：标识结果字节供复核，不能独立证明结果真实。
6. 问：把七项填满 `passed` 就能宣布 ready 吗？答：不能。`validateFinalAcceptanceIndex` 只校验结构，`assessFinalAcceptance` 对自述索引始终返回 `ready:false`，并把自述通过项列为 unverified。只有 `verifyFinalAcceptance` 在冻结清单存在、无 pending/failed、逐项来源修订匹配且外部检查器返回真时才可能 ready。当前没有真实检查器或最终结果，因此不能拿测试中注入的 `async () => true` 冒充验收。追问：为何单测仍要用假 true？答：验证接口控制流，而不是验证证据事实。
7. 问：把 App 修订标为 Web 来源为什么要拒绝？答：修订值出现在清单里并不说明它属于所声明的组件。索引显式记录 `sourceComponent`，核验时用该键读取冻结清单的对应修订；App 值冒称 Web 即使作为别处的合法值也不应通过。单测覆盖错组件与陈旧来源。这个比较仍只是一项与一个组件的对应关系，App/Web/bundle 联合产物要由未来检查器读取证据核对。追问：为什么不能比较清单所有值集合？答：那会丢失组件身份。
8. 问：仓库内证据路径为什么要限制格式和 `..`？答：最终索引应指向版本化的报告、测试或产物，不能把本机临时文件、外部任意 URL 或路径穿越当作可复现证据。schema 将引用限制在 `docs`、`data`、`tests`、`artifacts` 前缀，并拒绝 `..` 片段。它减少输入歧义，但并未实际读取目标文件或验证 Git 跟踪状态；这些仍是独立检查器职责。追问：合规路径不存在怎么办？答：检查器应失败，不应由格式校验默认通过。
9. 问：付费 Provider canary 没运行，能否说计费正确？答：不能。索引另设 not-run/passed/failed 字段，`paidProviderCanaryGap` 与结构性 ready 分开报告；假 Provider 的请求顺序和本地账本不能证明真实费用、CDN、超时回调或供应商最终状态。即使未来七类结构性验收都过了，未跑 canary 仍必须明确披露外部行为未知；是否执行需独立预算和授权。追问：不跑 canary 是否一票否决全部结构结论？答：不必混同，但绝不能推断真实 Provider 结论。
10. 问：T02 Golden Eval 18/18 可以直接放入最终质量结论吗？答：不能。T02 的 18/18 是冻结本地 fake 场景的 deterministic hard gate，人工 rubric 仍未评审；T11 的生产 Run 成对矩阵和结果级判定也尚未完成。最终报告必须给出 baseline/candidate 的相同 case/seed 分母、每例硬门、产物、失败、人工评分来源及成本口径，不能把“结构覆盖”或旧 fake 基线冒充候选改进。追问：若有缺失 cell 怎么办？答：按缺失分母报告，不静默剔除。
11. 问：恢复类验收需要超出数据库单测的什么证据？答：需要在冻结版本下验证真实进程停止/重启、运行中租约接管、pending 审批到期、未知 Vendor 请求不重放、迟到回执保留以及 UI 重连后的权威状态。局部恢复函数与新 Runtime 实例测试能证明状态机规则，却不能覆盖 OS 进程、网络边界和多组件启动顺序。当前 T21 未运行这类测试，不能把“函数可调用”说成“灾难恢复已验证”。追问：未知结果自动重试吗？答：不能从超时推断未发生副作用。
12. 问：安全类验收为什么不能只看类型检查与正向路径？答：类型检查不审查认证 actor 与 Project 归属，也不证明旧 Socket 入口、路径解析、日志脱敏或模型提案无法绕过审批。最终应覆盖跨 Project、越权 Owner、撤销 grant、恶意资源/URL、敏感数据投影及付费请求边界的负向组合。现有阶段单测给了局部反例，仍需统一修订下的入口审计；失败要保留诊断和证据。追问：没有发现问题就等于安全？答：不等于，只能报告已测范围。
13. 问：Build 和 browser 为什么分别是两项？答：Build 证明 App 后端 bundle、Web 静态资源、声明文件和锁定依赖能在干净环境生成且与冻结修订匹配；Browser 才证明真实页面路由、模式切换、审批全文、取消与重连等用户操作正确。可构建页面仍可能有交互或缓存问题，浏览器跑通也可能依赖开发机旧产物。T01 的历史基线不能覆盖当前堆叠代码，T21 必须重新测。追问：只截图能当浏览器验收吗？答：需明确步骤、修订、断言和结果记录。
14. 问：兼容与回滚风险最终怎么交代？答：新 Script/Production Harness 与旧 Socket/工作台路径并存，不能只证明新入口成功就忽略旧入口授权、数据迁移、状态投影和失败回退。Issue #77 要求文档列出兼容、迁移、回滚、保留和运营风险；最终报告应指出哪些旧路径仍开放、何时可切流或回滚、旧持久记录怎样解释。当前阶段报告只提供局部边界，没有完成这些跨版本验证。追问：错误时自动退回旧 Socket 合适吗？答：不合适，会隐藏不同的权限与证据链。
15. 问：什么时候才可以关闭 T21 Issue？答：应先收敛其依赖的 T11、T18、T20 等开放工作，再冻结十三类修订，执行七类完整套件，生成逐项命令/结果/产物证据，独立核验引用和组合，发布 baseline/candidate 分母及所有失败，并披露 paid canary 缺口与残余风险。只有证据与 Issue #77 的每条验收条件对应，才可考虑关闭。现在只有 3 个索引契约单测和类型检查的阶段记录，绝不能提前给出完成结论。追问：若最终仍有失败？答：保留 failed 和可复现路径，不以缺失项填绿。
