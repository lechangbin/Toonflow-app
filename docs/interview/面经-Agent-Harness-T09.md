# Agent Harness T09 面经：计费请求的安全授权与不确定结果

> 仅供技术追问准备，不代写简历摘要或 bullet。第一人称回答须由本人理解并核对贡献边界后使用。T09 仍为阶段实现：定向单测通过，不得声称真实 Provider、浏览器、全量测试、上线或账单收益已经验收。

## 主题一：问题与授权边界

### Q1. 为什么旧图片“生成失败”不能作为安全重试依据？

**第一人口播：** 原来的图片状态主要服务页面展示，超时后可能显示失败，却不能证明供应商没有收到请求或没有计费。我的任务是把一条单资产生图路径改成可解释的计费操作，因此先把“本地图片结果”和“外部请求效果”拆开建模：发出前记录请求意图，超时或断线保持未知，只有看见可信产物并完成本地接受后才标记成功。定向测试用假供应商模拟超时和重复调用，验证同一审批不会再次跨供应商边界；真实账单结果仍需最终验收核对。

**追问 1A：这是不是实现了 exactly-once？**

**第一人口播：** 我不会把它叫作跨供应商的全局 exactly-once，因为网络调用和本地 SQLite 事务不能组成一个原子提交。实现保证的是同一已记录请求只给首次创建者一次外呼权，重复进入时返回既有请求并拒绝再次提交；在崩溃发生于落账后、真正发网前的窗口，系统也宁愿保留未知、等待人工核对，而不冒着重复扣费的风险自动重发。这个取舍牺牲了自动完成率，换取可解释的安全边界，最终还要用真实 Provider 验证。

**追问 1B：为什么不直接让用户点“再试一次”？**

**第一人口播：** 用户点击重试时通常只看见页面失败提示，不知道供应商是否已经受理；把同一批准当成可复用令牌，会让一次授权可能对应多次收费。我把审批限制为最多一次提交，未知结果只提供刷新、人工核对和取消意图等动作；即使未来确认供应商明确没有效果，也应创建新的操作和新的审批，让用户重新看到预算范围。前端契约测试明确要求未知状态不显示原请求重发入口，而不是仅依靠按钮临时禁用。

### Q2. 审批到底绑定了哪些东西？

**第一人口播：** 单纯保存“同意生成”无法回答用户当时同意了哪个资产、哪个模型以及可能花多少钱。我在服务端构建固定的项目与资产身份、供应商及模型、分辨率、币种、预估上限和最多一次调用，并把规范化范围计算哈希，与工具修订、预览、有效期和目标状态指纹一同持久化。批准前以及真正提交前都会重新核对项目所有权与当前输入；浏览器执行时只传审批身份，服务端取回原范围。单测证明改目标、过期或旧版本决定不能产生外部请求。

### Q3. 预算上限是否能保证供应商最终不超过它？

**第一人口播：** 不能。当前项目没有统一可信的供应商实时定价接口，供应商账单也不由本地事务控制；如果把估算写成强制封顶，就会制造错误的成本承诺。我选择让项目 Owner 显式配置按模型和分辨率版本化的本地审批估算，缺省时拒绝创建计费提案，并在界面说明这只是用户授权范围而非最终价格保证。我的阶段测试覆盖缺报价拒绝、越权配置和修订冲突；实际价格偏差需要最终验收用真实账单或 Provider 记录另行核对。

## 主题二：请求身份与不确定恢复

### Q4. 请求意图为什么必须在外部调用之前持久化？

**第一人口播：** 如果先调用供应商再写数据库，进程在两步之间退出，就会留下一个可能已计费却完全没有本地身份的请求，重启后只能猜。我把工具调用、供应商请求 ID、图片占位和请求意图检查点放进同一事务；只有事务提交成功的执行者能拿到一次提交许可。重复调用或重启读到既有身份时只返回现有请求，不再次发送。假供应商测试和启动恢复测试覆盖这条边界，但真实网络与进程强杀场景仍保留到最后验收。

**追问 4A：如果落账后尚未调用供应商就崩溃，不是永远卡住吗？**

**第一人口播：** 这是我有意承认的灰区：本地只能证明请求身份已保存，不能在重启后可靠证明外部调用尚未开始。自动补发虽然可能让一些未发送任务继续，却可能对另一些已经发出的任务形成第二次计费，因此恢复器把该状态收敛为未知并要求人工核对。我会向面试官说明这是安全与自动完成率之间的权衡，而不是宣称完全消除了分布式不确定性；将来如果供应商提供幂等键或可核验任务查询，才能进一步缩小灰区。

**追问 4B：为什么普通 HTTP 错误也可能是 unknown？**

**第一人口播：** 外部接口的错误发生在多个位置：请求可能还没离开客户端，也可能已被服务端接收，只是响应在网关或下载阶段丢失。没有来自供应商的可验证“未受理、未计费”证明时，仅凭超时、连接重置或错误码把它归类为无效果是不安全的。因此当前执行编排对调用阶段异常采用保守未知，并保存原请求身份；界面提示核对而非重新执行。这个分类偏保守，可能增加人工处理，但不会把不确定结果误导成可以免费重试。

### Q5. Provider task ID 什么时候能用于恢复？

**第一人口播：** 一个任务 ID 必须来自可信供应商响应，并先与本地请求身份一起写入检查点，之后才能按它轮询或接受完成事件。当前配置的图片 Vendor 接口是同步返回媒体，未向 Harness 暴露可核验任务 ID，所以我没有伪造轮询能力；断线后的请求只能停在未知并由操作员查看供应商记录。代码中预留了记录真实任务 ID 的状态转换与检查点，测试验证重复写相同 ID 幂等、换 ID 冲突；上线前需要具体供应商适配器提供真实语义。

### Q6. 重复点击“提交”为什么不会发出第二次收费调用？

**第一人口播：** 前端禁用按钮只防正常交互，重连、超时重发或两个窗口并发仍可能重复请求。我把提交权放在数据库事务里：先检查审批有效、版本匹配、目标未漂移和没有既有工具调用，再创建唯一的请求记录；只有创建这一记录的调用者获得 `maySubmit`，后来的调用只看见已存在请求。执行器严格在这个布尔权限为真时调用 Vendor。单元测试用假供应商计数证明重复执行的额外外呼次数为零；跨进程真实并发仍须最终验收。

## 主题三：产物、取消与本地事务

### Q7. 供应商返回图片，为什么不立即标记业务成功？

**第一人口播：** 返回媒体只说明我观察到了一个外部结果，尚不能证明文件已安全落盘，也不能证明它仍属于当前资产与审批。我的流程先校验媒体格式和内容哈希，记录与请求关联的产物证据；接着在独立的本地接受事务里重新检查所有权、审批、目标状态和取消标记，再同时更新图片、资产绑定、工具收据、运行输出与检查点。任何本地提交条件失败都保留证据而不标成功。定向测试确认接受后这些记录一致，失败时不会出现只有页面图片成功的局部状态。

**追问 7A：数据库与文件系统仍无法原子提交，怎么处理？**

**第一人口播：** 我没有假装 SQLite 事务能回滚文件系统。媒体写入前先登记与请求和内容哈希绑定的待写入记录；如果进程中断或本地写入失败，操作员仍能看到这个意图，但界面明确说明文件可能不存在、图片未成功。若文件存在，授权用户可重新读取并核对哈希，只完成本地观察，不调用供应商。测试覆盖写入失败、内容被篡改和同一媒体恢复；自动启动恢复与磁盘级故障演练尚未完成。

**追问 7B：重复回调携带另一张图片会怎样？**

**第一人口播：** 同一请求可能因供应商回调重试而收到相同内容，也可能由于异常收到不同内容；两者不能混为一谈。我用内容哈希和请求身份检查：相同媒体在已观察状态下返回既有证据，不增加第二条产物；不同哈希则拒绝替换，待写入阶段也不允许另一内容占用同一请求。这样避免后到的回调悄悄更换用户批准后实际接受的图片。测试分别断言重复回调只保留一条记录、冲突内容被拒绝，真实回调协议仍待具体供应商验证。

### Q8. 用户取消后供应商仍返回图片，系统怎么处理？

**第一人口播：** 取消按钮只能证明本地用户不想继续，不能保证供应商已停止计算或退款。我把取消记录为意图，将本地图片占位转为取消状态，并禁止正常接受事务继续绑定资产；若之后观察到图片，则以迟到产物身份保留媒体和哈希，供操作员核对可能发生的计费。结束本地跟踪后，迟到回调也只能更新证据而不能复活已取消的 Run。假供应商与数据库测试覆盖取消后迟到、不误报成功和资产未改写。

### Q9. “结束跟踪”与“供应商确实没有效果”有什么不同？

**第一人口播：** 结束跟踪是本地工作流决定，不是外部事实证明。用户可以在已取消或迟到结果时终止本地 Run，系统保留原请求、证据和“供应商效果未被排除”的注意信息，并移除可能误导的继续执行动作。若供应商明确拒绝且能验证无效果，那是另一种更强的事实，才有理由以新审批发起新请求；当前同步适配器没有提供这种可验证信号，所以不会凭人工点一下就把未知状态改成无效果。这个区分是防止面试时把状态机术语当作实际计费保证。

## 主题四：应用边界与用户操作

### Q10. Agent 能否自己选资产和模型、绕过人工审批？

**第一人口播：** Agent 或浏览器可以提出目标，但不能自行取得收费能力。服务端会根据认证用户查项目所有权，核对资产所属、已配置图片模型、最新提示词与参考媒体，形成固定的审批预览；真正执行时从持久审批取回范围，忽略浏览器附带的替换参数。Web 只根据后端允许动作显示批准、提交、取消和核对按钮。当前单资产人工入口已经接上这条受控路径；Agent 自动提案接线还未完成，因此我不会说所有 Agent 图像请求都已被统一治理。

**追问 10A：前端怎么避免把 unknown 显示成失败可重试？**

**第一人口播：** 我没有把按钮逻辑写成“状态不是成功就显示重试”。前端使用服务端投影的允许动作，未知结果显示请求 ID 和人工核对提示，不提供原审批的二次提交；取消后的状态强调退款和供应商效果都未确认，迟到产物提供证据查看和结束跟踪，而不是确认使用。纯契约测试固定了这些文案与动作映射，后端还在提交事务中拒绝重复外呼，因此即使浏览器状态陈旧，也不能靠按钮绕过服务端边界。真实点击与刷新待最终浏览器验收。

**追问 10B：用户临时改了提示词再批准会怎样？**

**第一人口播：** 用户看到的输入如果在提案与批准之间改变，原授权就不应继续有效。我让提案记录服务端最新可生成提示词的修订与内容摘要，以及所选参考图、父资产锚点的媒体哈希；批准和提交时重新读取并比较目标状态。临时只改浏览器文本却未保存，不会被当成新的服务端输入；用户需要先完成原有提示词持久化流程。定向测试覆盖提示词和媒体变化导致指纹不同；最终还要通过浏览器操作验证提示信息足够清楚。

### Q11. 为什么只迁移单资产生图，没有同时改批量？

**第一人口播：** 批量生图涉及并发槽、多个资产的部分失败和总预算聚合，直接和单次计费审批一起改会扩大证明范围。我选择先把一个单资产入口形成完整的范围、意图、产物和人工恢复闭环；旧批量路径明确保留，不把它描述为已受控。这样测试可以针对一次 Provider 副作用验证最多一次提交、重复点击和迟到结果，再将来讨论批量任务的逐项授权或总预算约束。代价是阶段内仍存在未受控旧路径，最终迁移前不能声称全系统统一收费治理。

### Q12. HTTP 入口如何避免客户端伪造操作人？

**第一人口播：** 在浏览器请求体里传一个用户 ID 没有安全意义，任何人都能修改它。我让受认证中间件保护的路由从已验证令牌中提取操作人，再由领域方法按项目 Owner 与资源归属复核；报价写入、审批决定、提交、取消、产物核对都不信任请求体里的 actor 字段。路由定向测试故意发送伪造 ID，检查实际传入的仍是认证身份，同时旧版本或越权操作映射为冲突。项目其他旧路由的权限状况不在本切片的安全结论之内。

## 主题五：证据、限制与下一步

### Q13. 当前测试能证明什么，不能证明什么？

**第一人口播：** 当前证据主要是状态转换、SQLite 提案与请求意图、假供应商调用计数、重复回调、取消迟到、媒体恢复和 HTTP 身份传递的定向测试；最近一次应用端 T09 套件是三十七个用例通过，Web 还有两个纯契约用例通过，并做了静态类型检查。它们证明代码在模拟输入和本地数据库边界下符合预期，不证明供应商真实扣费、浏览器交互、跨进程竞争或打包环境可靠。全量测试按阶段计划留到所有阶段完成后的最终验收。

**追问 13A：如何证明同一审批只调用一次供应商？**

**第一人口播：** 我会展示一条行为级而不是仅看函数返回值的测试：用假供应商累加调用次数，先通过同一审批创建请求并完成一次生成，再重复执行相同审批，断言第二次只读取持久请求且调用次数不增加。数据库中还应只有一个工具调用和供应商请求身份，产物重复回调不产生第二份接受记录。这个证据对应本地编排和 SQLite 约束，不等于供应商端 exactly-once；真实端还需核对请求日志和账单。

**追问 13B：如果最终没有真实账单数据，怎么写结果？**

**第一人口播：** 我只写能够从源码和测试核验的结构性结果，例如“同一审批的重复提交在假供应商测试中额外调用为零”“未知结果不会自动重发”“取消后的迟到产物不会自动绑定资产”。我不会写成本下降百分比、误扣费率下降或上线稳定运行，因为这些都需要真实账单、运行日志、用户操作与时间窗口。验收计划应记录请求 ID 到供应商记录的映射、估算与实际费用差异以及人工核对耗时，再决定能否形成量化结论。

### Q14. 目前最重要的技术限制是什么？

**第一人口播：** 最大限制是现有图片 Vendor 接口以同步调用返回媒体，没有向 Harness 暴露可验证的 Provider task ID。请求一旦超时，系统无法自动查询它究竟成功、失败还是已扣费，只能维持未知并给用户人工核对入口；这并非状态机没设计，而是下游契约没有提供所需事实。另一个限制是本地待写入媒体虽可被人工核对，尚无启动时自动扫描恢复。真实供应商联调、浏览器操作与全量测试也未完成，因此 T09 的 ADR 和 Issue 仍保持未验收状态。

### Q15. 下一步怎样把这个切片推进到可验收？

**第一人口播：** 我会先做 App 与 Web 的跨端契约核对，确认提案、批准、执行、超时刷新、取消和产物恢复使用同一版本与动作语义；再针对具体供应商核实是否能拿到任务 ID、幂等键或明确无效果拒绝，如果拿不到就把人工核对作为产品限制写清。之后按总计划统一跑全量单元与集成测试、App/Web 构建、浏览器断线和重复点击、真实 Provider 以及打包环境，并保存对应提交与证据。没有完成这些步骤之前，只能把当前结论表述为阶段实现。
