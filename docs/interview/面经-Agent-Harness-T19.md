# Agent Harness T19 面经：Context/Skill 消融契约（阶段版）

> 对应开放 Issue #75。目前只有版本化清单、结果拒绝规则和假 adapter 矩阵驱动，没有实际消融样本或采用结论。本文不写简历 bullet；个人 ownership 由用户按提交记录确认。

## 项目背景

Context、Memory、Skill 路由等机制都可能增加质量、延迟和成本。如果只观察最终回复，就无法判断哪一层真正贡献了结果。T19 先定义同用例、同预算、重复 seed 和安全硬门的消融契约，准备以后接入 T11 的真实 Run 证据；当前尚未运行实际策略变体。

## 主问与追问

1. 问：已经做出 Context/Skill 消融效果结论了吗？答：没有。已实现的是 `ablationContract` 的清单/结果 schema、汇总拒绝规则，以及 `ablationRunner` 对注入 adapter 的确定性矩阵驱动。Context 四个候选相对 full-context 分别移除 retrieval、Memory、compaction、provenance；Skill 比较四种路由，但所有 variant 都保留权限门。定向测试只验证契约，不包含真实策略执行、人工质量或收益数字。追问：为何先做契约？答：先固定分母与安全边界，避免看结果后再定义实验。
2. 问：为什么 Context 用 leave-one-out 而不是一次删掉所有机制？答：一次删多项会同时改变输入信息、预算与来源结构，若质量波动便无法归因到某一层。四个候选各只移除一项，保留同一个 full-context 参考和共同用例预算，使后续能问“缺了该项发生什么”。但这种设计仍不能排除机制交互，需要未来组合试验；当前甚至没有真实结果，不能声称哪一项最重要。追问：移除 provenance 会不会绕过安全？答：零容忍安全门仍保留，危险结果不能采用。
3. 问：Skill 路由消融为什么不能去掉权限闸门？答：比较的是显式、关键词、依赖感知、排序等选择策略，不是比较“有无授权”。若某候选为了速度绕开 Skill Tool permission，质量可能上升，却牺牲 Project 隔离和能力边界，实验已失去可采用前提。清单固定 permission-gated-route 参考和四种候选，安全硬门均必须通过；这只是设计约束，实际路由效果仍待执行。追问：路由变体能否改变 Skill 内容？答：应受冻结修订约束，不让内容变化混杂比较。
4. 问：为什么至少两个 seed 且所有 variant 需要同一矩阵？答：单次模型结果可能受随机性影响，不同 case 或 seed 集会让两组分数不可比较。清单要求至少两个递增唯一 seed，`expectedAblationRunKeys` 枚举 reference 与四候选的每个 case/seed；汇总把缺失与重复单列或拒绝。它只固定实验身份，当前 seed 驱动是否真正作用于供应商随机性还需要执行器证据。追问：缺一个 cell 可以只算已有分母吗？答：不能形成采用结论。
5. 问：共同预算具体冻结什么？答：清单要求各变体使用相同最大输入 Token、输出 Token、Tool 次数和超时，还锁定 App、Runtime、Tool、Context、Memory、Skill、Model、Vendor 与 case 修订。假执行驱动逐 cell 传相同预算和修订给 adapter，并在结果中检查 token、Tool、延迟是否越界。相同配置是必要条件，不证明供应商实际按同样策略消耗资源；真实执行仍需记录。追问：为什么费用不只看总额？答：每例上限可暴露少数异常昂贵 case。
6. 问：如何防止看完结果再调阈值？答：质量下限、p95 延迟、每例费用、重试上限和四种零容忍门先写入 Manifest，再与用例、修订、预算一起哈希。每条结果必须绑定该 hash，执行时间不得早于清单冻结时间。未来真实实验还需将清单及版本存成不可变文件并审查提交顺序；当前代码约束了输入形状，却没有一份已运行的正式冻结实验。追问：改阈值怎么办？答：产生新清单和新实验，不能改写旧结果。
7. 问：质量满分但发生权限提升能采用吗？答：不能。泄露、holdout 污染、脱敏失败和权限提升是零容忍硬门，任何一项 false 都计为失败；未知 null 也不能当通过。汇总把安全失败、未知、质量待审、成本、延迟和预算分别列出，不做可相互抵消的综合分。定向单测可构造满分但权限门失败来验证规则，不代表真实模型已安全。追问：为何未知不是失败？答：语义不同，但两者都不能支持采用。
8. 问：为什么预期失败类别也要按 case 冻结？答：某些权限挑战例正确行为就是拒绝，正常任务则可能期待 `none`。若只看硬门通过，错误拒绝或错误放行都可能被掩盖。Manifest 的 `expectedFailureClasses` 对每个 case 固定类别，结果逐条比较，任何非预期都阻断阈值通过；额外或缺失 case 在清单校验时拒绝。当前仅有规则测试，没有真实逐例失败分类报告。追问：为什么不能把所有失败都算坏？答：安全拒绝可能是预期成功行为。
9. 问：adapter 抛异常且错误消息含原始 Prompt，怎么记录？答：矩阵驱动在 adapter 解析异常时不持久化异常文本，而为该 cell 生成 `failureClass:evidence`、质量未审、指标与四种硬门均未知的安全失败记录；严格 schema 也拒绝 adapter 偷带 `rawPrompt` 字段。这样既保留缺口分母，也避免秘密进入可分享评测结果。它不证明正式执行器的所有日志都安全，后续仍需复用 Trace-safe 投影。追问：费用为何是 null？答：异常无法证明零费用。
10. 问：为什么结果只保留 evidence ID，不复制 Prompt 或 Provider payload？答：评测报告需要可审计，不需要扩大敏感正文或密钥的传播范围。结果 schema 只允许 manifest/case/seed、指标、失败类别、安全门和受限 ID；若质量分不为 null，必须给出评分证据 ID。检查者可去权限受控来源核查，而分享层不携带原文。当前还没有真实评审者或证据库接入，ID 存在也不能证明评分可信。追问：ID 指向不存在的证据怎么办？答：未来来源核验必须拒绝。
11. 问：p95 延迟在缺失数据时如何解释？答：汇总只对非 null 延迟排序取 p95，但要判阈值通过，延迟行数必须等于该 variant 已执行行数，且矩阵没有 missing、unknown 指标。这样一条异常导致无延迟不会让剩余快样本产生虚假的“p95 达标”。当前指标可由假 adapter 给出，不能据此声称系统延迟下降。追问：为什么不填 0？答：0 会把未知样本拉低统计量并误导成本/性能结论。
12. 问：`thresholdsPassed` 与 `adoptable` 为什么分开？答：前者只说明提供的指标对象按合同满足阈值；假 adapter 完全能填出一组漂亮数字。后者还必须证明数据来自真实生产 Agent Run、对应冻结输入和人工评审，当前缺 T11 来源核验，所以代码始终返回 `adoptable:false`。这个故意保守的状态防止“类型与单测通过”被写成方案采用。追问：何时可能改为 true？答：真实来源、评审和完整矩阵独立核验后。
13. 问：结果中的 unknown 与 hardGateFailure 有什么区别？答：失败门 false 表示有证据证明发生泄露或权限提升等违规；null 表示 adapter 失败或未取得证据，不能断言违规，也不能断言安全。汇总分别计数 `hardGateFailures` 与 `hardGateUnknown`，unknownMetrics 也独立统计。两者都会阻止阈值通过，但事故报告语义必须不同，避免把“测不出”说成“已出事”或“零风险”。追问：未知费用怎么报告？答：保持 null 并说明无法核算。
14. 问：T19 和 T11、T18 的依赖关系是什么？答：T11 需要提供冻结 case/seed 和真实生产 Run、评分与费用来源，T18 要先稳定新旧入口的兼容行为；T19 才能在此基础上实现真实变体执行、等资源重复运行、逐例报告和采用/拒绝理由。当前假驱动没有实际改变 Context/Skill 执行效果，无法替代上游证据。面试中应把契约设计与实验结果分开。追问：若 T11 样本缺失可否先宣布消融？答：只能标 incomplete，不能宣称优胜。
15. 问：完成 T19 需要哪些可核验证据？答：先在不可变清单中冻结实际 18-case 或明确子集、修订、预算、阈值及重复 seed；再让真实执行器按每个 variant/case/seed 产生生产 Run 关联和安全投影结果，独立核对评审及费用来源，发布每例失败与总分母，最后给出采用或拒绝理由。任何未跑、未知或硬门失败不得被平均数隐藏。Issue #75 当前仍开放，全量和真实环境验收要在 T21 统一完成。追问：现在有什么数字可报？答：只有契约定向测试，不报收益。
