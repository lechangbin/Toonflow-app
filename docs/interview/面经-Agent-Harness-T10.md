# Agent Harness T10 面经：可核验的因果与安全证据

> 仅供技术追问准备；用户自行决定简历写法，本文不生成摘要或 bullet。第一人称口播须结合本人实际贡献核对后使用。所有结果仅指 T10 分支与定向单测，不代表真实 Provider、浏览器、全量测试或上线验收。

## 主题一：为什么需要因果链

### Q1. 为什么已有日志还要单独设计 Trace？

**第一人口播：** 原有日志能帮助开发者定位代码位置，却不能稳定回答一次 Agent 运行中究竟先批准了什么、哪个尝试发出了请求、迟到结果属于哪次请求。我的阶段任务是把这些操作变成可持久核对的业务证据，所以我把事件写进与状态变化相同的数据库事务，记录连续序号和前驱，再关联运行、步骤、尝试与外部请求。这样即使页面重连或日志滚动，仍能按提交顺序重建过程。定向测试验证了链路，真实故障与全量系统验收还未完成。

**追问 1A：为什么不按时间戳排序？**

**第一人口播：** 时间戳适合告诉操作员大致何时发生，却不足以证明先后因果：不同模块的时钟来源、毫秒级并发、重试后的补写以及前端消息到达顺序，都可能让展示顺序看似合理却与提交顺序不同。我把每个运行的序号放在持久事务内分配，并记录上一条事件的身份；读取时检查序号连续及前驱相符。对没有前驱的旧记录明确标注历史未链接，而不是按时间把它们拼成一条虚构的完整链。

**追问 1B：一条 Trace 能代替状态表吗？**

**第一人口播：** 不能。状态表回答当前运行、审批或供应商请求现在处于什么可操作状态，Trace 回答状态怎样演变以及对应哪次尝试。若让页面只靠事件回放决定按钮，就可能在丢失或损坏事件时误开放重试；我仍以持久状态和服务端允许动作为权威，Trace 作为核验和解释层。写入时两者处于同一事务，读出时如果因果链损坏就拒绝称其完整，但保留可检查的运行状态，避免证据故障扩大为业务状态不可见。

### Q2. 如何保证 Trace 和状态不会各成功一半？

**第一人口播：** 如果先更新业务状态再异步写事件，进程刚好退出就会出现“已经提交但查不到为什么”的空白；反过来先写事件也可能宣称一次根本没成功的动作。我把追加入口接进运行、恢复、受控工具与计费图片各自的现有事务，在事务里先核对关联实体，再查最后一个序号并插入下一条。任何一步失败就让事务整体回滚。单元测试覆盖初始运行原子创建和审批、工具提交等路径；跨进程压力与真实断电仍留给最终验收。

### Q3. 为什么要同时存前驱和连续序号？

**第一人口播：** 连续序号帮助排序并发现缺口，前驱身份帮助识别同一个运行内的错误拼接或中途替换；两者解决的问题不同。实现中每次追加查当前最后一条，把它的身份作为新事件前驱，并在同一事务保存下一序号。导出时重新审计两者是否匹配，出现缺口或错误前驱就拒绝给出完整证据，不通过排序掩盖问题。这个机制不是密码学防篡改链，也没有跨数据库可信时间戳，我不会把它包装成不可抵赖审计。

### Q4. 关联 Run、Step、Attempt 和工具收据有什么价值？

**第一人口播：** 一个运行可能经过多次模型尝试和多次工具调用，只有“运行发生了错误”并不能判断错误是否发生在当前尝试、旧尝试还是别的项目。我的做法是在写 Trace 时校验步骤、尝试、工具收据与当前运行属于同一条父子链；有供应商请求时继续核对它所属的工具调用，有图片产物时核对请求归属。这样导出的关联 ID 能被业务表交叉检查，避免把一条真实事件接到错误运行上。相关失配和恢复路径有定向测试，但旧记录仍可能缺少这些关联。

### Q5. 历史 Trace 没有前驱字段，怎么迁移？

**第一人口播：** 历史记录只有当时保存的字段，升级数据库结构不可能凭空得知事件真正的前驱。我只增加可空关联列，保持旧记录原样；读取时依据序号和前驱情况区分已链接、历史未链接与损坏。若旧记录没有前驱，界面不能说它具备完整因果，即使时间看上去顺序正确。新写入从当前最后一条继续链接，保证以后产生的事件有显式前驱。升级测试检查老运行仍可读取、数据未被重写，也提醒面试官历史证据能力存在客观边界。

## 主题二：失败分类与外部效果

### Q6. 怎么证明“超时”不是“无效果”？

**第一人口播：** 外部图片请求可能已经到达供应商，响应却在网关或本地超时后丢失，因此本地异常不能证明未计费或未生成。我把 Trace 关联到持久供应商请求身份，诊断中分开记录失败阶段、效果确定性与重试处置；不确定效果保留为待核对而不直接重发。页面根据服务端状态显示核对动作，不能凭一条错误文本推导安全重试。定向测试使用假供应商模拟超时和重复调用；真实账单及供应商任务语义必须最后验收。

**追问 6A：诊断为什么不直接保存异常堆栈？**

**第一人口播：** 原始异常可能包含 URL、密钥、请求体、提示词或用户正文，而面向操作员的证据导出范围比开发环境日志更广。我的做法是把错误压到受控的失败类别、阶段、确定性、严重度和重试处置等固定字段，再用共享校验器检查字段与值；原始堆栈不进入 Trace。这样仍能解释该由谁核对、能否安全重试，同时降低把秘密带入可下载 JSON 的风险。它不能证明系统所有其他日志也安全，最终还需要独立泄漏检查。

**追问 6B：所有失败都能归类吗？**

**第一人口播：** 我只会对当前纳入 Harness 的运行、恢复、受控工具和计费图片链路作阶段性说明；历史数据和旧批量图片路径不应被说成已经完全覆盖。分类不明确时不能用“执行失败”笼统替代效果确定性，更不能把供应商调用后的错误当成无效果。当前写入路径使用安全诊断结构，导出时再次验证；如果持久记录里的诊断损坏，证据导出失效关闭。最终验收还要逐个检查实际 Provider 适配器和所有失败分支，不虚报全系统覆盖率。

### Q7. 取消以后又收到结果，因果链应如何解释？

**第一人口播：** 取消按钮表达的是用户停止本地跟踪的意图，并不保证供应商停止计算或退款。我的阶段设计让取消意图先成为独立持久事件，随后到达的图片仍关联原供应商请求和产物身份，但被标为迟到证据，不复活运行也不自动绑定资产。导出时按提交序列能看到“请求已经发出—取消意图—迟到观察”的事实，而不是把迟到结果解释为一次新的授权。假供应商及相关事务单测覆盖这一边界，真实供应商取消协议仍待核对。

### Q8. 人工审批和外部请求怎样在同一条链上？

**第一人口播：** 审批本身只能授权一次明确的目标和预算范围，不能说明供应商调用已经发生；请求意图也不能替代用户批准。我的做法是让审批、受控工具收据、工具调用、供应商请求和产物分别保留身份，并把关键状态转换写入相同运行的因果 Trace。追加时核对供应商请求属于对应工具调用、工具调用属于相同尝试和收据，避免从 UI 上把两个不相干记录拼成故事。面试时我会明确区分批准、发出、观察、接受四个边界，不把任何单一事件说成最终成功。

### Q9. 恢复后重试如何不覆盖第一次尝试？

**第一人口播：** 如果恢复器把旧尝试原位改成“重试中”，就会失去第一次调用是否已发出的证据。当前恢复逻辑根据已提交检查点判断：模型外呼意图前可建立新的后继尝试，意图后则保守停住等待核对；Trace 关联原尝试或后继尝试，并由统一追加器接上原来的前驱。这样操作员可以解释“为什么允许本地重试”与“为什么外部效果未知时不能重发”。定向恢复单测检查关联和前驱，真实进程强杀窗口仍是最终验收内容。

### Q10. Trace 能保证跨供应商 exactly-once 吗？

**第一人口播：** 不能。Trace 是本地因果证据，不会让 SQLite 和外部供应商组成分布式原子事务。我们的控制边界是先持久化一次请求身份与审批范围，只有首次提交者获得外呼权；后来的同一操作不能重复提交。如果数据库记录已落地而进程在网络调用前后崩溃，本地仍无法单靠 Trace 判断供应商是否受理，只能保留未知并核对可信外部信息。把这一限制讲清楚，比宣称精确一次更能说明工程权衡，真实供应商幂等能力尚待验证。

## 主题三：导出、权限与保留

### Q11. 为什么不能直接把数据库 Trace 行返回前端？

**第一人口播：** 数据库行的字段会随实现增长，未来可能误加入原始异常、请求内容或文件地址；如果接口直接序列化整行，安全边界就取决于每个后续开发者是否记得隐私要求。我在服务端建立明确字段白名单，只投影身份、提交序列、状态和经过验证的安全诊断；最终对象再过一次共享敏感内容检查。越权、超量、损坏或不安全内容都整体拒绝导出。定向单测覆盖这些拒绝路径，但下载后的用户自行传播不属于服务端可控制范围。

**追问 11A：前端再做一次脱敏不行吗？**

**第一人口播：** 只在前端脱敏意味着敏感值已经穿过网络并进入浏览器内存、开发者工具或缓存；即使视觉上遮住也不能撤回泄漏。因此服务端先按 Owner 身份授权，再构造最小化的证据对象并作安全校验，前端只负责展示和下载这个服务端版本。前端也验证版本和事件结构，以避免把意外字段展示成可信结果，但那是第二层防御，不能替代服务端控制。最终验收应抓包检查真实返回，而不只看抽屉里的文字。

**追问 11B：为什么超过上限不分页导出？**

**第一人口播：** 当前导出表示一份可解释的运行证据，如果静默截断后仍叫它完整时间线，可能刚好漏掉取消或迟到产物，误导面试和运维判断。我给一次导出设定明确条数上限，超过时拒绝而不是返回一个没有缺口标识的前半段；未来若要分页，需要带稳定快照边界、页间连续性和完整性汇总，不能简单用偏移量分批。这个取舍优先保证当前证据语义诚实，长生命周期项目的导出容量仍待最终压测。

### Q12. 项目存续期间为什么不定期删除 Trace？

**第一人口播：** 对有外部计费和未知效果的 Agent 运行，几天前的请求可能在后续对账或用户投诉时才需要核对。如果用固定 TTL 自动删除 Trace、收据和产物证据，运行仍存在却失去了证明请求身份和审批范围的材料。当前策略明确保留到 Project 生命周期结束，不单独保存导出的 JSON；只有 Owner 删除整个项目时，关联的 Agent 证据随数据库事务清除。这个策略有存储成本，增长曲线和合规保留期仍需依据真实部署场景评估，不能说它已是通用最优。

### Q13. 删除 Project 时如何避免“业务没了但证据还在”？

**第一人口播：** 删除不是简单一条项目记录的删除语句：Trace、审批、工具收据、供应商请求、产物和检查点彼此有关联，也可能仍有运行中的状态。我的实现先确认请求者确为 Project Owner，然后在同一 SQLite 事务内删除项目和相关 Agent 证据；审批删除保护只在这个项目删除事务中通过临时许可，普通删除仍受拦截。如果任何一步失败，数据库事务回滚，避免留下半删除记录。测试注入清理失败并检查回滚；旧版本遗留孤儿记录的历史清理另需评估。

### Q14. 数据库删除成功但本地图片目录删不掉怎么办？

**第一人口播：** SQLite 事务不能包含文件系统操作；若先删目录再删数据库，数据库失败会留下引用已消失文件的记录。我选择先提交有权限的数据库删除，再清理项目媒体目录，并把媒体结果作为独立状态返回。清理失败时前端明确提示需人工处理，不能向用户谎称文件也已删除。这个路径目前没有自动重试队列，属于已知限制；最终验收需要故障注入、目录权限场景与实际人工处理流程，不能把单元测试等同于磁盘级保证。

### Q15. 怎么向面试官说明当前的证据强度？

**第一人口播：** 我会把“已实现机制”和“已验证效果”分开讲。代码里有版本化的时间线、脱敏和保留策略，定向测试验证了前驱关联、旧库升级、权限、损坏拒绝和 Project 删除回滚；这能支撑阶段性的架构结果。它不能证明所有旧路径都写入完整 Trace，也不能证明真实供应商的账单、浏览器抓包、并发压力或磁盘故障已通过。我会展示具体测试及 PR 作为证据，同时把这些缺口列到最终验收清单，避免把待测性能或线上收益写成事实。
