# Agent Harness T03 面经：Trace-safe 诊断与脱敏门禁

> 使用边界：按本阶段约定，本文件不提供简历项目简介和简历 bullet，只提供基于真实实现的面试准备材料。证据基线为提交 `20db9d1b9e78ad9a9706fd79afbeabd46e416699`。所有“结果”仅指源码结构、聚焦单元测试或静态守卫能够证明的结果；没有上线、性能收益或完整回归结论。全量测试、正式构建与端到端验收延期到所有阶段完成后的最终验收。

## 一、Agent Harness（8 道）

### 1. 你为什么要为 Agent 系统设计统一的安全诊断契约？

**口述答案（STAR/证据化）：** 在这个阶段，我面对的情境是 Agent、Vendor、VM、评测和 UI 都可能产生失败信息，但原来主要依赖自由文本或各调用点自行处理。我的任务不是增加更多日志，而是让诊断在跨边界时既可分类又不泄漏。我将失败拆成主分类、阶段、稳定 kind、严重度、结果确定性、预期性和重试处置，并建立带版本号和 audience 的统一投影。随后让评测和图片 Vendor 适配复用同一入口，同时把旧自由文本入口收紧。阶段结果可以由诊断模块、ADR 和聚焦单测核验；我不会声称 Run/Trace 存储或线上观测已经完成，因为它们属于后续里程碑。

**追问 1：为什么不让每个业务模块自己脱敏？**

**口述答案（STAR/证据化）：** 当规则散落在调用方时，我观察到同一类数据会被不同处理：有的去掉 message，有的仍输出 response，有的把 URL 当普通字符串。我的任务是降低策略分叉和审计成本，所以把递归检查、字段白名单、秘密模式、异常链和结构路径集中到一个深模块，业务只负责提供受控语义。这样新增敏感类型时主要修改一个边界并扩充负向夹具，而不是搜遍仓库碰运气。当前结果是 Golden Eval、图片失败映射和旧日志入口共享或服从同一安全边界；但是否覆盖所有历史日志仍需最终验收和持续扫描，不能把本阶段静态守卫夸大成全仓绝对证明。

**追问 2：这个统一契约会不会过度设计？**

**口述答案（STAR/证据化）：** 如果系统只有单一同步调用，一个错误码可能够用；但这里已经存在模型调用、工具执行、图片生成、下载、评测和 UI 等不同消费者。我的任务是用最小但可扩展的维度解决真实歧义，而不是抽象未来幻想。比如 timeout 只说明 kind，不能说明副作用是否发生；audience 只说明投影去向，不能替代 failure class。因此这些维度各有独立决策价值。我也刻意没有在 T03 同时建设数据库、查询页面和分布式追踪，只先稳定出口契约。这个范围控制说明设计是为当前跨边界问题服务，并通过 ADR 明确后续扩展点和代价。

### 2. 为什么选择 fail-closed，而不是发现危险字段后删掉再输出？

**口述答案（STAR/证据化）：** 当诊断对象包含未知字段或秘密时，简单删除字段虽然能减少直接泄漏，却会产生新的语义风险：消费者看到剩余结构，可能误以为证据完整。我的任务是同时保护机密性和证据可信度，因此任何敏感 key、秘密值、原始 Provider 载荷、隐藏推理、URL、二进制、未知字段、循环或过深结构都会拒绝整条导出。返回值只包含稳定 violation code 和索引化结构位置，不回显原 key/value。阶段结果由版本化负向夹具和恶意输入单测证明。代价是合法新字段也会先被拒绝，但这迫使契约变更经过显式评审，而不是静默漂移。

**追问 1：整条拒绝会不会损失太多可观测性？**

**口述答案（STAR/证据化）：** 会有可观测性损失，所以我把它当成明确取舍而不是免费收益。情境是安全边界无法证明部分删除后剩余内容仍完整，我的首要任务是避免输出不可信的半截证据。行动上，拒绝结果仍保留 violation code 和结构位置，调用方可以统计哪类契约失败，却拿不到原始秘密；对旧日志则输出稳定拒绝标记。结果是安全失败可聚合，但细节定位需要在受控本地环境或调用方重构为白名单字段。后续应把高价值自由文本逐个迁移为结构化属性，而不是放松门禁。当前没有测量误拒绝率，必须在最终验收用合法样本回放补充数据。

**追问 2：如果只是出现一个未知但无害的字段，为什么也要拒绝？**

**口述答案（STAR/证据化）：** 未知字段的问题不只在当前值是否无害，还在于消费者不知道其语义、生命周期和未来取值。我的任务是阻止未经审查的契约扩张，因此运行时会枚举顶层字段与属性 key，即便值看起来普通，也返回 unknownField。要支持新字段，需要先定义用途、类型、范围和是否会携带用户数据，再更新 allowlist、测试与文档。这样结果是 schema 演进成为显式动作，评测、Trace 和 UI 不会各自解释同名字段。提交中的未知字段测试证明了拒绝行为和不回显值，但新字段治理流程仍是团队约定，需要后续在变更模板或 CI 中进一步固化。

### 3. 你如何设计诊断分类法，为什么不是一个错误码解决所有问题？

**口述答案（STAR/证据化）：** 我先从诊断的使用动作反推维度：面试或排障需要知道哪里失败、属于哪一类、是否预期、影响是否确定、能否重试。任务是避免把这些正交问题压进一个不断膨胀的字符串。行动上，我定义六个主 failure class，并用 stage 和稳定 kind 描述位置与现象，再用 severity、certainty、expectedness、retryDisposition表达处置含义。例如 Vendor timeout 可以同时是错误级别、非预期、结果未知、先对账。结果是消费者可按不同维度聚合，且测试会拒绝未注册 stage/kind。分类法目前只覆盖已识别场景，不声称完备；新增类别必须结合真实故障样本演进。

**追问 1：failure class 和 kind 有什么区别？**

**口述答案（STAR/证据化）：** 在设计时我把 failure class 当作稳定的责任域，把 kind 当作更具体、跨阶段可复用的失败现象。比如 Vendor 是主分类，timeout、transport、providerRejected 是 kind；Tool 是另一主分类，但也可以有 executionFailed。我的任务是让高层报表能按责任域聚合，同时让处置逻辑针对稳定现象决策。如果把所有信息塞进 `vendor_image_generation_timeout` 这类组合码，组合数量会快速膨胀，改名也影响所有消费者。当前实现用独立字段和运行时注册表约束二者，聚焦测试验证六类主分类均可通过同一投影；真正的统计看板尚未实现，所以这里只能陈述可聚合的契约能力。

**追问 2：为什么 stage 和 kind 都要做运行时注册，而不是只靠 TypeScript？**

**口述答案（STAR/证据化）：** 类型系统只保护编译期可信调用，对 JSON、VM、数据库旧记录、第三方对象和 `as never` 之类断言都无能为力。我的任务是把安全保证放到实际出口，因此在投影时再次检查 audience、stage、kind、严重度和处置枚举。行动上，提交定义显式注册表，并用“看起来合法但未注册”的字符串做负向测试，证明它不会因符合正则就通过。结果是契约漂移在运行时被拒绝，而不是进入持久化或 UI 后才暴露。代价是每次扩展都需要同步发布；后续若存在多版本客户端，还需设计版本兼容策略，T03 尚未覆盖这一部分。

### 4. 你如何防止秘密、原始响应和隐藏推理进入诊断？

**口述答案（STAR/证据化）：** 情境是泄漏并不只来自名为 apiKey 的字段，也可能藏在数组、异常 cause、JWT、Bearer 文本、签名 URL、Base64 数据或 Provider 原始响应里。我的任务是建立递归且有界的检查器。行动上，我同时检查 key 语义和字符串模式，对对象、数组、Error、Buffer、TypedArray 做分类；检测循环引用和最大深度；对 raw response、payload、reasoning 等语义键直接拒绝；违反时只输出稳定代码与结构索引。结果由版本化负向夹具覆盖 npm/GitHub/AWS 风格凭据、Data URI、签名 URL、二进制和隐藏推理。它是工程门禁而非形式化证明，未知秘密格式仍需持续补充。

**追问 1：正则检测会有误报和漏报，你怎么处理？**

**口述答案（STAR/证据化）：** 我没有把正则宣传成万能 DLP。面对误报和漏报，我的任务是用多层约束降低风险：首先只允许少量结构化字段，从源头缩小输入面；其次对 key 和 value 分别检测；再次限制字符串为安全标识符，数值有语义范围；最后用负向夹具固化已知绕过案例。结果是即便某个秘密模式未命中，它仍可能因未知字段、URL 或原始载荷语义被挡住。误报则通过合法样本回放识别，再以明确契约扩展解决，而不是在调用点绕过。最终仍需结合真实日志审计和安全测试，当前阶段没有“零泄漏率”的测量证据。

**追问 2：为什么 violation path 不直接包含原字段名？**

**口述答案（STAR/证据化）：** 原字段名本身也可能是攻击者输入，甚至包含 token、用户文本或路径，因此错误报告如果原样回显 key，会形成二次泄漏。我的任务是让拒绝结果可定位但不复制不可信内容。行动上，检查器记录 `payload.[key:n]` 这类结构索引和稳定 violation code，而不记录原 key/value。结果是开发者能知道问题位于第几个字段、属于何种规则，并结合本地受控复现定位；跨边界输出则没有秘密副本。这个折中降低了远程排障便利，后续可以考虑在受保护环境使用不可逆字段名哈希，但 T03 没有实现，也不应在面试中说成已有能力。

### 5. 异常链为什么只保留 Error.name？

**口述答案（STAR/证据化）：** 在旧代码里，异常 message 和 stack 很容易携带请求正文、签名 URL、文件路径或 Provider 响应，但完全丢弃 cause 又会损失“哪一层失败”的信息。我的任务是在定位价值和最小披露之间取平衡。行动上，我遍历有界的 Error cause 链，检查 message 中是否存在危险内容，但投影结果只保留经过安全标识符校验的 `name`；循环和超过八层会拒绝。结果是可以看到 AgentRunError、ToolExecutionError、PersistenceError 这样的类别序列，却看不到正文和堆栈。聚焦测试验证了干净原因链可输出、含秘密消息会整体拒绝，尚未验证真实生产异常分布。

**追问 1：Error.name 也可能被恶意赋值，你考虑了吗？**

**口述答案（STAR/证据化）：** 考虑了，因为 JavaScript 的 Error.name 是可写字符串，不能把它当可信枚举。我的任务是避免攻击者把密钥塞进 name 绕过“只保留名称”的策略。行动上，name 先经过长度与字符集限制，再经过同一秘密字符串检查；不符合契约会产生 invalidContract 或 secretValue，并导致整条投影失败，而不是把它替换后悄悄继续。测试中把 npm 风格 token 放入 Error.name，验证返回值不包含原值。结果说明异常链出口仍服从统一安全规则；不过 Error 子类名称注册表目前没有单独维护，后续若需更强聚合可再收紧。

**追问 2：为什么不保留清洗后的 message？**

**口述答案（STAR/证据化）：** 自由文本 message 的组合空间太大，清洗意味着我必须证明所有秘密格式、路径、用户输入和 Provider 内容都被识别，这在当前阶段做不到。我的任务是给跨边界诊断提供可承诺的安全属性，因此选择不输出 message，只保留结构化字段和受约束名称。结果是诊断细节减少，但不会因为“看起来清洗过”就让消费者误信；需要的业务信息应由调用方提炼成允许的 operation、attempt、status 等属性。未来若引入受控 message template，也应使用模板 ID 加参数白名单，而不是恢复任意文本。该模板机制尚未实现，所以当前答案必须坚持实际边界。

### 6. 你如何建模失败后的重试策略，避免重复副作用？

**口述答案（STAR/证据化）：** 在图片生成链路中，请求超时并不能证明供应商没有受理，如果直接自动重试，可能重复生成、重复计费或产生两个资产。我的任务是把传输现象与业务副作用分开。行动上，我引入结果确定性：`known-no-effect` 表示可确认未执行，`known-effect` 表示副作用已出现，`unknown-effect` 表示无法判断；再独立给出 `safe-retry`、`deduplicate-first` 或 `reconcile-first`。图片生成阶段的 timeout、transport 和 HTTP 错误按结果未知处理，下载失败因为远端产物已存在而按已发生处理，两者都先对账。聚焦单测验证映射，真实 Provider 对账接口仍属后续能力。

**追问 1：为什么 HTTP 错误也可能是 unknown-effect？**

**口述答案（STAR/证据化）：** HTTP 状态只能说明客户端观察到的响应，不总能证明服务端事务是否执行。例如网关可能在上游已受理后返回 502，或者响应在代理链路丢失。我的任务是选择保守且不会扩大副作用的默认值，所以对生成阶段的 httpError 与超时、传输失败统一映射为 unknown-effect 和 reconcile-first，而不是仅凭状态码自动重放。结果是处置层被迫先查询供应商任务或使用幂等键确认状态。当前 T03 只建立语义和测试映射，没有实现所有 Vendor 的查询与去重能力，因此我会明确说“为后续对账提供契约”，而不是宣称重复生成问题已经端到端解决。

**追问 2：下载失败为什么是 known-effect，而不是 known-no-effect？**

**口述答案（STAR/证据化）：** 下载阶段意味着供应商已经返回了可获取的媒体位置，生成副作用至少在远端发生了。我的任务是让重试策略反映这个事实：如果把下载失败标成 known-no-effect，系统可能重新提交生成请求，造成不必要的重复产物。行动上，我把 download 阶段和 noImageData 这类已观察到供应商结果的场景映射为 known-effect，并要求 reconcile-first；后续可以重试下载或核对远端任务，而不是重做生成。聚焦测试覆盖了这个映射修正。至于远端 URL 是否仍有效、下载能否幂等恢复，需要最终端到端验收和后续恢复机制验证。

### 7. 统一契约如何服务 Trace、ToolReceipt、评测和 UI 四种消费者？

**口述答案（STAR/证据化）：** 四类消费者对信息用途不同，但如果各自实现脱敏，很容易产生最弱环节。我的任务是先统一“什么可以离开原始执行上下文”的最低安全契约。行动上，投影接口要求显式 audience，并在输出中记录版本和受众；同一结构化输入分别投影到 trace、toolReceipt、evaluation、ui，均经过完全相同的字段、值和原因链门禁。测试既验证正常输入对四种受众一致通过，也验证同一恶意输入对四种受众全部拒绝。结果是形成共享出口协议，但 T03 没有新增四套存储或完整 UI，因此 audience 当前代表消费意图和未来接口，不等价于各消费系统已落地。

**追问 1：不同 audience 未来需要不同字段怎么办？**

**口述答案（STAR/证据化）：** 我会把共同安全核心与受众特定投影分层，而不是复制四套检查器。当前情境是先建立最小共同契约，所以所有 audience 共享字段集合。未来如果 UI 只需用户可理解的 kind，而评测需要 attempt 和 elapsedMs，我的任务会是先在核心模型里证明字段安全，再由 audience 策略做进一步最小化；任何特定字段仍不能绕过共同门禁。这样结果是“核心允许”不代表“所有受众都必须暴露”，可以单向收窄。当前提交尚未实现受众差异化字段表，所以面试中我会把它作为演进方案，而不会伪装成已有功能。

**追问 2：如何保证四个消费者不会出现安全策略漂移？**

**口述答案（STAR/证据化）：** 我的主要措施是把规则放在共享投影而不是消费者内部，并用参数化测试对全部 audience 运行相同恶意样本。任务是让新增受众或修改规则时，测试自动暴露不一致。行动上，受众值也有运行时注册表，非法 audience 会被拒绝；正常和恶意案例都遍历固定集合。结果是当前源码中的四个标签没有独立旁路。后续如果消费者在投影之后又拼接自由文本，核心模块无法单独阻止，所以最终验收还要从实际日志、响应和持久化出口做端到端扫描，这也是我没有把阶段单测说成完整安全证明的原因。

### 8. 你如何验证安全门禁，而不只写 happy path？

**口述答案（STAR/证据化）：** 安全代码如果只测正常对象，无法证明面对恶意结构时会怎样失败。我的任务是建立可重复、可扩展的负向证据。行动上，我创建带 schemaVersion 与 taxonomyVersion 的 JSON 夹具，覆盖 Base64/Data URI、签名 URL、常见凭据、敏感 key、原始 Provider 载荷、隐藏推理和二进制；代码测试另覆盖循环、深度、恶意 getter、异常链、非法数值、未知字段与未注册枚举。同时增加静态契约测试，防止关键旧入口重新打印捕获异常。阶段结果是聚焦单测和静态检查可验证这些规则；全仓测试、构建和 E2E 按用户要求留到最终验收。

**追问 1：为什么负向夹具要版本化？**

**口述答案（STAR/证据化）：** 门禁规则和分类法都会演进，如果反例只是散落在测试代码里，很难判断某次 schema 变化对应哪套威胁语料。我的任务是让安全回归资产可追踪，所以夹具同时记录自身版本和目标 taxonomy 版本，每个 case 有稳定 ID、允许字段和期望 violation codes。结果是新增绕过案例可以作为数据条目被复用，评审也能看到规则变化是否改变预期。当前只建立第一版夹具，还没有兼容多版本执行器或自动生成安全报告；这些是后续可深化项，不能把“有版本号”夸大成完整的契约迁移平台。

**追问 2：静态正则测试可靠吗？**

**口述答案（STAR/证据化）：** 静态正则测试不是语义分析器，既可能漏掉等价写法，也可能因格式变化产生误报。我使用它的情境是保护少数已经迁移的高风险路径，任务是快速阻止明显回退，例如再次把捕获的 error 或 Provider 对象传给 console。它与运行时单测互补：前者约束调用点文本模式，后者验证核心门禁行为。结果是本阶段关键入口有低成本护栏，但不能代表全仓数据流安全。最终验收还应加入 lint 规则、AST 检查、真实 E2E 输出扫描或专业安全审计；这些未在提交中实现，所以我会清楚说明证据强弱。

## 二、Agent 应用开发（4 道）

### 9. 这套诊断能力如何改善 Agent 应用的错误处理？

**口述答案（STAR/证据化）：** Agent 应用的失败经常跨越上下文构建、决策、工具、Vendor 和产物保存，如果只返回一段错误字符串，UI 无法稳定展示，重试逻辑也会误判。我的任务是把失败变成可消费的领域事实，而不是把底层异常直接向上抛。行动上，我用 failure class、stage、kind、certainty 和 retryDisposition建立稳定语义，并让 UI 成为受控 audience；旧 Agent socket 路径不再回传捕获异常原文，而使用本地稳定错误。结果是上层具备基于类别决定提示和恢复动作的契约基础，同时降低 Provider 信息泄漏。当前尚未完成完整诊断 UI，所以改善主要体现在后端出口和接口可设计性。

**追问 1：用户看到固定错误会不会体验更差？**

**口述答案（STAR/证据化）：** 短期看，固定错误比详细 Provider 文本少，但原始错误既可能泄漏又不稳定，直接展示会让产品行为受第三方措辞控制。我的任务是先建立安全且可预测的用户边界。行动上，socket 和模型测试等路径返回本地通用错误，详细处置语义保留在结构化诊断契约中；未来 UI 可以基于稳定 kind 映射为经过产品审核的文案和操作按钮。结果是错误展示从“透传字符串”转向“稳定分类驱动”，但 T03 没实现全部文案映射，因此我承认当前用户细节减少，并把可解释 UI 作为后续建设，而不是声称体验已量化提升。

**追问 2：Agent 失败时哪些信息适合展示给用户？**

**口述答案（STAR/证据化）：** 我会按最小必要原则区分用户行动信息和内部诊断信息。用户需要知道操作是否完成、是否可重试、是否应等待或检查配置，不需要 Provider 原始响应、请求 ID、堆栈或隐藏推理。我的任务是让这些边界可由契约表达。行动上，UI audience 仍经过统一门禁，certainty 和 retryDisposition可支持“先刷新状态”“安全重试”“联系管理员”等产品决策；failure class 和 kind用于映射稳定文案。结果是具备设计基础，但当前提交只证明安全投影，没有实现完整 UI 映射和可用性测试，所以面试中应区分“接口能力”与“已交付体验”。

### 10. 你怎样把 Vendor 错误适配成应用内部稳定语义？

**口述答案（STAR/证据化）：** 不同 Vendor 的错误字段、状态和消息经常变化，如果直接向领域层传播，业务会绑定第三方细节。我的任务是建立防腐层。行动上，我定义图片失败的有限 kind、stage、attempt 和少量白名单属性；进入共享投影前先检查精确顶层字段、枚举和数值范围，非法契约不会被静默修正，而会标为 contractRejected。合法诊断再映射为统一 failure class、certainty 和 retryDisposition。结果是领域逻辑不需要理解 Provider 原始对象，且恶意或漂移字段无法混入。阶段测试覆盖非法 kind、stage、秘密与未知字段；真实多 Vendor 兼容仍需逐适配器验证。

**追问 1：为什么不能把非法 Vendor 字段纠正为默认值？**

**口述答案（STAR/证据化）：** 静默纠正会把“不知道发生了什么”伪装成一个合法事实。例如未知 kind 默认成 transport，可能让系统选择错误的重试策略；负数 attempt 被改成 1，也掩盖上游契约问题。我的任务是保护诊断证据的真实性，所以在导出和持久化边界采用严格验证，遇到未知字段或非法范围整条拒绝。为兼容旧调用可以保留清洗 helper，但不能让它承担可信出口。结果是错误会更早暴露为 contractRejected，便于修复适配器；代价是老数据可能被拒绝，需要迁移计划。提交中的严格 validator 与负向测试证明了这一行为。

**追问 2：Provider request ID 为什么可以保留？**

**口述答案（STAR/证据化）：** request ID 对供应商侧对账和工单定位有价值，但也不能无条件透传。我的任务是只保留必要且可验证安全的标识。行动上，我把它放入显式属性白名单，要求是长度受限、只含安全标识符字符的字符串，并再次经过秘密模式检查；URL、空格、密钥样式或过长内容会使投影失败。结果是合法 ID 可以用于关联，而 Provider 原始响应不会随之进入。是否所有供应商 ID 都符合当前字符集还需真实样本验证；如果发现合法格式不兼容，应调整契约和测试，而不是在调用方绕过门禁。

### 11. Golden Eval 为什么要复用同一检查器，怎样避免破坏既有评测？

**口述答案（STAR/证据化）：** 评测数据常包含模型输出、证据和失败详情，本身也是敏感信息出口。如果评测单独维护脱敏逻辑，会与 Trace 或 UI 产生差异。我的任务是复用核心安全规则，同时保持既有 Golden Eval 对外结果兼容。行动上，我让评测适配层调用共享 `inspectTraceSafePayload`，保留原有包装格式和既有基线输出，不把新的内部分类强行改写到外部结果。阶段验证包括评测聚焦单测和基线结果对比，说明共享门禁没有改变约定输出。全量评测集和生产数据回放尚未执行，因此只能声称局部兼容已验证。

**追问 1：为什么不直接让评测输出完整 TraceSafeDiagnostic？**

**口述答案（STAR/证据化）：** 既有评测已经有消费者和基线格式，直接替换会把安全重构与协议迁移绑定，增加回归面。我的任务是先统一安全语义，而不是在一个阶段同时重做所有外部接口。行动上采用适配模式：内部调用共享检查器，外层继续产生原约定结构；未来若升级 schema，可以通过显式版本迁移逐步推进。结果是降低了 T03 的变化范围，也能用字节级基线证明未意外改动。代价是短期存在包装层，后续要维护边界；但这比未经版本管理的一次性破坏更可控。

**追问 2：评测中如果出现隐藏推理，为什么也要拒绝？**

**口述答案（STAR/证据化）：** 隐藏推理可能包含系统提示、内部策略、用户隐私或不可作为产品证据的中间过程。我的任务是保证评测出口只使用明确允许的结果与证据字段，而不因“仅内部评测”就降低安全标准。行动上，检查器对 reasoning、thinking、chain-of-thought 等语义键直接给出 hiddenReasoning，并整条拒绝；四个 audience 使用相同规则。结果是隐藏推理不会被评测数据顺带持久化或导出。若未来需要研究中间信号，应设计独立、隔离且有权限控制的数据方案，当前实现没有该能力，所以不能通过改字段名绕过。

### 12. 旧自由文本日志如何迁移，为什么选择固定拒绝标记？

**口述答案（STAR/证据化）：** VM logger 和进程级异常入口接收任意值，没有足够上下文证明哪段文本安全。我的任务是在不一次性重写所有调用方的前提下先关闭泄漏出口。行动上，我把 legacy formatter 改成无条件返回稳定的 `diagnostic-rejected:unstructuredLog` 标记，VM 与全局错误路径使用它；同时迁移模型测试、socket、后台任务和 Vendor 适配器，删除异常正文、签名材料与原始响应日志。结果是旧接口不会再回显“看起来普通”的路径、JSON 或 token，静态守卫防止关键写法回归。后续仍应把有价值日志改为结构化诊断，因为固定标记只是安全降级，不是最终观测体验。

**追问 1：为什么不先正则扫描，安全文本就继续输出？**

**口述答案（STAR/证据化）：** “没匹配到已知危险模式”不等于“已证明安全”，尤其自由文本可能包含新型 token、业务隐私、Windows 路径或经过编码的内容。我的任务是对跨边界输出给出可解释保证，所以 legacy 入口不再做猜测，而是全部固定标记。行动上，真正需要保留的信息必须由调用方转成白名单结构，经过类型和运行时规则。结果是避免安全感来自不完整正则；代价是旧日志信噪比下降。这个取舍在 ADR 和测试中可核验，后续结构化迁移完成度应作为最终验收项，而不是恢复自由文本回显。

**追问 2：如何渐进迁移而不让排障完全失明？**

**口述答案（STAR/证据化）：** 我会先盘点高价值失败路径，再按业务优先级为每个路径定义稳定 kind、stage 和少量属性，而不是把旧 message 原封不动搬进 operation。任务是逐步恢复可观测性，同时守住安全边界。行动上，调用方先构造结构化输入，经统一投影成功后再交给受众；拒绝次数可作为迁移信号。对于暂未迁移的入口保留固定标记，至少能统计事件发生。结果是观测信息从不受控文本逐步转为可聚合语义。T03 已完成部分关键入口收口，但没有给出全仓迁移比例，面试中不能虚构覆盖率。

## 三、AI 应用后端（3 道）

### 13. 这套设计在后端边界治理上解决了什么问题？

**口述答案（STAR/证据化）：** AI 应用后端同时连接客户端、Agent、数据库、VM 和第三方 Vendor，任何一层的原始错误都可能穿透到日志或响应。我的任务是明确数据越界前的最后一道可信检查。行动上，我将诊断投影设计成深模块：输入必须符合固定 schema，递归载荷受检查，异常正文不输出，Vendor 原始消息在适配器处转换为本地稳定错误，路由与 socket 不再直接返回捕获异常。结果是边界从“调用方自觉”变为“出口强制契约”，并有静态守卫和单元测试支撑。它尚未替代认证、授权、审计日志和数据分级，因此只是后端纵深防御的一层。

**追问 1：为什么这是后端职责，而不是前端展示层的职责？**

**口述答案（STAR/证据化）：** 如果只在前端隐藏，敏感内容已经经过网络响应、服务日志或持久化，泄漏事实并未消失；其他客户端也可能绕开该前端。我的任务是把控制放在最接近数据源且能覆盖所有消费者的服务端边界。行动上，后端先将错误转成安全诊断，UI 只接收经过投影的稳定语义，再做用户文案映射。结果是安全策略不依赖某个页面版本，并能同样保护评测和未来 ToolReceipt。前端仍负责最小展示和交互，但不能承担清洗 Provider 原文的核心责任。当前提交主要在后端仓库落地，没有声称前端已完成全部适配。

**追问 2：为什么还需要调用点静态守卫，核心门禁不够吗？**

**口述答案（STAR/证据化）：** 核心门禁只能保护经过它的数据，如果调用点仍直接 `console.error(error)` 或把 `message` 写入响应，就会形成旁路。我的任务是同时减少旁路和保护主出口。行动上，一方面让关键路径调用共享门禁，另一方面用静态测试检查已经迁移的模型测试、socket、后台任务、全局错误和 Vendor 文件不再出现高风险写法。结果是防御覆盖“规则正确性”和“调用路径服从规则”两个层面。静态正则并非完美数据流分析，所以最终验收还应进行全仓搜索和端到端输出扫描，当前不能声称旁路为零。

### 14. 你如何处理不可信对象、循环引用和恶意 getter，避免诊断代码自身崩溃？

**口述答案（STAR/证据化）：** 诊断通常运行在失败路径上，如果检查器因循环对象、超深结构或 getter 抛错再次崩溃，会放大原故障，甚至成为拒绝服务入口。我的任务是让门禁在异常输入下确定性失败。行动上，我用 WeakSet 跟踪递归对象，设置最大深度，对 Buffer、ArrayBuffer 和视图单独处理，并把 `Object.entries` 包进安全读取函数；无法枚举时只记录 invalidContract，不传播原异常。结果是循环和深层对象返回稳定 violation，legacy formatter 面对恶意 getter也只输出固定标记。聚焦单测验证这些边界，但尚未进行大规模模糊测试和性能压测。

**追问 1：为什么设置最大深度，深度选取如何解释？**

**口述答案（STAR/证据化）：** 没有深度上限时，攻击者可以构造极深对象消耗栈和 CPU；即便没有攻击，诊断对象过深也违背“少量结构化字段”的设计目标。我的任务是建立明确资源边界，所以检查器超过固定层数就返回 payloadTooDeep，而不继续遍历。当前数值是工程保护阈值，并非基于生产基准得出的最优值。结果是行为确定且可测试；最终验收应通过典型 payload 和恶意深层对象做基准，再决定是否调整阈值。面试中我会说明它是安全上限，不会虚构性能数据或宣称已经完成容量规划。

**追问 2：WeakSet 和 Set 分别用在什么地方？**

**口述答案（STAR/证据化）：** 对普通对象递归检查时，我使用 WeakSet 记录已经访问的对象引用，用于识别环，同时不需要长期持有对象；对 Error cause 链则使用局部 Set，因为链深度很小且元素类型可能需要作为 unknown 处理。我的任务是确保两类遍历都不会无限循环。行动上，一旦再次遇到同一引用，就生成 circularReference，并停止该路径；原因链还额外限制最大层数。结果由循环对象和原因链测试覆盖。这里的选择主要是生命周期和 API 适配，不是性能优化结论；没有基准数据时我不会宣称 WeakSet 带来具体内存收益。

### 15. 你如何规划数据库、兼容性和最终验收，而不让 T03 范围失控？

**口述答案（STAR/证据化）：** 统一诊断很容易顺势扩展到 Run 表、Trace 表、查询 API、前端页面和全链路追踪，但一次完成会让契约设计与存储迁移相互绑死。我的任务是先交付可复用且经过局部验证的安全出口。行动上，我在 ADR 中明确 T03 不创建 Agent Run/Trace 持久化；schemaVersion 为后续迁移提供锚点；现有 Golden Eval 用适配层保持输出兼容。本阶段只跑聚焦单元测试和静态检查，完整测试、生产构建与 E2E 统一延期到全部阶段后的最终验收。结果是变更范围可审查，同时保留后续接入点；当前不能声称数据库或全链路观测已经完成。

**追问 1：后续落库时你会怎样设计，避免存入危险原文？**

**口述答案（STAR/证据化）：** 我的原则是数据库只接受投影成功的结构，而不是保存原始对象后查询时再脱敏。后续任务会在写入仓储前要求 `TraceSafeResult.ok`，存 schemaVersion、audience、分类维度和白名单属性；拒绝事件只记录稳定 violation 计数，不保存原 key/value。对于幂等、关联 Run 和生命周期还需单独领域设计，并制定旧版本读取策略。这样结果是持久化层不会成为原始秘密仓库。需要强调的是，这一段是基于当前契约的后续设计方向，提交 `20db9d1` 没有相应数据表或 migration，所以不能作为已完成事实写进项目成果。

**追问 2：最终全量验收你会覆盖哪些内容？**

**口述答案（STAR/证据化）：** 所有阶段完成后，我会把局部证据升级为系统证据。任务包括运行全仓测试和正式构建，覆盖模型测试、Agent socket、工具失败、Vendor 生成超时、下载失败、评测导出和 UI 错误展示的端到端场景；同时扫描日志、响应、持久化和构建产物是否出现夹具中的秘密样本，并验证 unknown-effect 场景不会盲目重放。还应记录精确命令、用例数、提交哈希和失败修复。当前用户明确要求每阶段只做单元测试，因此这些工作尚未执行；我会把它们列为待验收，而不会提前宣称全量绿色。

## 五、面试陈述红线

- 可以说“建立统一、版本化、fail-closed 的诊断投影契约，并完成关键入口适配和阶段单测”。
- 不可以说“已经完成全链路 Trace 平台”“四类消费者都已持久化”“已经上线”“性能提升了某个比例”或“全仓测试全部通过”。
- 可以说“为安全重试提供 certainty 与 retryDisposition 语义，并对图片 Vendor 场景完成映射”。
- 不可以说“已经彻底消除重复生成”；真正的 Vendor 对账、幂等和端到端恢复仍需后续阶段。
- 可以引用提交 `20db9d1`、ADR、源码路径、负向夹具和聚焦测试作为证据；全量测试与最终验收证据必须等所有阶段完成后再补。
