# Agent Harness T17 面经：生产 Run 与计费提案（阶段版）

> 仅对应本分支已实现的局部链路。旧生产 Socket 的批量图片、视频、多分镜与新建轨道路径尚未完整迁移；新受控 Video 虽有候选/审批和默认关闭的执行入口，仍未通过真实 Provider 与浏览器验收。单条空轨道分镜已具备受控提案与审批。全量验收留到 T21，不给未经测量的效果数字，也不代写简历。

本文件按增量实施顺序保留 `8a`–`8ag` 的追问编号。建议先准备 15 个核心主问：`1`–`10` 加 `8a`（派生资产审批）、`8g`（单条分镜边界）、`8q`（Video 批准非派发）、`8v`（请求不重放）、`8ab`（默认关闭的执行入口）；其余为对应模块的深追问。早期问题中的“先做候选契约”应结合后续条目阅读，不能把当时尚未实现的状态当作当前结论。

## 一面：先把边界讲准

1. 问：T17 到底做完了什么？答：建立独立生产 Harness Run，冻结已发布 Skill，可通过受控 Tool 读取拍摄计划/分镜表文本，并在独立 grant 下分别提出单资产图片、派生资产和单条分镜候选。候选会创建待 Owner 审批子 Run；仅经独立批准的本地资产或分镜写入才算效果已提交，图片还需后续 Vendor 路径。追问“证据在哪”：看 `src/agentRuntime/index.ts`、`src/agents/productionAgent/harnessPreparation.ts`、`tests/productionHarnessRun.test.ts`。
2. 问：为何不让模型直接调用旧的图片生成 Tool？答：旧 Socket 流程没有完整的受控租约、审批、请求账本和恢复证据。模型建议只是意图，不能代替 Owner 授权成本。这里让模型停在 proposal，后续沿用 T09 审批与 Vendor ledger。追问“代价”：多一次 Owner 处理，而且目前只覆盖单资产，旧路径仍需迁移。
3. 问：为什么生产工作区读 Tool 只开放两个文本字段？答：剧本 `scriptPlan` 和 `storyboardTable` 是当前指导 Run 需要的有界只读信息；资产数组和生成状态包含不同的隐私、写入和外部成本语义，不应塞进一个宽 Tool。适配器按 Project/剧本键核对并拒绝重复行、不合规文本。证据：`src/agents/productionAgent/harnessWorkspaceRead.ts` 与对应单测。

## 二面：权限、事务与失败追问

4. 问：Skill manifest 请求了图片 Tool，模型就能提案吗？答：不能。还需当前 Owner 显式授予 `propose:billable-image`；运行时检查生产 role/scope、冻结 Skill 请求和 Project grant 的交集。grant 与 `read:production-workspace` 独立，撤销后新操作被拒绝。证据：`src/skillRuntime/grants.ts`、`tests/productionHarnessGrants.test.ts`。
5. 问：父 Run 在模型请求时失去租约，会怎样？答：创建子审批的同一数据库事务会用 Run ID、owner/epoch、fence、过期时间检查租约；失效时不落子审批。假模型单测伪造 fence 验证拒绝。不能据此宣称已完成真实多进程故障验收。
6. 问：模型重试同一个 Tool 调用会重复计费吗？答：提案本身不计费。同一父 Run 和 operation ID 派生确定性请求键，子 Run 的指纹约束目标；不同目标是冲突，不会悄悄复用。真正提交由 T09 Owner 审批与 Vendor ledger 控制。假 Provider 超时被记为未知，重复执行不会再次调用，取消后的迟到图片保留证据但不链接 Asset；真实 Provider 的迟到和对账仍待 T21。
7. 问：如何证明一条审批来自被授权的父 Run？答：子 Run 冻结父 Run ID、操作 ID、Skill ID 和 Tool 合约哈希；父 Run 有同操作的权限判定。inspect 时复核父 scope、判定哈希、allow 结果和审批操作一致性；数据库不允许改写审批绑定。前端需要的效果状态另由 Owner-only 的只读投影从父判定定位子 Run，不取模型自述。证据：`src/controlledTools/billableImageApproval.ts`、`src/agents/productionAgent/harnessEffects.ts`、`docs/adr/0023-production-agent-image-proposal-boundary.md`。
8. 问：父 Run 已成功，Owner 后续处理子审批，会把父 Run 状态改写吗？答：不会。父 Run 的成功只表示模型指导步骤完成，子 Run 是独立的计费效果决策。定向测试验证非 Owner 不能批准；Owner 批准后，假 Provider 只调用一次，图片证据和 Asset 关联在子 Run 提交，父 Run 仍成功。拒绝路径由 T09 审批单测覆盖；面试时必须分别描述两个状态。
8a. 问：派生资产只是本地写表，为何还要审批？答：本地写入虽然没有 Vendor 成本，却会改变 Project 的资产关系和视觉派生指令，错误内容可能被后续生成消费。模型只持有 `propose:derived-asset`，没有 `write:derived-asset`；T08 审批时再次检查精确 payload、目标版本、等价状态和目标状态哈希。定向测试在模型提案后确认资产表没有新增，Owner 批准后只新增一条，撤销 grant 后新提案被拒绝。证据：`src/controlledTools/derivedAssetWrite.ts`、`tests/productionHarnessRun.test.ts`、`docs/adr/0024-production-agent-derived-asset-proposal-boundary.md`。
8b. 问：派生资产提案怎么避免冒用父 Run？答：子 Run 创建和父 Run 权限判定在同一事务内进行；校验父 Run 的运行状态、Owner 身份与有效 lease，冻结 Skill 必须请求该 Tool 与独立能力，Project grant 必须当前有效。子 Run 保存父 Run、操作、Skill 和提案合约哈希；inspect 再复核权限判定哈希与 operation ID。相同操作派生确定性请求键，变更 payload 冲突。这证明本地持久绑定，不代表已经通过跨进程或恶意数据库篡改验收。
8c. 问：Owner 如何确认自己批准的不是被前端摘要掩盖的内容？答：T08 快照原本只有预览和载荷哈希，模型提案接入后不足以逐字段核对。现在 Owner-only inspect 在 schema、payload 哈希、预览、Tool 合约与 Receipt 绑定全部有效时才返回精确 payload；损坏证据不给 payload。试用面板展示完整 JSON，并在缺 payload 时禁用批准；服务端依然以冻结 payload 和目标状态作为提交依据，前端展示不是授权的唯一屏障。证据：`src/controlledTools/derivedAssetWrite.ts`、`tests/derivedAssetWrite.test.ts`、Web PR #8。浏览器交互尚未验收。
8d. 问：Project Owner 怎么知道当前给模型开放了哪些能力？答：后端认证 Owner-only 的生产 grant 快照分别返回工作区读、图片、派生资产和单条分镜提案的 active/version；试用面板用当前版本提交明确的开启或撤销命令，遇到版本冲突只提示刷新，不自动覆盖别人的更新。开启提案能力仍不等于批准效果，模型还要绑定已发布 Skill，并在调用时通过当前 grant 与租约校验。证据：`src/skillRuntime/grants.ts`、`tests/productionHarnessGrants.test.ts`、Web 合约单测；尚无浏览器验收。
8e. 问：旧生产路径与 Harness 并行时，是否还存在“假成功”？答：存在，不能笼统说已迁移。审计发现旧 `add_flowData_storyboard` 将 Socket 写入排队后立即返回 `true`，即使之后回调报错。兼容层现等待回调，错误返回“结果不确定、人工核对、不自动重试”；定向测试覆盖确认和报错。但未解决断线无回调、进程崩溃、幂等与分镜写入持久回执，因此它只是避免一个明确的假成功，完整迁移仍在 T17 待办。证据：`src/agents/productionAgent/tools.ts`、`tests/productionLegacyStoryboardBoundary.test.ts`。
8f. 问：为什么收到前端回执仍不能宣称“分镜链路已可靠”？答：跨仓库核对发现前端原本先把分镜加入本地数组，再向后端写入；后端失败时本地界面可能显示未持久化的数据，且失败回执的字段与 App 检查的字段不一致。兼容修正让 Web 写入后重读服务端数据才确认，失败时只重读、不重发；App 将 `{success:false}` 视为不确定结果。单测覆盖回执与重读顺序，但旧后端批量写路由仍可能部分提交，断连也没有持久 ToolReceipt，所以必须继续迁移到受控分镜写入，不能把这次修正包装为端到端恰好一次。
8g. 问：为什么新分镜写入候选只允许已有空 Video Track 上的一条 Storyboard？答：旧批量路径把分镜插入、资产关联、分组和 Video Track 创建混在同一个前端驱动流程，任何后段失败都可能留下部分状态。先收敛为“空 Track、同一时长、一条分镜”，后端可独立验证 Project/Script/Asset 归属，并冻结精确 payload 与 Track 目标状态哈希。Owner 批准事务同时写入分镜与关联、回执、Checkpoint 和 Trace；关联失败全部回滚，目标变化转冲突，重复决策不再次写入。相关定向 SQLite 用例证明本地事务边界，但多分镜编排、轨道创建和浏览器验收尚未完成，不能据此声称分镜黄金链路完成迁移。证据：`src/controlledTools/storyboardWriteApproval.ts`、`tests/storyboardWriteApproval.test.ts`、ADR-0025。
8h. 问：模型为什么不能直接调用分镜审批接口？答：模型生成的内容只是候选，不代表 Project Owner 接受了对生产计划的更改。受控 Tool 只有提出候选的能力；后端在同一事务检查父 Run 的有效租约、冻结 Skill 申请、当前 Owner grant 与权限判定，才创建待审子 Run。独立的认证 Owner HTTP 命令按版本批准，提交前再次核对目标状态。假模型测试证明提案后分镜表仍为空、撤销授权后新提案拒绝、伪造围栏被拒；这证明本地权限与事务链路，不是浏览器或跨进程故障验收。证据：`src/skillRuntime/grants.ts`、`src/controlledTools/storyboardWriteApproval.ts`、`tests/productionHarnessRun.test.ts`。
8i. 问：旧 Socket 前端一直不回调怎么办？答：兼容路径设定有限等待时间，超时只表示无法确认写入结果，返回“需人工核对、不要自动重试”，不会把排队或断连解释为成功或明确失败。即使收到回调，也必须是显式 `{success:true}` 才算确认；旧格式或无结构回执同样转为结果不确定。迟到回调不能触发再次提交。定向测试用短计时器验证无回调能退出且只发送一次；生产默认等待 20 秒。该措施避免调用无限悬挂，却不解决旧后端部分提交、崩溃恢复或跨进程对账，最终仍要用持久审批与回执替换旧路径。证据：`src/agents/productionAgent/tools.ts`、`tests/productionLegacyStoryboardBoundary.test.ts`。
8j. 问：为什么不直接把现有视频生成函数暴露给模型？答：它虽然有统一的 Video Capability、Prompt Revision 和 Generation Task，但当前手动路由会立即发起异步供应商调用，超时或断线后的“失败”不能证明供应商未接单或未计费，也缺少 Agent Run 的批准、提交意图和未知结果防重放证据。模型可伪造来源字段的风险也先在 HTTP 入口收紧：浏览器只能提交用户来源，不能自称 Project Agent。路由定向测试证明伪造来源未触达编排，正常用户路径仍可进入；这不是视频生成已迁移的证据。后续需先形成可恢复的授权与 Vendor 请求账本，再接模型 Tool。证据：`src/video/production.ts`、`tests/videoWorkbenchOriginBoundary.test.ts`、`docs/agents/video-generation.md`。
8k. 问：为什么受控 Video 候选先只支持 text-to-video？答：单轨道文本生视频只需冻结现有 Track 选型和 active Prompt Revision，不涉及浏览器上传路径、图片读取或多关键帧跨 Project 归属。候选预检确认 Project/Script/Track 归属、选型一致、没有已有 Video，并把 Prompt Revision 的 brief、draft 和渲染文本哈希纳入目标状态；人工修改后旧候选冲突。三个 SQLite 定向测试覆盖越界与漂移。这一步只是无副作用预检；后续虽已增加审批、请求意图和默认关闭的执行入口，真实 Provider 与浏览器仍未验收，不能说“视频生成 Agent 化已完成”。证据：`src/controlledTools/videoGenerationProposalContract.ts`、`tests/videoGenerationProposalContract.test.ts`、ADR-0026。
8l. 问：既然受控候选尚未接图片输入，为什么还要修旧 Video 的图片解析？答：旧手动单条/批量路由仍可真实调用 Vendor；原代码只用 Storyboard 或 Asset ID 取图片，上传路径也直接读，遗漏当前 Project/Script 边界。现在编排解析引用时，Storyboard 必须属于当前 Project/Script，Asset 必须属于当前 Project 且直接属于或显式关联当前 Script，上传路径必须在本 Project/Script 的视频输入命名空间。定向 SQLite 测试验证跨 Project、跨 Script、路径穿越均在读取图片前拒绝，同时原文生视频假供应商编排回归通过。该修正只封住图片引用边界，不代表手动路由具备完整 Owner 授权或 Agent 恰好一次计费能力。证据：`src/video/inputResolution.ts`、`tests/videoInputScope.test.ts`、`src/video/production.ts`。
8m. 问：工作台已有 JWT，为什么还要单独核对 Owner？答：JWT 只能证明是谁发起请求，不证明此人可以操作请求体里指定的 Project。五个生成或更新 Prompt/Video 的路由和 Video 输入上传路由现在使用 token 中的 actor ID 核对目标 Project Owner；批量 Prompt 对全部目标 Project 先完成核对，避免同一批次前几项已写、后几项才发现越权。定向测试让用户 1 请求用户 2 的 Project，六个入口都在调用底层编排或写入前返回 403，缺失 actor 也被拒。这是手动兼容入口的权限补丁；其他工作台路由仍需独立审计，Agent 提案还要冻结 Skill/grant、Owner 审批与可恢复 Vendor 账本。证据：`src/video/workbenchOwner.ts`、`tests/videoWorkbenchOriginBoundary.test.ts`。
8n. 问：把视频命令准备从手动生成流程抽出来，是否就能让 Agent 安全生成视频？答：不能。原流程的前半段已有 Model、Capability、Prompt Profile 和图片输入校验，后半段却会创建记录并调用供应商；校验正确不等于费用已获授权或结果可恢复。共享准备接口给受控候选提供目标状态与脱敏命令哈希，定向测试确认准备本身不创建任务、不请求供应商，并在 Prompt 异步变化时拒绝。后续审批、请求账本、媒体观察和默认关闭的执行入口已分别实现，但它们是额外边界，不由“准备函数复用”自动保证；真实 Provider 仍待验收。证据：`src/video/production.ts`、`src/controlledTools/videoGenerationPreparation.ts`、`tests/videoOrchestrationIntegration.test.ts`、ADR-0026。
8o. 问：Vendor Capability 有可用 Model，为什么不能据此给 Owner 展示一个估价并直接批准？答：能力契约只说明选型与约束，不等于供应商对当前 Project 的计费报价。当前仅由 Project Owner 配置版本化本地费用上限估算，服务端按 Vendor、Model、能力、输出时长/分辨率/画幅、音频选型精确匹配，缺配置或状态损坏就拒绝。SQLite 定向测试证明跨 Owner 不可设置、旧 revision 冲突、不同选型不能借用估算；认证 HTTP 入口用 token actor 而非浏览器声明的身份，Project 删除时清理策略。Web 工作台已有当前无图文生视频选型的读取/按版本设置控件，但未做浏览器验收。估算仍不是实际账单、审批或 Vendor 请求；审批冻结 quote revision 和精确选型，并在提交前重检。证据：`src/controlledTools/videoQuotePolicy.ts`、`src/routes/agentRuns/videoQuote.ts`、`tests/videoQuotePolicy.test.ts`、`tests/videoQuoteRoutes.test.ts`、Web `tests/videoQuotePolicyClient.test.ts`、ADR-0026。
8p. 问：既然本地费用估算可改，视频候选如何防止 Owner 批准到过时的价格或命令？答：候选范围把 payload、Track/Prompt 目标状态、共享准备形成的命令哈希，以及 Project/完整选型/quote revision/金额一同冻结。Owner 决策前重跑准备和报价，版本或内容漂移均冲突；独立审批 Run 后续已接入这套范围，批准仍不自动派发。定向测试覆盖报价版本、命令、目标漂移和跨时长借用；真实 Provider 费用与浏览器批准体验尚未验收。证据：`src/controlledTools/videoApprovalScope.ts`、`src/controlledTools/videoGenerationApproval.ts`、`tests/videoApprovalScope.test.ts`、ADR-0026。
8q. 问：Owner 批准了受控 Video，是否意味着 Agent 已经生成视频或已经产生费用？答：不意味着。子 Run 持久化审批、Receipt、Checkpoint 和 Trace；批准前重验命令、Track/Prompt 与本地报价，批准后仍是 waiting/pending，单靠批准不产生 Vendor 请求或 Project Video。后续虽增加独立 Owner HTTP 执行路由及内部 Vendor 组合，该路由默认关闭，须操作员显式启用并由 Owner 另行执行；模型仍只能提出候选，不能把批准等同派发。定向 SQLite/假 Vendor 测试证明本地边界，真实费用、CDN 与浏览器操作尚未验收。证据：`src/controlledTools/videoGenerationApproval.ts`、`src/routes/agentRuns/videoGenerationExecution.ts`、`tests/videoGenerationApproval.test.ts`、`tests/videoGenerationExecutionRoutes.test.ts`、ADR-0026。
8r. 问：若进程在 Video 请求意图落库后、收到供应商回复前退出，重启能否自动重试？答：不能。新内部账本把审批、ToolCall、requestId、scope/command hash 与 Checkpoint 在事务内绑定；重复 reserve 只拿到同一个 requestId 且 `newIntent:false`。启动发现仍是 `dispatch_recorded` 时转 `unknown`，Run 标记需要对账，不得再生成第二个提交意图。SQLite 测试覆盖单次意图、身份字段不可改、重启恢复函数与不重放；它没有真正调用 Provider，因而尚不能证明供应商是否接单。内部 Provider task ID 观察已能落证据，但迟到视频 Artifact 与人工对账闭环仍缺。证据：`src/controlledTools/videoRequestLedger.ts`、`tests/videoRequestLedger.test.ts`、ADR-0026。
8s. 问：供应商任务 ID 后来才到，能否把 unknown 直接改成成功？答：不能。已核实的 task ID 只挂回原 requestId，写一次 `provider-task-observed` Checkpoint 和 Trace，第二个不同 ID 会冲突，数据库也不允许改写已有观察。unknown 因而拥有可追踪任务身份，但这一步仍没有视频字节或项目采纳，也不能推断真实费用。后续本地媒体观察与 Artifact 提交已另有独立事务和假 Provider 测试；真实供应商迟到回调、费用与跨进程组合尚未验收。证据：`src/controlledTools/videoRequestLedger.ts`、`src/controlledTools/videoArtifact.ts`、`tests/videoRequestLedger.test.ts`。
8t. 问：拿到视频字节后为何不立即把 `o_video` 标记成功？答：字节到达、文件写盘和 Project 采纳跨越不同失败边界。观察器先把请求关联、内容哈希和确定性路径落成 `write_pending`，文件写完后读回核验，再标为 `observed`；若中途崩溃，Owner 可只检查既有本地路径，不再调用 Provider。取消后的字节标 `late`，不写 `o_video`。Trace 明确关联 Run→ToolCall→Video request→Artifact。定向测试覆盖写盘失败/恢复、Owner 隔离和迟到不采纳；项目采纳已有独立内部事务，但仍缺真实 Provider 组合和验收。证据：`src/controlledTools/videoArtifact.ts`、`tests/videoArtifact.test.ts`、ADR-0026。
8u. 问：媒体已观察后，如何避免一半写了 Video、一半没写 GenerationTask 或 Run 回执？答：本地提交 Runtime 在一个 SQLite 事务内重验 Owner、审批绑定、Track/Prompt 状态、Artifact 非迟到和 Run version，再写 ProductionAction、GenerationTask、Video、ArtifactRevision、Receipt/Output、Checkpoint、Run 和 Trace。定向测试模拟 Revision 插入失败，证明项目 Video/Task/Action 都回滚而媒体观察仍在；重复提交只返回同一输出。后续假 Provider 编排已组合该本地提交，但真实 Vendor、CDN、跨进程与费用仍未验收，GenerationTask 也只存脱敏命令哈希。证据：`src/controlledTools/videoArtifactCommit.ts`、`tests/videoArtifactCommit.test.ts`、ADR-0026。
8v. 问：编排层怎样保证模型重试不会再次调用视频供应商？答：编排先从服务端读取批准范围并重备命令，哈希一致后才向账本申请请求意图；只有当次事务刚创建的 `newIntent:true` 才调用注入的供应商 port。旧意图、包括 unknown，返回同一 requestId 且不再调用。fake-port 测试核对调用顺序、重复不调用、命令漂移在落账前拒绝、超时转 unknown 和项目采纳失败留观察证据。该编排尚未绑定生产 Vendor 或 HTTP execute，测试不能证明真实供应商恰好一次，也不支持任意远程视频 URL 的安全下载。证据：`src/controlledTools/videoGenerationExecution.ts`、`tests/videoGenerationExecution.test.ts`、ADR-0026。
8w. 问：用户点“取消视频生成”后，为什么不能说供应商已停止且不会扣费？答：取消先是本地意图，原请求可能已经跨过网络边界。Video 账本记录 `cancellationRequestedAt`，阻止将之后的媒体采纳进 Project；本地 `stopWithoutReplay` 关闭 Run/Receipt，但不删除请求、task ID、Artifact 或 Trace，也不创建第二次意图。迟到 task ID 只挂回原请求，迟到字节标 `late`；已观察但未采纳的媒体若随后取消，也原子转为 late。定向 SQLite 用例覆盖这些状态，但没有真实 Provider cancel 确认或费用对账，故不能承诺退款、免计费或远端停止。证据：`src/controlledTools/videoRequestLedger.ts`、`src/controlledTools/videoArtifact.ts`、`tests/videoRequestLedger.test.ts`、`tests/videoArtifact.test.ts`、ADR-0026。
8x. 问：审批记录已批准后，为什么 Owner 刷新页面可能看不到后续请求状态？答：原本的审批快照是“仅本地审批”读模型，假设 approved Run 永远 waiting、Receipt 永远 pending；一旦请求成功或本地停止，这个假设会把真实证据误判为损坏。现在按 ToolCall→Video 请求→可选 Artifact 重建快照，并核对 scope/Receipt/Run 终态，Owner 可看到请求状态、task ID 与媒体状态。已有请求的审批过了审阅 TTL 也不会被恢复任务过期成新派发机会。定向 SQLite 测试覆盖请求落账、unknown 后停止、成功采纳与 TTL 后 inspect；Web 执行界面和真实 Provider 对账仍待完成。证据：`src/controlledTools/videoGenerationApproval.ts`、`tests/videoGenerationApproval.test.ts`、ADR-0026。
8y. 问：已有 Video 请求账本，为什么重启仍可能把正常 Run 判为证据损坏？答：通用恢复器最初把 `vendor-request-intent` 和 `provider-task-observed` 一律关联图片请求表；Video 使用同一 Checkpoint 类型却有独立请求表，故校验会错误失败。现在按 Video 审批 scope 选择账本，提交 Checkpoint 还核对已采纳视频媒体、Project Video、GenerationTask 和 ArtifactRevision。定向单测在 waiting 意图和 succeeded Video Run 上调用恢复函数，并跑相邻图片恢复用例；这验证数据库层的证据链，不是杀进程、跨进程租约或真实供应商恢复。证据：`src/database/agentRunRecovery.ts`、`tests/videoRequestLedger.test.ts`、`tests/videoGenerationApproval.test.ts`、ADR-0026。
8z. 问：供应商给一个 MP4 下载 URL，为什么不能直接用旧工作台的 `axios.get`？答：视频结果 URL 是外部输入，任意下载可能访问内网/元数据地址，自动跳转或 DNS 变化也会绕过初始校验。受控解析器只接受显式 host allowlist 的 HTTPS 地址，拒绝 IP 字面量、私有或混合 DNS、认证信息、非标准端口与跳转，并把公开 IPv4 地址固定到 TLS 请求；还限制大小、时间和 MP4 头。没有配置 host 时宁可拒绝 URL，不把能力元数据当信任来源。3 个 fake-network 单测只证明本地校验与调用顺序，真实供应商 CDN/证书兼容和生产组合仍待验收。证据：`src/controlledTools/videoMediaResolution.ts`、`tests/videoMediaResolution.test.ts`、ADR-0026。
8aa. 问：首次视频已经成功，为什么重复点击执行一度会报“目标版本改变”？答：成功后 Track 已有 Video 是预期变化。原编排在检查是否已有请求之前，先重备原命令和重验“无 Video”目标，导致重复调用无法返回原请求，虽然也不会再次调用供应商。修正后先认证 Owner 并核对批准 Run、ToolCall、scope 和请求身份；若已有意图，直接返回原 requestId/status，只有确实要创建新意图才重验目标/命令/报价。竞态中的准备失败也再查一次既有请求；数据库事务依旧是唯一意图创建点。假 Provider/SQLite 集成测试证明首次成功后重复不再调用，timeout 或不可信 URL 也不重发。此处是本地防重放，不是供应商计费恰好一次。证据：`src/controlledTools/videoGenerationExecution.ts`、`src/controlledTools/videoRequestLedger.ts`、`tests/videoGenerationExecutionComposition.test.ts`、ADR-0026。
8ab. 问：代码已有真实 Vendor 组合，为何不能说受控 Video 已上线？答：内部组合与模型提案不等于默认开放。单独的 Owner HTTP 执行路由要求操作员显式开启 `TOONFLOW_CONTROLLED_VIDEO_EXECUTION=enabled`，默认 404；审批路由本身仍没有 execute，模型 Tool 只能创建待审候选，Web 也没有视频审批/执行按钮。底层按认证 Owner、精确审批、Run version 和意图账本执行，返回结果明确区分 unknown 与 succeeded。路由定向测试只证明开关、actor 来源和冲突处理，假 Vendor/SQLite 测试证明本地顺序；真实 Provider 费用、CDN、网络超时、跨进程恢复和浏览器操作仍待 T21 验收，现阶段不应在运营环境随意启用。证据：`src/routes/agentRuns/videoGenerationExecution.ts`、`tests/videoGenerationExecutionRoutes.test.ts`、`tests/videoGenerationExecutionComposition.test.ts`、ADR-0026。
8ac. 问：模型已有生产 Agent 身份，为什么还需要单独开启 Video 提案 grant？答：角色说明它能参与生产指导，不等于 Owner 允许它提出计费视频候选，更不等于可直接执行 `generate:track-video`。`propose:track-video` 与工作区读取、图片和分镜提案各自独立，Project Owner 按版本显式开启/撤销；模型 Tool 还要求已发布 Skill 请求该 Tool 和能力、父 Run 有有效租约。定向测试验证默认拒绝、非 Owner、版本冲突、撤销和其他 grant 不串权，假模型测试验证撤销后新提案拒绝。它只扩大候选提交能力，没有扩大供应商调用权。证据：`src/skillRuntime/grants.ts`、`src/controlledTools/videoGenerationApproval.ts`、`tests/productionHarnessGrants.test.ts`、`tests/videoProductionProposal.test.ts`。
8ad. 问：怎样证明 Video 子审批来自真实授权模型调用，而不是 UI 或模型文本捏造？答：提案事务核对父 Run、有效租约、Owner、冻结 Skill 请求和当前 Project grant，再把有哈希的权限判定与确定性子审批一起落库。子 Run 输入记录父 Run、操作 ID、Skill 和提案合约；Owner inspect 复核对应的权限判定及其哈希，父 Run `/effects` 只能沿这些证据找到子审批。同操作重复得到同一审批，变更候选冲突；待审与批准都没有 VendorRequest。一个假模型/SQLite 用例验证本地链路与撤销拒绝，但还没有跨进程篡改或浏览器验收。证据：`src/controlledTools/videoGenerationApproval.ts`、`src/agents/productionAgent/harnessEffects.ts`、`tests/videoProductionProposal.test.ts`。
8ad-1. 问：非法或已结束的父 Run 发起视频提案，会不会先查询供应商能力？答：基础 Owner、父 Run 运行状态和租约检查已前移到候选准备之前；写审批时再校验一次，防止预检与落库之间状态变化。假模型/SQLite 单测在父 Run 结束后尝试提案，确认准备函数未调用。这不证明所有 Vendor 查询零成本，也不代替真实网络验收。证据：`src/controlledTools/videoGenerationApproval.ts`、`tests/videoProductionProposal.test.ts`。
8ae. 问：Web 点了取消或停止，为什么不能把 Video 标成“供应商已取消”？答：Web 只向原 requestId 发送 Owner 命令，服务端按当前 Run version 记录本地取消意图或停止追踪；原请求可能已到供应商，账单和迟到回执仍需对账。`write_pending` 的恢复只检查原本地媒体路径，已观察媒体采纳还要重验审批、Track/Prompt 和媒体证据。Web 命令失败不自动重试，执行路由默认 404；10 个相关前端合约定向用例不能替代浏览器或真实 Provider 验收。证据：`src/controlledTools/videoRequestLedger.ts`、Web `src/utils/productionHarnessContract.ts`、`tests/productionHarnessContract.test.ts`、ADR-0026。

## 三面：反例、取舍与未完成项

8af. 问：Project ID 和 Asset ID 都归属正确，旧批量图片接口为什么还要查 Owner？答：归属校验只证明资源之间的关系，不证明调用者有权花费 Project 的图片生成额度。该入口会先预置 `o_image` 并异步调用 Vendor，因此必须在任何本地占位或外部提交前从认证请求取得 actor 并核对 Project Owner。现在越权定向测试看到 403、零占位、零 Vendor 请求；它没有给旧异步生成增加可恢复账本，也不覆盖其他图片路由。证据：`src/routes/production/assets/batchGenerateAssetsImage.ts`、`tests/assetImageGeneration.test.ts`。
8ag. 问：这项 Owner 检查是否只保护 Production Agent 专用批量接口？答：不是；旧单张图片和工作台批量图片路由也在调用共享生成领域模块前核对认证 Owner。测试覆盖拒绝时不初始化生成依赖，以及授权测试桩下原单张、批量、队列路径保持原行为。但这些旧路径仍是异步/直接 Vendor 调用，没有受控 ToolApproval、未知结果对账或端到端验收，也不能据此推断资产工作台其他写路由安全。证据：`src/routes/assetsGenerate/generateAssets.ts`、`src/routes/assetsGenerate/batchGenerateImageAssets.ts`、`tests/assetImageGeneration.test.ts`。

9. 问：为什么暂不把生产 Agent 宣称为“可恢复生成工作流”？答：持久 Run 已承载指导、单资产图片、派生资产、单条空轨道分镜和受控 Video 候选；Video 也有独立审批、请求意图、媒体观察及默认关闭的 Owner 执行入口。但旧 Socket 的批量图片、多分镜与轨道创建仍并行，Video 的真实 Provider、跨进程恢复和 Web 执行界面未验收。局部账本与假 Vendor 结果不能证明整条生产链无重放、可恢复或费用准确；父 Run 的成功更不能当成子效果成功。
10. 问：若要继续推进，优先顺序是什么？答：先逐项收敛旧 Socket 的批量图片、分镜和轨道创建，把每个效果接到 typed Step、Owner 授权、目标状态和持久回执；对受控 Video 再完成真实 Provider/CDN、未知结果对账、跨进程重启与 Web 审批/执行入口验收。之后冻结 App/Web/Model/Vendor 修订，在 T21 做功能、兼容、恢复、安全、评测、构建与浏览器全量验证。不能把“模型回答成功”替代效果完成，也不能因内部执行路由存在就默认开启运营开关。
11. 问：升级供应商模型目录时，如何避免把服务商格式泄漏到生产编排？答：【S】项目原有 Agnes 适配器支持旧文本、图片和 Video V2.0，但用户当前选择的是更新的三个 Flash 模型；其中 Video 2.5 的任务字段与 V2.0 的帧数格式不同。【T】我需要让上层继续用统一 Video Capability 和冻结命令，同时准确声明新模型能接受的时长、分辨率与输入角色。【A】我只在 Agnes Vendor 适配器中增加目录和请求翻译：文本仍走兼容 Chat Completions，图片沿用 2.1 的尺寸与参考图字段，视频将 `720p`、时长和图片字节变成供应商要求的 `720P`、字符串秒数、keyframe 模式与 Data URI；旧 V2.0 仍走原帧数路径。单测经配置运行时验证模型目录和请求体。【R】本机短文本与 Image 2.5 Flash 的文生图、单/双/六参考图请求得到可核对的非空 PNG，七张被服务商明确拒绝；用户另称 Base64 视频图片输入已实测可用，但本轮多次视频提交因队列满未创建任务。首次图片 CLI 的 0 字节文件已排除。上述均未经过 Toonflow 生产持久化链路，不能称三模型业务验收完成。证据：`data/vendor/agnes.ts`、`src/lib/vendor.json`、`tests/agnesVendorAdapter.test.ts`、Issue #32/#102。
12. 问：既然 Provider 最多接受六张参考图，为什么不能直接截取前六张继续生成？答：静默截断会让调用者以为七张都参与了生成，返回的图片却只依据前六张，排查提示词和素材效果时无法发现输入已变。上层目录仍声明六张限制；适配器作为最后一道提交接缝，对超过已验证上限的请求在网络调用前明确拒绝，不创建供应商请求。定向单测同时验证六张正常传递、七张零 POST。它只防止本地静默丢失，不证明模型生成质量或整个资产链路验收完成。证据：`data/vendor/agnes.ts`、`tests/agnesVendorAdapter.test.ts`、Issue #32。
13. 问：真实模型探针成功后，为什么仍不能说生产 Agent 生成链已经验收？答（本人复现后可口播）：【情境】我需要区分供应商接口可用、应用适配器可用和项目生产效果真正落账这三个层次，避免把一次返回图片的网络请求当成完整交付。【任务】在不泄露密钥、不改用户 Project 的前提下，先验证当前文本和图片模型能否穿过配置化 Vendor 的加载与请求路径。【行动】我把配置放入内存数据库，密钥仅从进程环境读取，文本经应用的配置化 Vendor 和 AI SDK 发出；图片用单张 Base64 参考图走同一配置路径，并只核对阶段回调、PNG 文件头、大小和哈希。视频则先核对首帧请求形态，再做一次最小真实提交。【结果】文本返回预期标记，图片得到非空 PNG；视频提交明确被队列满拒绝，连任务 ID 都没有。图片输出字节没有归档为可复算 Artifact，也未经过 Owner 审批、持久请求账本、项目资产关联或工作台读回，因此我只称其为配置化适配器探针，不称质量收益、视频完成或端到端生产验收。证据：`src/vendor/index.ts`、`src/vendor/loader.ts`、`data/vendor/agnes.ts`、T17 阶段报告；本人面试前应复现并能解释每一层边界。

## 练习与证据缺口

自测时画两条时间线：A）模型提案→Owner 拒绝，B）模型提案→Owner 批准→Vendor 提交结果未知；分别标出 Run 状态和每一步的权限主体。当前可核验的是本轮定向单测、局部假 Provider 成功路径与 TypeScript 检查；尚无浏览器、真实供应商、完整回归或线上指标。每个回答如需提数字，必须先找到对应测试/日志/报告，找不到就说“待测”。
