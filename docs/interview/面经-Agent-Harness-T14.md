# Agent Harness T14 面经：Skill 修订生命周期（阶段版）

> 对应 Issue #70。只覆盖发布、激活、回滚、Run 绑定和少量旧版适配，不提供简历 bullet。T15 才处理依赖闭包与权限交集；T16/T17 才开始接入 Agent，T21 完整验收未执行。第一人称 ownership 由用户按提交记录确认。

## 项目背景

Agent Skill 原本容易被当作“当前 Markdown 文件”。如果作者编辑文件或管理员切换版本，正在运行和后来重试的 Agent 可能看到不同指令，却缺少可核验身份。T14 把稳定定义、可编辑草稿、不可变已发布修订、当前激活指针和 Run 冻结绑定分开，形成版本归因基础。它不是完整 Skill 授权市场。

## 主问与追问

1. 问：为什么不能直接把 Markdown 路径当 Skill 版本？答：路径会指向可变内容，修改文件后同一次 Agent Run 的重试可能读到新指令，无法解释已发生行为。T14 将稳定 Skill 身份与内容修订分离，发布时冻结正文和 manifest 哈希，Run 再单独绑定确切修订。定向测试覆盖激活变化后旧 Run 仍读原版；旧 Socket 仍用遗留文件路径，不能说全局切换完成。追问：哈希能否说明内容安全？答：只能说明一致性，安全性还需发布校验、权限和最终测试。
2. 问：草稿和已发布修订为什么分开？答：作者需要反复修改草稿，但运行时需要一份不会在后台变动的指令。草稿按预期哈希更新，发布时重新验证正文和 manifest，发布后数据库触发器阻止原地改写或删除。这样可以在编辑效率和运行可复现之间建立边界；增加的代价是每次改变都要产生新版，并管理激活指针。追问：编辑草稿能影响已启动 Run 吗？答：不能，已启动 Run 只认冻结的已发布修订。
3. 问：Skill Definition、Revision、Binding 和 Run Binding 各负责什么？答：Definition 是稳定名称；Revision 是一次带正文和声明的内容快照；Binding 选择未来新 Run 默认使用哪版；Run Binding 记录某次执行实际拿到的修订及哈希。若把后三者合成一行，管理员回滚可能改写历史或无法区分作者编辑与部署选择。T14 本地测试展示新旧 Run 的不同解析；跨进程完整运行仍待验收。追问：回滚为何不是删新版？答：保留新版作为历史证据，只移动未来选择指针。
4. 问：发布前验证 manifest 的哪些内容？答：校验 Skill/语义版本身份、适配角色与意图、依赖及资源声明、请求的 Tools/Capabilities、路由元数据、去重、大小和安全文本，再核对草稿内容哈希。这里验证的是“声明格式和来源完整”，不是授予能力。测试覆盖无效草稿和发布后不可修改；真正的依赖解析、资源访问与权限交集主要在 T15，不能归为 T14 已完成。追问：manifest 写了 Tool 就能调用吗？答：不能，必须再过运行时授权闸门。
5. 问：为什么激活要使用 expectedBindingVersion？答：管理员 A、B 可能同时编辑激活指针；若最后写入直接覆盖，A 的决定会无声消失。版本比较要求调用方基于自己看到的指针版本提交，冲突时刷新而非盲写。回滚也是一次新版本的指针变更，不会改历史 Run。定向测试覆盖过时绑定版本冲突；管理 UI 尚未完成，不能声称页面已处理所有并发情形。追问：内容哈希 CAS 与绑定版本 CAS 有何不同？答：前者保护草稿正文，后者保护发布选择。
6. 问：Run 为什么冻结修订 ID 和哈希，而不是只存 Skill ID？答：Skill ID 只能确定“哪种能力”，不能确定某一时刻具体指令。Run 启动时冻结修订及正文/manifest 哈希，后续激活新版本或回滚不改变它；幂等重试读取原绑定而非再看当前指针。这样能解释一次行为对应的指令版本。T14 初版 `bindRun` 只绑定根修订，完整依赖闭包证据是 T15 增量。追问：旧 Run 会自动拿到安全修复吗？答：不会，必要时应终止或明确重新发起。
7. 问：为什么 Project Owner 不能管理全局 Skill？答：Skill Definition 和激活指针是跨 Project 共享的；若单个 Project 的 Owner 能发布或激活，就可能影响其他 Project 后续 Run。管理路由从认证上下文读取 actor 并判断应用管理员，拒绝请求体伪造身份；列表不返回正文，单版检查才读取详细内容。定向路由测试覆盖非管理员拒绝。该边界是服务端管理控制，不代表前端编辑器已集成。追问：项目级授权由谁管理？答：那是独立的 Project grant，不等同全局发布权。
8. 问：旧 `o_skillList` 为何不自动迁移为发布修订？答：旧记录和 Markdown 文件缺少新 manifest 的角色、依赖、资源和权限声明，文件也可能含旧回调或路径依赖。若升级时按文件名猜测发布，可能把未审指令立即交给新 Agent。T14 保留旧数据，并只提供一个显式适配的纯参考文本源，先生成管理员可检查草稿；保存、发布、激活仍分步。测试证明升级不会自动填充新表。追问：如何迁更多旧 Skill？答：逐个建立来源锁定和契约测试。
9. 问：旧版适配为什么要钉住内容 SHA-256？答：允许列表若只约束文件名，源文件修改后同一导入 ID 就可能指向另一套指令。适配器校验规范化正文哈希和 frontmatter，只接受经审查的纯叙事参考文本，并把请求 Tool/Capability 固定为空。内容一变，管理员必须重新审查，不能继续沿旧允许项导入。测试覆盖来源变化和未知来源拒绝；适配结果仍只是草稿提案。追问：这能处理旧执行 Skill 吗？答：不能，含旧 Tool/回调的来源被排除。
10. 问：Skill 的 requestedCapabilities 为什么不能当作权限？答：Skill 是由作者编写的指令制品，它只能提出想使用的能力。真正权限来自平台、Project、Run、角色、Tool 策略与当前审批；若文本声明直接生效，作者就能自授读取或付费效果。T14 manifest 把请求结构化并冻结，T15 才把它与外部 grant 求交。面试里必须把“声明已验证”和“调用已获授权”分开。追问：批准一次效果会永久授权吗？答：不会，审批应绑定精确操作和版本。
11. 问：发布后发现问题应如何回滚？答：管理员可把激活指针按版本 CAS 切回旧的已发布修订，让未来 Run 选择旧版；已启动 Run 的绑定仍指向当时版本，历史不会被静默重写。需要紧急阻断旧 Run 时，应另用撤销或取消机制，而不是假定回滚会改变在途执行。T14 测试覆盖未来 Run 选择；发布策略的 deprecated/revoked 生命周期是后续 T15。追问：为何保留坏版本？答：历史证据和复盘需要知道它确实被发布过。
12. 问：如何发现草稿在“预览”与“发布”之间变化？答：发布命令带预期内容哈希，在事务里重新读取草稿并核对内容、manifest 和当前状态；若作者或另一个管理员已经修改，发布拒绝而不是发出未审内容。定向测试模拟过时哈希冲突。这个机制保护本地并发边界，但不能凭此声称发布内容已经过业务审查或真实模型安全测试。追问：只比正文够吗？答：不够，manifest 也决定角色、资源及能力请求。
13. 问：已发布内容为何不允许普通删除？答：历史 Run 的绑定、检查和事故复盘依赖那份修订存在；若删除，后续看到的哈希可能只剩空引用。数据库触发器保护已发布 Revision 的更新和删除，Project 删除只清与该 Project 相关的 Run 绑定证据，不把全局 Skill 随之删除。测试覆盖不可变和 Project 清理。这是保留策略的一部分，最终长期归档与备份仍需系统验收。追问：草稿能删除吗？答：应按管理流程处理，不能与已发布证据混同。
14. 问：T14 与 T15 的分界是什么？答：T14 建立可编辑、可发布、可激活和可绑定的修订身份，让运行能回答“用了哪一版”；T15 在此基础上解析完整依赖图、资源、权限交集和路由决定。没有 T15，单个 manifest 的依赖/Tool 请求只是声明；没有 T16/T17 接线，旧 Agent 仍可能走旧路径。面试时我会按 Issue 分阶段说明，避免把堆叠分支上的最终状态都算作 T14。追问：为什么要这样拆？答：先固定身份，再讨论执行授权，才能可靠追责。
15. 问：当前能否说 Skill Runtime 已完整可用？答：不能。T14 有持久化、管理员 API 和一个受限旧版导入，但管理 UI、完整旧 Skill 适配、依赖闭包、资源加载、运行时权限、Agent 黄金链路与真实 Provider/浏览器验收分属后续阶段。定向测试和 TypeScript 检查证明局部契约，不是上线或使用效果证据。可讲的准确结论是“不可变修订和 Run 版本归因的基础已实现”。追问：最终如何验收？答：冻结 App/Web 修订，验证发布到运行、回滚、撤销、跨 Project 权限和恢复。
