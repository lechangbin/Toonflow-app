# 面经：Agent Harness T04 持久化只读 Agent Run

> 本文件仅用于面试准备，不包含项目简介或简历 bullet。回答只陈述当前源码与阶段验证能够证明的事实；未执行的全量测试、构建、Web 验收和性能测量均不作完成性表述。

## 一、Agent Harness（8 个主问）

### 1. 为什么要把一次 Agent 调用建模成持久化 Run，而不是一次普通 HTTP 请求？

**第一人口播：** 我面对的核心问题不是如何多调一次模型，而是一次调用跨越 HTTP、异步调度、数据库和外部 Provider 后，系统怎样始终回答“它现在到底处于什么状态”。普通请求或 Socket 只代表传输连接，页面刷新、客户端超时或进程重启都会让连接态失真。因此我把请求身份、执行状态、步骤、输出和安全事件落成持久化记录，HTTP 只负责启动和检查，UI 再从快照投影。结果是相同 Run 在断线后仍能按 ID 和 Project 查询，终态文本来自持久化 Output，而不是前端缓存。当前只完成单个只读 Model Step，没有把它夸大为完整工作流引擎。

**追问 1：Run、Step、Output、Trace 为什么要拆成四类记录？**

**第一人口播：** 我拆分时按照变化原因和查询语义划边界。Run 承担请求身份、总体生命周期、版本与注意力；Step 表示 Run 内可排序的执行单元；Output 只保存可向用户展示的最终结果；Trace 保存有序且经过安全投影的生命周期证据。若全部塞入单表 JSON，更新任一状态都可能重写大对象，也难以用唯一约束证明序号、步骤和输出关系。当前四表是最小可用边界，不是完整事件溯源；例如 Trace 还没有建立跨 Run 的因果关系。我能证明的是职责与事务一致性，而不是宣称它已经支撑任意 DAG 编排。

**追问 2：聊天消息为什么不能直接作为 Run？**

**第一人口播：** 聊天消息面向展示，Run 面向执行事实，两者生命周期不同。一条消息可能因为 UI 折叠、重放或版本替换而变化，但执行仍要保留步骤状态、幂等身份、输出哈希和诊断证据；反过来，Trace 里的内部生命周期也不应全部暴露给用户。因此我用确定性投影把 Run 映射为聊天消息，消息 ID 使用 Run ID，内容块 ID 也稳定派生，并携带版本和显示状态。页面刷新后重新 inspect 就能生成相同视图。当前 Web 消费端接线尚未完成，所以我只主张 App 侧投影契约已形成，不主张端到端界面已验收。

### 2. 你如何设计 Agent Run 的幂等启动？

**第一人口播：** 我先定义业务幂等作用域为 Project、角色、固定范围和客户端请求 ID，并对请求 ID 与正文做 trim 规范化，再计算完整输入指纹。事务写入使用联合唯一键上的 on-conflict ignore，然后重读数据库权威记录：同键同指纹返回原 Run，同键不同指纹报冲突，只有本次新建者才写 Step、Trace 并在提交后调度。这样网络重试和双连接竞态都能收敛到一个执行；瞬时 SQLite busy 仅以相同身份安全重试一次。当前已有单连接与双连接竞态测试，但没有给出生产规模吞吐指标。

**追问 1：只有 clientRequestId 为什么不够？**

**第一人口播：** 只有客户端请求 ID 能定位旧记录，却不能证明新请求与旧请求语义相同。客户端可能错误复用 ID，或者调用方升级后改变了角色、范围与正文；若服务端无条件返回旧 Run，就会把新的用户意图静默绑定到旧结果。我把 schema 版本、Project、角色、范围、请求 ID 和内容一起做确定性指纹，命中键后必须同时命中指纹才算安全重试。这个设计把“幂等重放”和“键冲突”分开表达。指纹不替代授权，也不用于加密内容；它只是请求等价性证据，原始业务输入仍按执行需要单独持久化。

**追问 2：并发两个相同启动都先查不到，是否仍会重复？**

**第一人口播：** 仅靠“先查再插”确实存在竞态，所以最终防线是数据库联合唯一约束。当前使用 on-conflict ignore 竞争写入，再重读权威记录并验证请求指纹，只有权威 ID 等于本次生成 ID 的事务才创建 Step 和 Trace；遇到瞬时 SQLITE_BUSY 会让出事件循环后用同一身份再试一次。文件数据库双连接测试验证相同启动只产生一个可执行 Run。不过这仍不等于完成高并发压测，持续锁竞争、多进程调度和目标部署负载仍需在最终验收测量。

### 3. Agent Run 的状态机是怎样设计的？

**第一人口播：** 我把持久化执行状态定义为 queued、running、waiting、succeeded、failed、cancelled。当前真正落地的主链是 queued 到 running，再到 succeeded 或 failed；启动恢复会把遗留 queued 或 running 停放为 waiting。终态提交会同时更新 Step、Run、Output 和 Trace，inspect 只读这些事实。这里我特别避免把所有用户感知都塞进一个枚举：是否需要人工处理由独立的 attentionReason 表达。转换规则集中在 lifecycle map，SQL 还校验旧状态与版本，未知存储值也会在读取时拒绝。cancelled 虽然在类型中预留，但本阶段没有取消接口和竞争实现，所以面试时我不会把预留状态说成已交付功能。

**追问 1：为什么 needs-attention 不是持久化状态？**

**第一人口播：** needs-attention 回答的是“是否需要人介入”，waiting 回答的是“执行是否暂停”，两者不是同一个维度。例如未来因为限流等待可能不需要人处理，而配置缺失或未知结果等待可能需要人确认。若把组合都做成互斥枚举，状态会膨胀，转换规则也容易矛盾。因此数据库保存 waiting 与 attentionReason 两个事实，UI 发现二者同时存在时才显示 needs-attention。这样后端状态机保持稳定，前端又能突出操作需求。当前测试直接验证了这一投影，但还没有实现 attention 的确认或恢复动作。

**追问 2：怎样保证非法状态转换不会发生？**

**第一人口播：** 我把 Run 与 Step 的允许转换集中在 lifecycle 模块的显式 map 中，先用领域函数拒绝非法边，再在 SQL 更新中带旧状态、Run version 与受影响行数条件。领取只接受 queued/pending，终态只接受 running/running，恢复按 queued 或 running 的真实前态进入 waiting；Run 与 Step 在同一事务同步推进，任一行数异常都会回滚。读取时也解析并拒绝未知状态，避免脏枚举被当成合法快照返回。测试既覆盖允许路径，也注入过期前态验证不会越过并发保护。当前单 Step 的转换已集中，但如果后续支持并行 Step，仍需扩展聚合版本、顺序和多写者 Trace 策略。

### 4. 为什么模型调用不能放在一个数据库事务里？

**第一人口播：** 模型调用是耗时且不可控的外部网络操作，数据库事务只能原子管理本地写入，无法把 Provider 的执行或计费一起回滚。如果让事务跨越整个调用，会长期占锁、放大 SQLite 写竞争，而且进程崩溃后仍无法知道远端是否完成。因此我把链路切为启动意图、领取运行和终态结果三个短事务，模型调用位于领取与终态之间。这个设计不消灭不确定性，而是让不确定性可被识别和恢复。测试通过触发器注入终态写失败，验证 Output、Step、Run 和成功 Trace 不会出现部分提交。

**追问 1：分段提交之间崩溃会发生什么？**

**第一人口播：** 如果启动事务提交前崩溃，所有本地记录回滚，不会只剩 Run 或 Step。提交后但领取前崩溃，readiness 会把 queued/pending 停放为 waiting，记录 interrupted-before-model-call 与 known-no-effect。领取后、终态前崩溃时，远端可能未执行、执行中或已成功，恢复会记录 interrupted-model-call 与 unknown-effect。两种情况都不自动重放，因为本阶段还没有显式恢复命令与持久队列；区别在于 certainty 和未来处置建议。每次停放都在事务内同步 Run、Step、版本和 Trace，并依靠前态条件避免重复恢复。这个设计是在表达不确定性，而不是声称 exactly-once。

**追问 2：为什么终态失败后还能再写 failed，不会再次部分提交？**

**第一人口播：** 成功终态事务如果任何写入失败会整体回滚，Run 仍保持 running、Output 也不存在。外层捕获异常后调用单独的失败收敛事务，将 Step、Run 和 Trace-safe 诊断一起写成 failed。单测用数据库触发器只拒绝成功 Trace，确认成功事务回滚后失败事务可以提交，并检查没有残留 Output。若数据库本身完全不可写，失败收敛也可能失败，系统只能依靠下次 readiness 看到 running 并停放；当前没有宣称所有基础设施故障都能当场收敛，这也是最终故障注入需要继续覆盖的边界。

### 5. 进程重启后如何处理正在调用模型的 Run？

**第一人口播：** 我把恢复放入数据库 readiness 的固定 recovery 阶段。恢复同时扫描 queued 与 running：前者以 Decision 分类连同 pending Step 停放为 waiting，标记 interrupted-before-model-call 与 known-no-effect；后者以 Vendor 分类连同 running Step 停放，标记 interrupted-model-call 与 unknown-effect。每个 Run 必须恰好有一个匹配前态的 active Step，Run/Step 更新也必须各影响一行，否则整个事务回滚。两类都不会自动重放；重复恢复不会追加事件，终态 Run 也不受影响。恢复诊断经过安全投影，只保留处置所需字段。这样服务接收工作前已有可解释状态，同时不会掩盖损坏聚合或猜测远端结果。

**追问 1：为什么自动 retry 在只读任务中也不安全？**

**第一人口播：** 只读描述的是不修改 Project 生产工件，不代表外部调用没有副作用。模型请求仍可能计费、占用限额、生成不同结果，Provider 也未必支持我们可控的幂等键。如果崩溃发生在远端成功但本地未提交的窗口，自动 retry 会重复成本并造成两个候选答案，却没有可靠依据选择哪一个。因此当前恢复只记录不确定事实并停放，后续若要重试，应由显式动作创建新的尝试关系，或者先通过 Provider checkpoint reconcile。这个取舍牺牲自动恢复速度，换来账单与事实语义更可靠。

**追问 2：为什么恢复属于 readiness，而不是 Runtime 构造函数？**

**第一人口播：** readiness 已经是项目打开数据库后的唯一有序生命周期，顺序包含 schema、upgrade、defaults、recovery 和 validate。把恢复接入这里，可以保证表已经存在、升级已经完成，而且服务对外提供工作前完成不一致状态收敛。如果藏进 Runtime 构造函数，只有第一次请求触发，其他入口可能先读到陈旧 running；如果多个组件各自恢复，还会增加并发和顺序不确定性。当前恢复函数本身仍具备幂等条件，因此维护重验证重复进入也不会重复追加。这个结论来自现有生命周期设计，而不是额外创建另一套迁移或启动器。

### 6. 如何保证 Trace 可观测但不泄漏敏感信息？

**第一人口播：** 我没有把 Error 或 Provider 原始响应直接写进 Trace，而是先按失败边界分类，再做 Trace-safe 投影。Project/Novel 查询抛错属于 Context/executionFailed/safe-retry，只有查询成功并确认 Project 不存在才是 contextMissing/never；目标解析和调用属于 Vendor；证据或终态写入属于 Artifact/persistence；输出门禁属于 Artifact/redaction。inspect 还会重新验证持久化诊断 schema，损坏或夹带字段的记录 fail closed。UI 使用固定文案，测试也确认伪密钥不会进入快照。这样既能回答失败发生在哪一层和能否重试，又不会复制敏感根因；这是信息边界，不等于全部合规工作完成。

**追问 1：为什么不保存原始错误，排障不会变难吗？**

**第一人口播：** 原始错误确实可能提供更多上下文，但它也可能包含认证头、请求地址、模型响应、用户正文甚至堆栈路径，直接进入长期持久化 Trace 会扩大泄漏面。我选择让业务 Trace 保留能驱动状态判断和处置的结构化字段，原始运行日志若确有需要，应进入权限、保留期和脱敏策略不同的运维通道。当前阶段建立双重 fail-closed：写入投影失败不能退回原始异常，读取既有诊断失败也不能直接 cast 后返回。代价是损坏 Run 的 inspect 会明确失败，后续需受控修复，而不是把敏感 payload 塞回响应。

**追问 2：Trace 与 chain of thought 有什么区别？**

**第一人口播：** Trace 记录的是系统可验证的生命周期事实，例如 Run 被创建、领取、成功、失败或在启动恢复时被停放，以及对应的安全诊断分类；它不记录模型隐藏推理、内部思维过程或 Provider 原始 token 流。Step 保存提示词指纹而不是提示词全文，Output 保存最终用户可见答案。这样的 Trace 足以回答执行发生到哪一步、为什么需要人工处理，却不会把不可审计且敏感的推理内容当成系统事实。当前事件数量很少，未来扩展因果关系时也应延续 allowlist，而不是演变成对所有内部对象的转储。

### 7. HTTP、Socket 和 UI 在这个 Harness 中分别承担什么职责？

**第一人口播：** HTTP start 负责接收版本化命令并返回已提交的 queued 快照，HTTP inspect 负责按 Run 与 Project 读取持久化快照；它们共同构成权威交互边界。UI 消息是从快照确定性生成的读模型，使用稳定 ID、版本、持久化状态和显示状态。Socket 即使后续加入，也只适合发送“某 Run 版本变化，请重新读取”的提示，不应携带唯一事实或替代数据库。这样断线与刷新不会改变状态语义。当前实现已经有 App 路由和投影函数，但 Toonflow-Web 尚未接入，故端到端刷新体验属于后续联合验收。

**追问 1：inspect 为什么设计成纯读？**

**第一人口播：** 用户刷新、轮询和多个页面同时观察都很常见，如果 inspect 会推进状态、追加事件或触发重试，那么读取次数就会改变业务结果，导致难以测试和排障。我让 inspect 只根据 runId 与 projectId 查询 Run、Steps、Outputs、Traces，再组装快照；单测在两次 inspect 前后统计 Trace 数并比较快照，确认没有副作用。需要恢复或重试的动作必须另建显式命令，携带自己的幂等和权限语义。纯读也让 HTTP 缓存、轮询退避和未来的读副本策略更容易讨论，虽然当前尚未实现这些优化。

**追问 2：UI 如何避免旧消息覆盖新状态？**

**第一人口播：** 投影中包含稳定的 Run ID 和单调递增的 Run version，内容块 ID 也从 Run ID 派生。消费端可以按同一消息 ID 替换，并拒绝版本更旧的投影，而不是把每次轮询当作新消息追加。服务端状态变更与版本递增在同一事务完成，使版本能代表快照演进。当前 App 侧只提供这些契约信息，没有实现 Web 端的版本比较逻辑，所以我会把“具备避免旧覆盖的协议基础”和“前端已经验证不会旧覆盖”严格区分，后者要等跨仓库接线与端到端测试。

### 8. 你如何为这条 Run 链路设计测试证据？

**第一人口播：** 我按风险组织测试。Schema 覆盖新库、升级、唯一约束和损坏恢复回滚；Runtime 覆盖规范化幂等、双连接竞态、事务注入、纯读、前态冲突、resolved target、上下文失败分类、持久化诊断重验证和输入输出门禁；恢复覆盖 queued/Decision 与 running/Vendor 两类中断、一个 active Step 不变量和幂等；路由覆盖版本范围、内容拒绝、404 与 AIMessage 投影。核心定向集合是 53/53，readiness/router 集合 12/12，其中 4 个 schema 测试重复，不能相加成 65 个独立测试；lint 与 diff check 通过。测试数字记录的是阶段命令结果，不代表独立场景总数。全量、构建和 Web 验收未跑。

**追问 1：为什么使用数据库触发器做失败注入？**

**第一人口播：** 单纯 mock 某个 repository 抛错只能证明异常分支被调用，不能证明真实 SQLite 事务里前面的 insert 和 update 是否回滚。我在测试数据库创建只拒绝特定 Trace 事件的触发器，使成功终态事务在最后一段真实 SQL 上失败，然后检查 Output 不存在、Run 和 Step 没有停在成功，随后失败收敛完成。启动事务也用类似方式拒绝创建 Trace，确认 Run 和 Step 一起回滚。这个方法仍是受控本地故障，不等于磁盘满、断电或数据库损坏测试，但比纯 mock 更接近原子性主张。

**追问 2：阶段单测通过后为什么还不能说项目验收完成？**

**第一人口播：** 聚焦单测证明的是本阶段契约在受控环境下成立，它没有覆盖仓库其他模块的回归、Electron 打包差异、真实 Provider 行为、Web 消费端、跨进程并发和长时间运行。用户明确要求每阶段只做单元与契约验证，把全量测试和完整构建留到所有阶段后的统一验收，因此我会在报告中记录未执行项而不是用模糊的“测试通过”掩盖范围。最终验收还应补 App/Web 联调、构建产物、迁移备份、故障注入和性能基线，届时再形成全局结论。

## 二、Agent 应用开发（4 个主问）

### 9. 这条只读 Agent 实际读取什么，又如何限制能力边界？

**第一人口播：** 我没有一开始就开放通用工具，而是把角色固定为 Script Agent，把范围固定为只读项目指导。执行时只查询 Project 的名称、类型、简介、视觉风格、视频画幅以及章节数量，把这些结构化事实与用户问题交给一个已配置文本模型。系统提示明确要求只能依据已提供事实回答，不得声称修改项目，也没有传入任何 tools。这样我可以先验证 Run 生命周期、持久化和恢复，而不会把生产工件副作用混入首条链路。限制是答案上下文较窄，当前也没有检索 Script 全文；这是有意控制的 tracer slice，不是能力不足却包装成完整 Agent。

**追问 1：只靠系统提示能保证只读吗？**

**第一人口播：** 不能，所以我把只读边界放在多层而不是只靠提示词。HTTP 契约只接受固定 role 与 scope；Runtime 的依赖中只有数据库读操作和文本模型调用；模型输入没有 tools；代码路径也没有注入修改 Project 工件的 repository。系统提示只是语义约束，用于避免模型在回答里虚构已执行修改，真正的能力约束来自没有可调用写工具。当前数据库仍会写 Run 自身的生命周期记录，这属于 Harness 控制面，不等于修改 Project 生产内容。未来开放工具时需要单独的权限、审批与 action ledger，不能沿用这条假设。

**追问 2：为什么先选一个固定范围，而不是做通用 Agent API？**

**第一人口播：** 通用 API 会同时引入动态角色、任意提示、工具权限、多步骤计划、取消和补偿，导致幂等与恢复语义无法在一个阶段内被充分证明。我选择一个业务价值可解释、风险又较低的只读项目指导场景，把接口、数据、模型目标和输出类型都固定下来，先穿透 start、schedule、model、commit、inspect 和 UI projection 全链。这样测试能针对明确不变量，而不是只验证抽象框架能编译。代价是复用范围有限；等这条纵向切片稳定后，再从真实第二个场景抽取扩展点，比预先设计万能协议更可靠。

### 10. 你如何处理用户输入和模型输出中的敏感内容？

**第一人口播：** 因为 Run 输入与最终输出都会持久化，我增加了统一的 persistable-text gate。启动时先 trim 请求 ID 与正文，再检查 credential 形态以及 password、apiKey、cookie、token 等敏感赋值，同时拒绝签名 URL 和 base64 负载；命中就不创建 Run。模型返回后也经过同一门禁，未通过不写 Output，而是归入 Artifact/redaction 失败链路。普通 URL 允许，避免把所有链接粗暴视为秘密。输入与输出共用同一检查函数，减少两条边界规则漂移。这个机制是预防性边界，不是完整 DLP，后续仍需保留期、访问控制及误报漏报评估。

**追问 1：为什么普通 URL 允许，签名 URL 却拒绝？**

**第一人口播：** 普通 URL 往往是用户问题或答案中必要的公开引用，全部拒绝会显著降低可用性；签名 URL 则常把临时访问凭据放在查询参数中，一旦持久化会延长其暴露范围。我的策略不是按“是否像链接”判断，而是识别具有授权语义的签名参数和凭据模式，同时对 base64 数据负载进行拦截。这样在安全性与业务表达之间做了更细的取舍。当前测试覆盖代表性允许和拒绝样本，但规则不是密码学证明，Provider 新格式出现时还要扩充检测集，并监控误报而非盲目扩大正则。

**追问 2：模型输出被拒绝后，为什么不直接截断或脱敏再展示？**

**第一人口播：** 自动截断可能破坏语义，简单替换也未必能识别完整秘密范围；若仍把处理后的文本当成功输出，会让用户误以为得到了完整可信答案。我选择 fail closed：输出门禁不通过就不写可展示 Output，Run 按失败链路收敛，UI 只显示固定失败文案，Trace 只保留结构化安全诊断。这样可用性较保守，但事实语义清晰。后续如果要提供可恢复体验，可以让模型基于不含敏感片段的新提示重新生成一个新 Step，或者由人工确认，而不是在同一终态里悄悄改写原答案。

### 11. 模型目标是怎样从逻辑角色解析并被审计的？

**第一人口播：** Runtime 请求的是逻辑文本目标，而不是在业务代码里写死某个 Provider 和模型。Vendor 层解析当前配置后返回一个已绑定的调用句柄，同时暴露安全的 resolved target 元数据，包括 Vendor ID、Model ID 及可选调优参数，但不包含凭据和源配置。我在真正调用模型前先把这份元数据写入 running Step，所以即使 invoke 失败，inspect 仍能回答这次尝试准备使用哪个目标。这样逻辑路由与实际执行证据分开，既保留可替换性，也提高故障审计能力。当前没有实现动态 fallback 或多模型竞速，不能据此声称具备完整路由策略。

**追问 1：为什么 resolved target 要在调用前单独持久化？**

**第一人口播：** 如果只在成功终态一起保存，那么模型超时、拒绝或进程中断时就失去“实际解析到哪个目标”的关键证据，排障只能重新读取当前配置，而当前配置可能已经变化。我先解析并把安全目标写到 running Step，再发起外部调用，使失败也可审计。这个写入不与远端调用形成原子事务，正是为了避免长事务；若目标元数据写入失败，代码不会调用模型，而是进入失败收敛。它记录的是执行身份，不包含 API Key，也不等价于保存 Provider 原始请求。

**追问 2：逻辑目标和物理目标分离带来什么测试价值？**

**第一人口播：** 业务测试可以断言 Runtime 始终请求约定的逻辑角色，而 Vendor 契约测试单独验证配置如何解析为物理目标和调优参数，不需要让每个业务测试了解 Provider 配置细节。在 Runtime 测试中我注入假的已绑定调用句柄，能稳定控制成功、失败与返回内容，同时快照仍能验证 resolved target 是否写入。这种依赖倒置让 Harness 关注生命周期，让 Adapter 关注解析与调用。当前假的 Provider 不能替代真实兼容性验证，因此最终验收仍应包含真实配置的受控 smoke test，但不能在单测结论里虚构真实服务表现。

### 12. 页面刷新后如何重建 Agent 的聊天表现？

**第一人口播：** 页面不需要依赖先前 Socket 消息或浏览器内存，只要持有 Run ID 与 Project ID，就可以调用 inspect 获取持久化快照。App 将快照转换为现有 AIMessage 形态：消息 ID 固定为 Run ID，内容块 ID 稳定派生，终态内容取自 Output，进行中状态取自 Run，attention 再投影成 needs-attention，并附带 schema version 与 Run version。inspect 本身不推进状态或追加 Trace，多页面读取也不会改变业务。这个设计给 Web 提供了刷新重建所需的信息。我要强调的是，目前只是 App HTTP 返回现有消息契约，Web 实际消费、轮询策略和浏览器刷新验收明确延期，并未在本阶段完成。

**追问 1：为什么 start 和 inspect 都返回 run 与 message？**

**第一人口播：** run 是面向控制和排障的完整持久化快照，message 是面向现有聊天 UI 的读模型。start 立即返回二者，客户端可以先展示 queued；inspect 也返回同样组合，刷新或轮询不需要实现第二套投影逻辑。两者同时存在也避免为了 UI 方便而删减 Run 事实。不过客户端应把 run/version 当作状态一致性依据，message 只是展示合同；未来如果 UI 形态变化，可以升级投影 schema 而不改动执行存储。本阶段路由单测只验证响应结构与校验，没有进行真实浏览器消费测试。

**追问 2：如果用户同时打开两个页面会怎样？**

**第一人口播：** 两个页面都只能通过纯读 inspect 获取同一数据库事实，不会因为读取次数推进状态。它们可以依据稳定消息 ID 合并同一条消息，并用单调版本拒绝旧快照覆盖新快照。如果两个页面重复提交相同的 clientRequestId，幂等约束会返回同一 Run；若相同键携带不同正文，则服务端返回冲突而不是猜测用户意图。当前这些服务端契约已有单元与双连接竞态证据，但 Web 端是否正确保存请求 ID、比较版本和处理 409 尚待接线与浏览器验收，因此不能把协议能力等同于完成的多页面体验。

## 三、AI 应用后端（3 个主问）

### 13. 在 SQLite 下如何处理幂等启动的真实并发竞态？

**第一人口播：** 我没有把单连接 Promise 并发当作充分证据，而是让插入使用联合唯一键上的 onConflict ignore，然后在同一事务读取权威记录：若 ID 是本次生成的就继续写 Step 与 Trace，否则比较请求指纹并返回既有 Run或冲突。SQLite 双连接竞争还可能出现 SQLITE_BUSY，所以启动只做一次让出事件循环后的安全重试，重试复用相同生成 ID 与指纹，不会创建第二个业务意图。双连接文件数据库测试覆盖了这一竞态。这个策略适合当前短事务，但不是无限重试；持续锁竞争仍应显式失败并由调用方按同一幂等键重试。

**追问 1：为什么用 onConflict ignore 后还必须重读？**

**第一人口播：** ignore 只告诉我自己的插入没有抛唯一冲突，却不告诉我现有记录是否与本次请求等价，更不能直接拿本地新 ID 当权威结果。因此插入后必须按完整幂等作用域重读数据库记录，比较它的 ID 和请求指纹。若是竞争者创建的相同请求，就返回那条 Run；若键相同但指纹不同，就报语义冲突；若仍读不到，则说明事务或数据库出现异常。这个“写入竞争、读取权威、验证等价”的流程比捕获字符串化唯一异常稳定，也让并发测试能断言只有一个可执行 Run 被调度。

**追问 2：为什么 SQLITE_BUSY 只重试一次？**

**第一人口播：** 这次重试针对两个极短幂等启动事务恰好竞争的瞬时窗口，先让出事件循环，再以相同请求身份重新尝试，可以提高本地 SQLite 的确定性。若无限或多次快速重试，会延长请求时间、掩盖持续写锁问题，还可能形成惊群。一次失败后让错误向上暴露，调用方仍可使用同一个 clientRequestId 安全重试。当前双连接测试证明代表性竞态能收敛，但没有做高并发锁压力测量；后续应结合 busy_timeout、队列化写入或数据库迁移评估，而不是把一次重试说成通用并发方案。

### 14. 你如何保证 Run 和 Step 的状态转换在并发下保持一致？

**第一人口播：** 我把允许的 Run 与 Step 转换集中在 lifecycle 模块，用显式 transition map 校验语义；真正写入时仍带上旧状态、Run version 和受影响行数约束。领取要求 queued/pending，成功要求 running/running，失败只接受当前允许的非终态，恢复也按 queued 或 running 的已知前态更新为 waiting。Run 与 Step 的关联推进放在同一事务，如果任一更新行数不是一就抛错回滚。读取快照也解析并拒绝未知状态，避免脏数据静默穿透。当前是单 Step 场景，未来多 Step 并行还需要更细的聚合版本与顺序策略。

**追问 1：有 transition map 了，为什么还要 SQL 前态条件？**

**第一人口播：** transition map 只能证明“从我刚读到的状态到目标状态”在领域上允许，不能阻止读完之后另一个执行者抢先更新。SQL 的 where status 和 version 条件把检查与写入绑定到数据库当前事实，受影响行数不是一就说明发生并发冲突。两者分工是：map 防止代码提出非法转换，条件更新防止合法转换基于过期快照执行。Run 与 Step 再通过事务共同提交，避免只推进其中一方。这仍属于乐观并发控制，不是分布式锁；冲突后的业务重试策略需按具体命令定义。

**追问 2：version 的用途与 Trace sequence 有什么不同？**

**第一人口播：** version 表示 Run 聚合快照经历了多少次受控状态提交，主要用于乐观并发条件和 UI 拒绝旧投影；Trace sequence 表示同一 Run 内事件的有序位置，主要用于解释发生顺序与唯一约束。一次状态提交可以同时递增 version 并追加一个 sequence，但二者语义不能互换：UI 不应把事件数当快照版本，恢复也不能只靠最大 sequence 判断当前状态。当前 Trace 序号在事务内按既定主链或查询最大值生成，单 Step 足够；若未来多写者并发追加，需要专门的序号分配策略。

### 15. 这套实现还存在哪些后端风险，你会如何演进？

**第一人口播：** 我会先明确当前边界：只有单 Model Step、进程内调度、SQLite 持久化和只读项目指导。恢复已把 queued/pending 归为 Decision/known-no-effect waiting，把 running 归为 Vendor/unknown-effect waiting，并要求恰好一个 active Step，否则事务回滚；但两者都不会自动重放，也没有 reconcile、retry、cancel API。Web 尚未消费投影，数据保留和真实负载也未测。演进顺序应先增加显式恢复命令和持久调度租约，再做取消竞争、权限审计与清理，最后扩展多步骤和工具；每一步继续沿用幂等身份、前态条件、安全 Trace 与 fail-closed 读取，并用新的真实场景验证抽象。

**追问 1：queued 重启和 running 重启为什么要区分 certainty？**

**第一人口播：** queued/pending 说明本地已记录意图但没有开始外部调用，所以恢复归为 Decision，certainty 是 known-no-effect，未来显式 retry 相对安全。running 表示已经领取，可能已保存 resolved target 并发出请求，崩溃后无法判断远端效果，因此归为 Vendor/unknown-effect 并优先 reconcile。两者都投影为 waiting 并要求关注，是因为当前没有自动恢复命令；分类、certainty 与 retry disposition 的差异为后续处置留下依据，也能阻止统一自动重试造成重复计费风险。恢复还要求每个 Run 恰好一个 active Step，避免在损坏聚合上给出虚假的确定性。

**追问 2：最终验收你会补哪些内容？**

**第一人口播：** 我会在所有路线阶段结束后运行仓库全量测试与完整构建，核对生成路由、数据库类型和打包产物；再做 App 与 Toonflow-Web 联调，覆盖刷新重建、重复提交、版本乱序、409、404 和 needs-attention 展示；用真实文件数据库执行多进程锁竞争、强制杀进程与恢复；对受控 Provider 做成功、超时、限流和未知结果 smoke test；最后测 inspect 与启动的延迟、锁等待和存储增长。只有这些证据完成后，才能给出系统级验收结论。目前可陈述的是定向测试与静态检查通过，而不是全量质量已证明。
