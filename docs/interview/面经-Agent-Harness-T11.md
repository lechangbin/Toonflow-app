# Agent Harness T11 面经：持久评测证据阶段版

> 只准备针对已实现代码的追问，不提供简历 bullet 或未证实的结果。T11 Issue #67 未完成。

1. 问：Evaluation Run 与 Agent Run 有什么区别？答：前者冻结一组对照用例、seed 和版本，是比较账本；后者才执行一次 Agent 请求。当前每条评测记录必须引用已终结、有 Trace 的生产 Agent Run。这样避免平行的评测专用流程跑通而生产 Runtime 失败。证据：术语表、ADR-0027、`evaluationRun.ts`。
2. 问：为什么要冻结两侧的修订？答：若 baseline 与 candidate 的 Model、Vendor、Tool、Skill 或 schema 随运行改变，就无法把差异归因到候选变化。清单在记录前锁定两侧修订、case manifest 哈希、同一组 case 和重复 seed，记录只允许落入冻结矩阵。但目前并未实际执行成对实验，不能报改善数字。
3. 问：如何防止一条 Run 被复用成多个评测样本？答：数据库约束同一个 Evaluation Run 中的 Agent Run ID 唯一，且 variant/case/seed 唯一。相同样本、相同 Run 重试写入返回原记录；换 Run 重绑或把同一 Run 填到另一 seed 会失败。对应 SQLite 单测覆盖。
4. 问：如果 Run 没完成或者缺少 Trace，能否记成结果？答：不能。`record` 只接收 terminal 状态、正版本、正确的样本请求 ID 和有效的最后 Trace；Output 可以为空，目前并未以 Output 是否存在单独评定成功质量。`inspect` 复核来源 Run 的请求身份、状态、版本、Output 哈希和最后 Trace，不一致就停止输出有效比较。
5. 问：这个阶段能说 Golden Eval 或消融结果了吗？答：不能。T02 Golden 18 例是独立的确定性领域基线；T11 新建了 18 条 AgentRuntime 请求及 Project fixture，但仅用本地 Fake Model 接通过一格结构链，未完成 72-cell 真实执行。账本能留单 Run 耗时和结构覆盖，待评审清单仍将业务硬门、rubric 与失败分类列为待判定；未采集真实费用或人工评分。T19 真正消融仍被 T11 阻塞，全量验收留到 T21。
6. 问：新执行适配器如何避免另造一条 Agent 路径？答：它调用既有 AgentRuntime 的 `start` 和 `inspect`，用确定性的评测样本请求 ID 继承 Runtime 幂等性；只有确认真正终结，才把该 Run 的持久证据写入 Evaluation Run。预检不在冻结矩阵或修订不符时在启动前失败。测试的调度器和 Text Model 是本地 Fake，不能证明真实供应商或所有 Golden 场景已经走该链路。
7. 问：为什么不能拿不同模型或数据库结构的两组 Run 直接比较？答：Model、Vendor 和 schema 改变会与候选策略变化混杂，无法归因。清单在 baseline/candidate 间要求这三种修订一致，若不同就在记录前拒绝；其他模块修订可作为候选差异保留。它仍是必要而非充分条件，预算相同与逐例质量、安全结果还未完成。
8. 问：只冻结 case ID 为什么不足以做成对比较？答：两侧可能传入不同的正文，比较结果便混入了输入差异。清单现在额外冻结每个 case 的正文哈希，执行前校验；账本也验证 Run 的确定性请求 ID 对应该 cell。不过 seed 尚未控制模型随机性，外部 Golden fixture 与输入的绑定还没有完成，不能把这个局部门禁夸大成完整同条件实验。
9. 问：绕过执行适配器直接写账本，或修改已记录 Run 的输入，如何发现？答：`record` 和 `inspect` 都会解析 Run 持久化的输入，按 Runtime 的 `trim()` 规则核对正文哈希，并核对冻结的 Project、role/scope 和样本请求 ID。伪造来源文本、换 Project 或换角色会拒绝；但 Project 数据快照和模型随机种子未冻结，不能宣称所有环境变量一致。
10. 问：早期已经有一套 18-case 冻结表，为什么还要收敛？答：早期 Draft #90 冻结真实 Golden manifest 和覆盖分母，但使用独立的 Run/Case 表与请求身份；后续生产 Agent Run 账本如果另起一套，就会出现两个权威来源。当前选择把 18-case 原文、哈希和明确提供的输入契约冻结在同一配对账本里，并已移植“覆盖不等于质量”的报告语义。早期 Draft 仍需收敛处理，不能作为两套 schema 并列交付，更不能宣称 18 例已跑通。
11. 问：覆盖报告为什么不能直接变成质量报告？答：它只按冻结的 case、seed 和 variant 统计“有无可复核生产 Run”，不会检查业务硬门、产物语义或人工 0/1/2 评分。即使所有 cell 都 observed，模型可能给出错误结论；现在一个真实只读样例只让基线侧 1/36 个 cell 从 missing 变 observed，且来源版本变更会使整份报告拒绝。质量和收益必须等 18 例真实场景及逐例证据齐全后另算。
12. 问：只保存最后一条 Trace 的 ID 为什么仍不够？答：最后锚点可能真实存在，但中间事件的序号或前驱身份已经断裂；这时无法证明 Run 的因果路径。当前写入与重读都复用生产 Trace 审计，要求完整连通后才承认结构覆盖；定向测试故意把第二条事件指向错误前驱，账本拒绝。它仍只证明记录链连通，不替代业务硬门或产物语义核验。
13. 问：延迟和成本为什么分开处理？答：生产 Run 的创建与完成时间可以复核，当前账本要求两者有效、顺序正确，并保存可重算的端到端耗时；来源时间变更时会拒绝原证据。实际 Provider 收费没有可靠计量入口，所以保持未知值而非写成零。这个耗时是单个 Run 的本地证据，不代表 18 例成对延迟结论，也不能从 Fake Model 用例推断线上成本。
14. 问：为什么 Run 成功后硬门仍是未评估？答：生产 Run 成功只说明执行生命周期完成，不证明当前冻结语料要求的业务产物正确、敏感信息未泄露或权限没有越界。待评审清单把每例声明的硬门 ID、必需产物和 rubric 版本列出，但结果先保持未评估；新语料的单格 Fake Model 测试虽有成功读取 ToolReceipt，也不能据此判定全部来源和安全硬门通过。后续必须由实际 Run、产物和独立校验器给出证据，再提交可追溯的逐例判定。
15. 问：同一评测用例的两次执行正文相同，但所属 Project 不同，为什么仍不可比？答：Agent 会读取 Project 内的章节、剧本和其他生产状态；仅比较请求文字和模型修订，无法排除这些数据差异。现在冻结每个用例的 Project 身份，启动前核对，记账及重读时也核对来源 Run；定向测试证明换 Project 会被拒绝。它仍未冻结 Project 内容快照，因此只能说排除了“不同 Project 身份”这一类混杂，不能宣称完全同条件或已经产生质量收益。证据：`evaluationAgentCase.ts`、`evaluationRun.ts`、T11 定向测试。
16. 问：来源 Run 的输出哈希字段没变，能否保证模型回复没被改？答：不能；字段本身也可能与正文不一致。T11 账本现在按生产 Runtime 的序列化哈希规则重算单个 Output 正文并核对 schema，记账与重读都执行；测试改写正文但不改哈希，账本拒绝。当前证据格式只保存一个输出哈希，所以多输出 Run 也拒绝，而不随机取第一条。将来多阶段 Agent 需要输出集合及产物引用的新契约；当前校验不等于 Golden 业务硬门或质量评分。证据：`evaluationRun.ts`、`tests/evaluationRun.test.ts`。
17. 问：评审提交了产物 SHA-256，为什么还要再验？答：提交值只是声明。报告 v2 在调用方给出明确 `artifactRoot` 后逐条读取引用文件、限制真实路径在根目录内、复算已声明的产物哈希；一个文件不符就拒绝整份报告。未传根目录时 `evidenceFileCheckedRuns=0`，不显示为已验。证据：`evaluationArtifactVerifier.ts`、`evaluationPairedAssessmentReport.ts` 及篡改单测。
18. 追问：两侧文件哈希全对，是否就能宣布候选质量提升？答：不能。哈希只证明当前读取字节与声明一致，不证明文件来自指定生产 Run，也不证明硬门判定、人工评分或身份真实。报告仍把分差标为暂定，72-cell 真实执行、独立场景语义校验和同条件控制没有完成。
19. 问：服务商并发额度很低，评测如何限流和断点续跑？答：`executeVariant` 只接受一个冻结变体，先对全部 case 正文、集合和修订做预检；随后按清单 case、seed 顺序逐格等待生产 Run 终结并记账。可设 `maxNewCells` 控制单次新增量，重进时从 `evaluation.inspect` 的已复核记录跳过旧 cell；定向测试观察到局部 Fake Model 最大并发 1、续跑不重发。追问边界：这不是跨进程锁或全局配额器，多个调用方并发发起仍需外层单执行者约束；测试没调用真实 Provider，不能报实际成本、72-cell 覆盖或业务质量。证据：`evaluationAgentCase.ts` 与 `tests/evaluationAgentCase.test.ts`。

20. 问：为什么 T11 新建 18 例、却不直接把 T02 Golden 18 例改名？答：T02 的测试对象包含提示词编译、数据库恢复和预期失败等领域接缝，并非 18 条已有生产 Agent 输入。改名加泛化提示词只会制造 72 个形式上的 Run，无法验证原有硬门。ADR-0028 固定独立语料身份；v2 Golden 和 v3 AgentRuntime corpus 都能冻结，但历史 T02 结果永不导入 T11 cell。证据：两份 manifest、`agentRuntimeCorpus.ts`、`evaluationRun.ts`。
21. 问：Project fixture 哈希和 Project ID 是否已经证明实验同条件？答：还没有完全证明。物化器在空 SQLite 中先核对 fixture 字节，再原子写入三章、事件、剧本与工作区；v3 账本冻结 fixture 哈希和 Project ID。执行适配器现在在 Model 调用前及 Run 终结后重验这些 Project 行，篡改章节会阻止下一格启动；但模型调用期间没有持续快照锁，外部并发写入仍可能造成瞬时漂移，完整同条件结论要等隔离运行与最终验收。
22. 问：新语料单格 Fake Model 测试究竟证明什么？答：它证明 checked-in 语料、fixture 物化、v3 冻结、生产 AgentRuntime、一次受控来源读取、证据记录及报告分母可以接通；一个 cell observed、其余 71 格 missing。成功 ToolReceipt 只证明进行了有权限的读取，尚无独立 hard-gate 评分，不能推出真实模型的 72-cell 质量或费用。
23. 问：为什么还要冻结 actor，而不只冻结 Project ID？答：同一 Project 下不同身份可能有不同 Skill 授权。v3 从已核验 fixture 读取 Owner ID，冻结每例 actor；适配器启动前拒绝换 actor，Runtime 对显式 actor 核对 Project Owner 并写入 Run input，账本记账和重读复核。否则 baseline/candidate 可用不同权限身份却被错误配对。这个约束不适用于没有 actor 字段的历史 v2 记录；它们保持旧语义。
24. 问：18 例为什么不包含中断恢复和真实审批提交？答：这批语料比较 Agent 对具体用户请求的行为，不能靠提示词可靠制造进程中断或把未经授权的计费/写入当成评测内容。中断恢复与提案→审批状态机由独立确定性验收承担，不计入 72-cell；本语料中的相关问题只检查 Agent 是否解释权限并克制副作用。逐例 Tool/Trace/Output 观察合同见 case matrix，独立机器硬门仍待 #104。
25. 问：#104 的安全报告能否代替人工面经/质量评分？答：不能。它复核冻结 fixture、本例允许且必需的 Tool 输入、真实 ToolReceipt 输出、因果 Trace、Run Output 安全性及无提案/计费副作用；伪造一份自洽哈希的 Tool 输出若与 fixture 不同也会失败，损坏 JSON 会标该格失败而保留 72 格分母。结果只标为 `verified-read-and-safety-only`，仍不评判自然语言回答是否完整准确，也不能证明 holdout 未被开发过程污染。v3 配对报告没传机器安全验证器时显示 `unverified-safety`，传入且通过后也只显示 `pending-semantic-verification`，不计算分差；人工自行勾选 hard gate 不能绕过这一点。#104 未完成，不能报告质量提升。
26. 问：文件 SHA-256 正确为什么还不足以证明评审产物来自这条 Agent Run？答：评审者可能提交一份真实存在但无关的文件。T11 v3 现从账本已观察的 Run 独立生成 Output、ToolReceipt、Trace 三类固定投影，包含该 cell 和 Run 身份；报告同时复算磁盘文件字节与投影哈希，任何一环不符都拒绝整份报告，并单列 `sourceProvenanceCheckedRuns`。合法取消/失败 Run 可没有 Output，因此保留在分母并标 `run-failed`，不强求三份成功产物。投影只进受保护的本地评审目录，不上传原始输出。即便来源绑定成立，语义正确性和评审人身份仍需独立核验，不能因此算出质量提升。
27. 问：已经用 Agnes 实测一格，为什么还说 T11 质量未验证？答：单格探针只在内存 SQLite 中执行 DEV-RT-009 的 baseline/seed 11，Run succeeded，Model 入口一次、受控读取一次、安全读取检查通过。这证明 Agnes + Skill/Grant + 生产 AgentRuntime + v3 账本的纵向接线可用；另 71 格缺失，candidate 没跑，seed 未控制模型随机性，也没有人工盲评或可靠费用凭据。`verified-read-and-safety-only` 不是回答语义评分，不能外推到完整语料或候选收益。证据：`scripts/agnesRuntimeCorpusCanary.ts`、单格报告及 #105。
28. 问：单并发跑 72 格时如何既能断点恢复又不把密钥写入 SQLite？答：运行数据库只在内存中保存当前 Agnes 配置；检查点先临时清空所有 Vendor 输入、`VACUUM` 清除旧页，再序列化并扫描密钥字节，写成新文件后恢复内存配置。恢复时加载快照到新内存数据库，验证完整性及 Vendor 配置为空，再从环境重新注入密钥。定向测试证明模拟密钥没有进入磁盘快照。但此工具尚未接入正式 runner，也不能让中途崩溃的外部模型调用具备幂等性；未知效果必须停机核查，不能自动补跑。
29. 问：怎样避免人工评审先看到 baseline/candidate 标签后有倾向性？答：T11 v3 的盲评准备器按同一 case/seed 固定 36 对、72 个 A/B 槽位，用 HMAC 私钥生成不可猜的 pair/token 和稳定侧序。评审包仅保留请求、rubric、fixture 哈希与安全回复或缺失/失败状态；variant、Run 身份与来源证据哈希只在单独的私有映射中。它避免显式标签泄漏，但还没有真实评审人、评分校准、双评一致性或分歧仲裁，不能把“可盲评”说成“已经盲评”。
30. 问：为什么一个 Evaluation Run 不能只持有一套 AgentRuntime 跑满 18 例？答：新语料包含普通 Script 只读、Script Harness 和 Production Harness；后两者有不同 Skill 绑定与 Project Grant，前两者甚至同为 `scriptAgent` 却 scope 不同。适配器现在用 role＋scope 选择现有生产 Runtime，仍让每条 case 走真实 `start`/`inspect` 与来源账本。局部测试跑通三种 scope 的 Fake Model 和受控读取，但未证明完整 72 格或真实供应商质量。
31. 问：外部模型调用中断后为什么不能凭缺格自动补跑？答：缺格只说明 Evaluation Run 尚未关联终态来源，不能证明 Provider 没收到请求。#105 的执行日志组件在调用前写 `inflight`，单执行者锁防止同目录并跑；完成时重开前后去密钥快照，要求 v3 来源账本恰好多出该格且保留之前所有格。未完成标记、孤儿快照或篡改会拒绝进程崩溃后的自动恢复。Windows 目录 fsync 不可移植，因此不能声称断电安全；组件尚未接入 72-cell runner，Provider 本身也没有幂等保证。
32. 问：单格编排函数执行回调报错时，为什么不自动清除 `inflight` 再试？答：回调可能已把请求交给 Provider，只是本地在记录终态前失败。清标重试会造成重复外部调用。编排器先写 marker，后执行、去密钥检查点、来源账本复核和完成标记；只有完整链成立才允许下一格。这个设计尚未证明全 72 格跑完，仍需真实 Runtime 装配与人工核对未知效果。
33. 问：如果 baseline/candidate 只改变 Skill，是否已经构成有效因果实验？答：只是更强的可比性约束，不是充分条件。v3 Skill-only 校验锁定其余八条修订轴，但还要核对实际激活的 Skill、模型温度/输出/步骤预算、相同 fixture 和并发；交替执行减弱简单时间顺序偏差。普通 Script 只读 case 未受 Harness Skill 处理，应单列负对照，不能把整体差异全归因于 Skill。seed 当前仅是 cell 身份，不控制 Agnes 随机性。没有 72 格来源、独立硬门与盲评时仍无收益结论。
34. 问：已把 Agnes 型号写进 Evaluation Run，为什么还要读取实际绑定？答：清单字段可以由调用方随意声明。定向政策测试通过真实 Vendor 解析 Script 和 Production 两个逻辑目标，核对 `agnes-3.0-flash`、温度 0、512 输出 token 和 524288 上下文；改动生产角色温度会在发请求前拒绝。两步上限由调用包装器强制，政策哈希冻结。单格真实复跑通过仍只说明一个纵向接线，未证明 72 格总预算或候选质量。
35. 问：为什么 Skill-only 比较不能只比较两个 Skill 文本哈希？答：文本哈希不说明哪个 Revision 在运行时被激活，也不说明候选是否偷偷多拿了 Tool 或 Project 能力。实际绑定检查从 Script/Production 两类活动 Revision、政策和 manifest 复算集合指纹，要求两侧 Skill ID 与 Tool/能力清单相同；候选仅可更改指导内容。逐例预检使用真实 Router 验证所有 Harness 请求选择预期 Skill；单测证明新增 `get_novel_text` 权限、撤销 Revision、同优先级路由歧义都会拒绝。预检尚未接入正式 72-cell runner，不能据此声称真实实验完成。
36. 问：为什么通过来源账本 `inspect` 后安全门还要重算 Output？答：两次读取之间可能发生状态变化。一份替换后的正文即使和新哈希自洽、没有敏感文本，也未必是被冻结 cell 所引用的原始 Output。安全门现在复算 schema/正文哈希并与 cell 的 `outputHash` 交叉比对；定向竞态测试验证替换会标 `output-source-drift`。这仍是来源一致性，不是自然语言事实正确性评分。
37. 问：评审投影已经绑定 Run ID 和 SHA-256，为什么还会关心来源读取竞态？答：文件 SHA-256只能证明导出文件字节没变，Run ID 也不能证明导出时读到的 Output 仍是该 cell 冻结的正文。投影器现在在生成文件前复算 Output schema/正文哈希并与 cell `outputHash` 对照，替换正文会拒绝。但当前 EvaluationCase 尚未冻结完整 Trace/ToolReceipt 内容摘要，不能称整条审计链永久不可篡改。
38. 问：正则脱敏门能证明没有任何秘密泄漏吗？答：不能。定向测试至少证明模拟 API key 赋值在 inspect 后进入 Output 时会被独立安全门标为 `output-missing-or-unsafe`；它覆盖已定义格式，不可能穷举未知凭据表示。评审投影仍需受保护目录和人工导出核查，检测不到的泄漏不能被描述为通过。
39. 问：已经把 holdout 划为 3 例，为什么报告仍标 `unverified-public-corpus`？答：分区名称和 manifest 哈希只能证明用例身份没被静默换掉，不能证明候选 Skill 作者未见过这些公开用例。当前三例已在仓库内可读，因此不应称为封存盲测。配对报告显式写出未验证状态；若需要独立泛化结论，需另建受控封存集并保留访问与冻结证据，否则仅能把现有结果当公开压力分层。
40. 问：为什么执行日志有 `inflight`，单格 runner 还需要调用前预检？答：明显的配置漂移、路由歧义或 Project 夹具不符若在外部调用前可发现，应在写 marker 前拒绝，避免制造一个实际上没有发 Provider 请求却需要人工核查的未知状态。预检不代替 marker 后执行适配器的复核；两者之间仍可能漂移。定向测试证明预检失败时模型回调为零且日志保持可安全恢复。
