# Agent Harness T06 面经：执行所有权、取消与重连

> 仅用于技术面试准备，不提供简历摘要或 bullet。下面的第一人称是“如何解释本阶段实现”的练习稿，不能据此声称个人独立主导、线上发布或取得未测量收益。每题都应在面试前用源码和定向测试重新核对。

## 高频主题一：租约和 fencing

### 1. 为什么 Agent Run 需要租约，单靠状态字段不够吗？

**第一人口播：** 在已有持久化 Run 的基础上，我面对的是一个任务可能被重复调度、进程可能中断、模型调用又会持续一段时间的问题。只看 queued 或 running 状态，无法知道当前是哪一个 worker 有权推进；布尔锁也可能在崩溃后永远不释放。我因此为可执行 Run 引入有期限的 owner、进程 epoch 和单调 fence，领取发生在短事务中，后续写入重新验证所有权。定向测试证明同一时间不同 worker 不能同时领取，过期后可以产生新代际；这只是在当前 SQLite 控制面成立，不是跨机器共识。

**追问 1：租约与普通锁最重要的区别是什么？**

**第一人口播：** 我的场景里模型请求不能放在数据库事务内，因此不适合长时间持有数据库锁。普通锁强调显式释放，持有者崩溃可能留下死锁；租约有截止时间，超时后允许其他 worker 接管。但超时只改变数据库中的授权，不会强制旧进程立即停止，所以我还需要单调 fencing token 来拒绝迟到写。实现中续租也必须在到期前由同一 owner、epoch 和 fence 完成。定向测试覆盖过期接管与旧租约续租失败，但没有验证操作系统冻结和真实跨机器时钟偏差。

**追问 2：为什么还要进程 epoch，只有 worker ID 和 fence 不够吗？**

**第一人口播：** worker ID 表示某个执行者的身份，但进程重启、对象重建或配置复用后，同名执行者未必仍是原来的持有者。我的控制面把进程 epoch 一并写进租约，续租与状态提交都要求 owner、epoch、fence 完全一致；fence 则负责全局单调代际，防止旧授权在过期接管后重新生效。这样身份、进程生命期和授权代际各有职责。当前 epoch 是进程内生成并由 Runtime 注入，测试可以控制它；我不会把它说成数据库级领导选举或分布式协调服务。

### 2. 为什么 TTL 到期还必须有 fencing token？

**第一人口播：** T05 已经把模型调用放在 SQLite 事务外，这意味着一个 worker 在调用中途可能超过租约期限，但远端调用不会自动停止。若新 worker接管后只检查“我现在有租约”，旧 worker 收到迟到响应仍可能覆盖状态。我让过期后的每次领取增加 Run 上的 fence，意图、失败和成功提交都在同一短事务内验证 owner、epoch、fence 和未过期条件。竞态测试让旧调用先停住、恢复器在到期点处理，再释放迟到结果；最终没有 Output 被旧 worker 写入。这个保证限定在数据库提交，不保证远端没有执行。

**追问 1：fence 和乐观版本号有什么区别？**

**第一人口播：** 在这条链路里，Run version 表示聚合生命周期或命令事实的修订，取消命令和领取都会推进它；fence 专门表示执行所有权的代际。若把版本号当成所有权，客户端命令导致版本变化就可能无意中让合法 worker 丢失授权；若只用 fence，旧页面又无法发现自己的命令基于过时状态。我因此把两者分开：工作写检查 fence 与状态前态，客户端取消检查 expectedVersion。续租只延长期限、不增加 version，避免长模型调用中无意义地制造客户端冲突。

**追问 2：为什么成功事务仍要检查受影响行数？**

**第一人口播：** 应用层先读到状态不代表提交时状态仍相同，尤其取消、恢复或租约接管可能插进来。我把 owner、epoch、fence、到期时间、当前状态和 version 放在条件更新里，并检查 Run、Step、Attempt 各自恰好改动一行。任何一个不满足就让整个成功事务回滚，因此提前插入的 Output 也不会形成半提交。测试中旧 worker 在过期恢复后拿到模型结果，会被所有权断言挡住。这个机制证明本地事务原子性，不解决远端模型是否已经计费的问题。

### 3. 长模型调用如何保证租约不在调用中自然过期？

**第一人口播：** 模型调用延迟不可控，如果只在领取时设置一次期限，合法调用稍长就无法提交。我把周期续租放在执行期间，按租约时长的比例触发，只更新到期时间，不推进 Run 的生命周期版本；续租始终要求相同 owner、epoch、fence 和有效前态。调用前还做一次所有权断言，降低已知失租后仍发起请求的机会。定向测试把租约设得很短，让 Provider Promise 保持未完成，观察到到期时间增长而版本不变，随后释放结果并成功提交。进程冻结仍可能失租，这是设计允许的安全退化。

**追问 1：心跳失败后为什么不能盲目继续写终态？**

**第一人口播：** 心跳失败可能是数据库短暂不可用，也可能意味着租约已经过期或被新代际接管。我的目标不是在不确定时维持自动完成率，而是防止两个执行者同时提交。因此调用前若已知续租失败就停止继续推进；即便失败发生在调用期间，终态事务仍会重新断言所有权，不能凭内存里的旧租约对象直接写。相应的代价是远端可能已产生响应但本地不能提交，需要依照调用意图进入待核对路径。现阶段没有真实 Provider 的跨网络故障注入结果。

**追问 2：心跳为什么不应该每次都增加 Run version？**

**第一人口播：** version 对客户端来说是状态与命令的并发契约，而心跳只是延长同一执行所有权的有效期，并不改变 Run 的业务状态或已提交证据。如果每次续租都增加 version，一个正常长调用会让刚刷新页面的取消命令快速变成过期版本，产生无意义的 409，也让 Checkpoint 版本间隙难以解释。我因此只更新到期时间，仍让领取、意图、取消和终态推进 version。测试明确断言长调用期间 lease expiry 增长而 version 不变；这不是“心跳不写数据库”，而是不写生命周期 revision。

## 高频主题二：恢复与副作用边界

### 4. 应用启动时为什么不直接把所有 running Run 判定为中断？

**第一人口播：** 数据库就绪流程也可能在应用维护检查时再次运行，而另一个 worker 仍持有有效租约。如果扫描只看 running，就会把正在调用模型的任务错误地改成 waiting，甚至制造虚假恢复 Attempt。我在恢复器内重读候选 Run，并以当前恢复时刻检查租约到期；有效租约保持原状，只有无租约或到期才进入 T05 的 Checkpoint 分类。定向测试先在过期前扫描，确认状态和 Trace 未变，再在到期点扫描，确认旧租约被清除且 Run 收敛。这个规则偏向安全，不把“启动”本身视为抢占许可。

**追问 1：进程已经重启，但旧租约还没到期怎么办？**

**第一人口播：** 旧进程可能确实已经消失，但仅凭本进程启动无法证明其他持有者已经死亡；若数据库同时被两个进程打开，贸然抢占有效租约会形成双执行窗口。因此当前策略是等待租约过期后再按 Checkpoint 恢复，牺牲最多一个租约周期的恢复速度来保留所有权安全。启动扫描若发生得太早，不会自动创建新 Provider 调用；再次恢复或后续运维扫描需要在到期后触发。本阶段没有实现分布式进程健康探测，也没有宣称自动调度所有安全后继 Attempt。

**追问 2：租约过期后为什么还要看 Checkpoint？**

**第一人口播：** 租约只回答“现在谁可以写本地 Run”，不回答“外部模型请求是否发生”。过期时旧 worker 可能在模型调用中，Provider 也可能已经计费或产生结果。我沿用 T05 的意图边界：最新可信证据在调用意图之前，属于已知无远端效果，可以记录因果后继；意图之后没有成功提交，就按未知效果停在 waiting 和 attention，绝不自动重放。测试让在途模型调用失租后返回，验证旧结果被拒绝，Run 仍保留意图证据而没有 Output。这是安全分类，不是 Provider 查询式 reconcile。

### 5. 什么情况下可以自动重试模型调用？

**第一人口播：** 当前 T06 并没有开放通用自动重试。设计上只有能够证明 Provider 尚未被调用的 pre-intent 窗口才具备安全重试资格；恢复器会把原 Attempt 标记为中断并创建带前驱的新 Attempt，留下因果证据。但本阶段仍将 Run 停在 waiting，不自动派发后继 Attempt，因为还没有完整的显式重试命令与调度策略。调用意图之后即使实际请求可能尚未发出，恢复时也无法证明这一点，所以按未知效果处理。面试中我会区分“具备重试资格”“已创建后继记录”和“系统已自动重试”三件事，避免夸大实现。

**追问 1：为什么不能根据没有 Output 判断 Provider 没执行？**

**第一人口播：** 没有 Output 只说明本地成功事务没有提交，不说明远端没有收到请求。进程可能在 Provider 已返回后、提交 Output 前崩溃，或者网络超时但 Provider 已处理。若看到空 Output 就再次调用，可能重复计费、生成两份不一致答案，甚至未来接入工具后重复修改业务数据。所以我用调用前的 durable intent 划分已知和未知窗口，未知时等待核对，不把“数据库里没有结果”偷换成“外部没有效果”。单元测试能验证本地不重放，真实 Provider 行为需要最后验收与额外协议。

**追问 2：安全的后继 Attempt 为什么还不自动执行？**

**第一人口播：** T05/T06 的目标先是把事实和权限边界做清楚：哪个 Attempt 中断、哪个 Checkpoint 可信、旧租约是否已经失效。如果立即把“可安全重试”连成自动调度，还要回答调度触发器、取消优先级、预算、重复启动、重试上限和失败退避等策略，而这些尚未落地。我选择让后继 Attempt 可检查但暂不自动调用 Provider，避免把恢复资格误当成重试授权。这样可用性暂时低一些，但行为与证据一致；后续阶段可以在明确命令和策略后再打开自动派发。

### 6. 如果旧 worker 在恢复后收到迟到的模型结果，会怎样？

**第一人口播：** 这是租约设计里最重要的反例。旧 worker 的内存仍持有模型响应，但恢复器已在到期后把 Run 收敛并清除了旧 owner/epoch/expiry；它尝试写终态时，事务内的所有权断言无法通过。因此不会写 Output、成功 Checkpoint 或 succeeded 状态，也不会把模型正文塞进诊断。我用一个受控 Promise 停住 Provider，推进恢复时间到租约到期点，再释放迟到结果，测试断言 worker 报所有权丢失、Run 在 waiting、Output 数为零。这里证明的是本地提交被隔离，远端结果是否存在仍是未知效果。

**追问 1：旧 worker 抛错后会不会把 Run 标记为 failed？**

**第一人口播：** 不能。所有权丢失不是当前 worker 有资格写入的业务失败。如果它在捕获异常后再写 failed，就等于绕开 fencing，把已经由恢复器或新代际接管的 Run 再次覆盖。实现中所有权丢失错误从执行流程向上传递，普通失败收敛路径也要求同一租约 tuple 和未过期条件；因此旧 worker 没有第二条无门禁写入通道。定向测试检查迟到结果后 Run 保持恢复器给出的待核对状态。调度器如何记录 worker 局部日志，不等于可以修改持久 Run。

**追问 2：能否用 fence 让远端 Provider 也拒绝旧调用？**

**第一人口播：** 当前不能。fence 只存于 Toonflow 的本地数据库条件写；普通文本模型 API 未承诺识别这个 token，也无法参与同一 SQLite 事务。它能阻止旧 worker 写本地 Output，却不能撤回已经发送的请求或避免远端计费。若未来某个 Provider 支持幂等键、查询调用状态或可验证取消，可以针对该适配器设计 reconcile 协议，但必须逐一验证对方保证。现在我只声称本地 fencing 和未知效果停机，不宣称端到端 exactly-once 或远端去重。否则会把本地安全性质错误外推到不受控的远端系统。

## 高频主题三：取消与命令幂等

### 7. queued 与 running 的取消为什么行为不同？

**第一人口播：** 在 queued 阶段，模型调用意图还未提交，系统能确认没有越过外部副作用边界，因此取消命令可以在一个事务中把 Run、Step、Attempt 都改为 cancelled，清除租约并阻止计划中的执行。running 阶段已经有持久调用意图，Provider 请求可能发出，贸然标记 cancelled 会向用户暗示远端已停止。我让取消先记录持久意图和命令身份，Run 继续保持 running；在途调用若成功就保留真实 Output，失败则按未知效果处理。测试覆盖两种状态，并验证前者模型调用次数为零、后者不会虚报终态取消。

**追问 1：为什么 running 取消后仍可能显示 succeeded？**

**第一人口播：** 用户点击取消与远端请求完成之间存在竞态。若 Provider 已经在处理，当前实现没有传输级 abort 承诺，更不能把本地取消意图解释为远端结果已被撤销。我的做法是把“用户希望停止后续工作”作为单独事实持久化，但仍允许合法持有租约的在途调用按真实结果提交成功。快照同时暴露成功状态与取消请求时间/命令 ID，避免丢失用户操作历史。定向测试在模型 Promise 未完成时请求取消，再释放结果，最终保留 Output。这个结果不是取消失败的隐藏，而是明确的效果边界。

**追问 2：queued 取消与 worker 领取同时发生怎么办？**

**第一人口播：** 两条路径都在 SQLite 的短事务和条件前态下推进。若取消先提交，Run 变为 cancelled 且记录取消意图，worker 的 queued 领取或后续 intent 提交不再满足前态；若 worker 先提交调用意图，取消看到 running 时只记录意图，不声称远端未执行。若 worker 只是领了租约但尚未提交意图，Run 仍 queued，取消可以安全终态并清除所有权，worker 的下一次所有权断言会失败。这样每个序列化顺序都有明确结果，而不是靠内存标志猜测。最终以数据库提交顺序为准，不能以用户点击时间推断效果。

### 8. 取消命令如何保证重试幂等？

**第一人口播：** 浏览器超时或重连后可能重发同一取消请求，单靠 expectedVersion 会把正常重试误判成冲突，因为第一次请求已推进版本。我为命令保存 Project 范围内的 Run ID、clientCommandId、输入指纹、预期版本和结果版本；同一 ID、同一输入再次到达时读取当前权威快照，不再追加 Trace 或改变状态。同一 ID 若换了预期版本或其他输入，就拒绝身份复用。定向测试验证同一命令重复后命令表仍只有一行，异输入冲突；这只解决本地命令幂等，不代表远端 Provider 取消幂等。

**追问 1：为什么要保存输入指纹，而不是只存 command ID？**

**第一人口播：** command ID 是客户端给出的名字，客户端错误或恶意复用时，同一个名字可能对应另一条 Run、另一预期版本，甚至未来另一种命令。若只按 ID 返回旧结果，就会把不同意图错误地当作成功重试。我把命令关键输入规范化后计算指纹，并在重复 ID 时对比；相同才认定为重放，不同则明确冲突。指纹不包含模型正文，也不用于证明操作者身份，权限仍由路由和 Project 范围约束。测试覆盖了同 ID 更改 expectedVersion 的冲突情况，后续命令扩展仍要遵循同一原则。

**追问 2：为什么重复命令返回“当前快照”而非第一次响应？**

**第一人口播：** 取消命令的作用是确保同一请求只改变状态一次，而 UI 重连真正需要的是服务端此刻的权威状态。第一次请求可能只写了 running 的取消意图，随后模型完成，若重复时硬返回旧的 running 响应，页面反而会退回过时视图。因此我保留命令记录用于判断是否同一输入，重复时不再写状态，但重新读取当前 Run 快照。命令表同时保存第一次结果版本，方便审计原始效果；响应本身允许展示更新后的事实。测试检查重复请求没有新增命令记录或状态推进。

### 9. expectedVersion 与幂等键分别解决什么问题？

**第一人口播：** 这两个机制不能互相替代。幂等键识别“这是不是同一条客户端命令的网络重发”，expectedVersion 判断“这条新命令是否基于最新的 Run 状态”。在途模型调用会从 queued 推进到 running，旧页面若拿着 queued 版本取消，应先收到冲突并刷新，再按当前状态决定如何处理；相同命令因响应丢失重发则先匹配命令身份，允许读取最新快照。实现顺序正是先查已有命令，再检查新命令的版本和状态。定向测试同时覆盖旧版本拒绝与同 ID 重放。

**追问 1：如果两个不同 command ID 同时取消同一 Run？**

**第一人口播：** 两条命令如果都带同一 expectedVersion，SQLite 事务会序列化，第一个成功并推进 Run version，第二个读到版本变化后拒绝。即便第二个客户端刷新后带新版本再次提交，当前实现也会看到已有取消意图而拒绝新的身份，保持首个已接受意图和命令 ID 稳定。这避免一连串点击反复改写取消时间或把审计事实替换掉。测试覆盖在途 Run 第一次取消后再用新 ID、新版本请求的冲突；它不是全站分布式幂等服务，只作用于该 Run 命令表。

**追问 2：这个方案对客户端生成 ID 有什么要求？**

**第一人口播：** 客户端应为一次逻辑取消操作生成稳定且唯一的 ID，网络重试必须复用它，而不是每次 HTTP 请求重新生成。请求还需携带上次权威快照中的 expectedVersion；若收到版本冲突，要重新读取 Run 并让用户理解当前状态，不能无限自动换版本重放。服务端验证 ID 非空、长度有界，并用唯一约束防并发插入。当前 Web 尚未接入这套流程，所以这仍是后端接口契约与前端实施要求，不应说成浏览器体验已经完成。

## 高频主题四：刷新与状态投影

### 10. Socket 断开时为什么不把 Run 标记失败？

**第一人口播：** Socket 描述的是浏览器和服务端之间的传输连接，不是模型执行本身。用户关标签、网络切换或代理超时，都可能让 Socket 断开，但 worker 仍在调用 Provider；若把断连写成 failed，会制造与真实执行相矛盾的持久事实。我让 Run 的状态只由数据库中的生命周期事务、恢复和命令决定，Socket 事件不参与授权或终态判断。断连后页面需要重新调用 Project 范围内的列表或 inspect，按服务端快照恢复展示。本阶段提供了接口和单元测试，没有宣称 Web UI 已完成实际接线或浏览器断网验证。

**追问 1：刷新后如何找到当前 Run？**

**第一人口播：** 客户端不应只保留上一次 Socket 内存对象，而应带 Project ID、固定 Agent role 和 scope 请求服务端列表。后端按同一范围读取当前未终结 Run，并返回最近 20 个 Run 的确定性排序快照；如果没有活跃 Run，则使用最新历史 Run 作为 current 的展示基准。每个快照都能再用 Run ID 和 Project ID inspect，避免跨项目读取。定向测试创建超过 20 条记录，核对 current、最近数量、顺序和另一个 Project 的空结果。前端何时触发请求仍待后续接线，不能把后端接口等同于已完成的重连体验。

**追问 2：为什么不是把所有历史 Run 一次性返回？**

**第一人口播：** 重连需要快速恢复当前工作和近期上下文，不需要在每次刷新时读取无限历史。当前接口固定返回最多 20 个最近 Run，同时单独返回 current，按创建时间和 ID 排序以避免同一时间戳下顺序不稳定。这是受控的展示窗口，不是归档删除，也不限制按已知 Run ID inspect。当前没有做性能基准，所以不能宣称这个数字是最优吞吐配置；如果后续需要完整历史，应增加分页和索引评估，而不是把上限偷偷放大。

### 11. 重连期间状态又变化了，列表快照会不会过时？

**第一人口播：** HTTP 返回的任何快照都可能在送达浏览器后变旧，因此接口目标不是制造永不变化的视图，而是给出可重新读取的权威状态和 version。客户端收到列表后，可以按 Run ID inspect；执行取消等命令时带 expectedVersion，由服务端拒绝过时写。模型完成可能发生在列表读取和页面渲染之间，这属于正常并发，而不是 Socket 断连导致的持久状态变化。本阶段后端实现 current 与最近列表、项目隔离和路由投影，未做 Web 实际重连流程，因此我会把浏览器一致性验证留到后续阶段。

**追问 1：列表读取为什么仍需要 Project 范围？**

**第一人口播：** Agent Run 包含用户输入、模型输出和诊断，即便只读也不能因为知道一个 Run ID 就跨项目拿到内容。我让列表和 inspect 都以 Project ID 为范围，列表还固定 role 与 scope，避免不同 Agent 能力的历史混在一个页面中。测试用另一个 Project 查询同一数据库，确认返回空集合。这里的 Project 过滤是数据访问边界的一部分，但完整身份认证和权限授权仍依赖上层 HTTP 中间件；我不会把字段过滤单独说成完整多租户安全审计。后续仍需核对用户与 Project 的实际授权关系。

**追问 2：HTTP 列表能替代实时推送吗？**

**第一人口播：** 不能完全替代。列表解决的是刷新和断线后的状态重建，能够从数据库找到当前与近期 Run；实时推送仍可用于降低页面更新延迟。但推送事件应该只作为“有新状态可取”的提示，不能成为业务状态唯一来源，因为事件可能丢失或乱序。我把持久 Run、命令和快照接口作为控制面，Socket 只属于传输层。当前 T06 尚未把 Web 推送与重连拉取整合，也没有浏览器 E2E 证明体验，因此我只会陈述后端契约已具备，不宣称实时 UI 已完整交付。

## 高频主题五：后端演进与证据边界

### 12. 老数据库如何升级到带租约的新结构？

**第一人口播：** Toonflow 已有 T04/T05 的 Run 历史，不能为新增能力清空表重建。我在新库建表中加入 owner、epoch、过期时间、fence 和取消字段，并在升级路径对已有 Run 增量加列，其中 fence 默认 0；命令表按现有初始化机制创建。这样旧 Run 的 status、version 和 Output 不被伪造修改，也不会因为新字段为空就宣称它曾持有租约。定向升级测试模拟旧表缺少 T06 字段及命令表，运行初始化和升级后检查历史 Run 仍为原终态、原版本，新增 fence 是 0。完整生产数据库迁移验收仍留到最终阶段。

**追问 1：为什么不能把所有旧 Run 的 fence 回填为 1？**

**第一人口播：** fence 的含义是某次执行所有权代际，不是表结构版本。旧 Run 从未经过 T06 领取协议，给它们回填 1 会伪造一段不存在的授权历史，也可能误导恢复与排障。把默认值设为 0，表示尚无 T06 领取；首次合法领取才在短事务中增加到 1。老 Run 的其他历史状态和版本保持不变，T04/T05 的 Checkpoint 兼容仍按原规则验证。升级测试检查这个默认语义，但没有把旧数据自动转换成可执行的新 Attempt，这需要单独的恢复策略。迁移只能补结构，不能补造事实。

**追问 2：数据库类型文件为什么要同步生成？**

**第一人口播：** 运行时 schema 已新增列和命令表，如果 TypeScript 的派生声明仍是旧结构，编辑器和静态检查就无法准确反映数据库契约，后续代码容易绕过类型或错误假设字段可空性。项目已有从实际 SQLite schema 生成声明的开发工具，我用新库结构重新生成类型文件，而不是手工猜字段。随后跑 TypeScript 静态检查，确保新 Runtime 与路由契约可以编译。生成类型不等于执行了完整生产迁移，升级行为仍需独立测试验证。类型一致性只是正确性门槛之一。

### 13. 本阶段怎样验证竞态，而不是只测正常路径？

**第一人口播：** 我把失败点放在真实并发边界：两个 worker 争同一 queued Run、租约到期后新代际接管、旧租约续租失败、长模型调用需要 heartbeat、取消与在途调用交错、恢复后迟到结果提交。测试使用 SQLite、可控时钟或 Promise 停住 Provider，在每个边界检查状态、版本、fence、Output 和 Trace；还覆盖旧库升级与 HTTP 路由返回。聚焦测试能证明这些受控场景的合同，但不代表真实多进程压力、操作系统强杀、浏览器断网或真实 Provider 故障均通过。我会把这些明确留在最终验收清单。

**追问 1：为什么要用可控 Promise 停住 Provider？**

**第一人口播：** 单纯在测试里加 sleep，很难稳定命中“模型请求已发出但尚未返回”的关键窗口，也无法精确安排取消或恢复的顺序。我让 fake Provider 返回一个由测试显式释放的 Promise，先确认 Run 已进入 running 且调用意图持久化，再执行取消或把恢复时间推进到租约到期，最后释放模型结果。这样断言的因果顺序是确定的，能分别验证“取消只记意图”和“旧 worker 迟到结果不能提交”。这只是本地受控竞态，不等同于真实网络包重传或供应商接口语义。

**追问 2：为什么阶段测试不运行整个仓库？**

**第一人口播：** 用户明确约定每个深化阶段只做相关单元与契约测试，把完整测试放到所有阶段完成后的统一验收。我的阶段验证因此聚焦于 Agent Run 的租约、Runtime、Schema、路由，再运行 TypeScript 静态检查和 diff 格式检查；报告中明确写出未执行全量 App/Web build、浏览器 E2E、Electron 打包及真实 Provider smoke test。这个划分有利于快速发现本阶段回归，但它不能替代最后跨模块验收。面试时我不会把“聚焦测试通过”说成“整个产品已上线稳定运行”。最终验收必须再证明跨模块兼容。

### 14. 你如何界定自己在这一阶段的责任与结果？

**第一人口播：** 在这个开源二次开发项目中，我会把可核验的事实限定为当前分支里的设计记录、代码 diff、定向测试和后续 PR/Issue 链接。T06 的目标是建立本地执行所有权、旧 worker 写入隔离、取消命令和后端重连快照契约；我能解释每个事务边界和测试观察，但不会据此声称真实用户采用、线上故障率下降或个人独立完成了原项目所有模块。若面试官追问“谁做了什么”，我会展示相应提交和评审记录；若还没有合并或最终验收，就明确说处于阶段交付而非完整产品发布。

**追问 1：如何证明不是只写了设计文档？**

**第一人口播：** 我会从一个具体竞态开始演示：停住 fake Provider，展示数据库中的调用意图和租约，再让恢复器在到期点清除旧所有权，释放迟到结果后检查旧 worker 被拒绝、Output 仍为空。这个场景有对应的 Runtime、恢复器和测试文件；取消命令也有命令表唯一约束与路由测试。设计文档负责解释选择，代码和自动化断言证明受控行为，Issue/PR 记录则说明交付轨迹。没有做过的多进程压力或真实浏览器断线，我不会用文档措辞冒充已验证证据。

**追问 2：如果面试官要求性能收益数字怎么办？**

**第一人口播：** 当前阶段没有真实流量、成本或延迟基线，我不会编造百分比。可以给出可测计划：统计同一 Run 并发领取成功数、过期后旧 fence 的拒绝率、重复取消造成的额外状态变更数、重连快照与数据库的差异，以及 heartbeat 写频率和 SQLite 锁等待。聚焦测试只给出正确性证据，例如受控样本中旧 worker 未写入 Output；它不能推导线上吞吐提升。等最终验收或试运行拿到可复现测量，再决定是否形成量化结果。没有基线就不能宣称改进幅度。

### 15. T06 仍有哪些限制，下一步应该做什么？

**第一人口播：** 我会把本阶段明确定位为后端控制面的一步，而不是完整 Agent 产品。它仍只支持固定范围、单个只读模型 Step；安全的 pre-intent 后继 Attempt 会记录但不自动派发，post-intent 未知效果没有 Provider reconcile；取消不是远端 abort；Web 尚未接入列表/取消并完成浏览器重连测试。下一步应先设计显式处置与重试授权、把 UI 接到权威快照，再做多进程、真实 Provider、App/Web 构建和全量验收。这样的边界陈述能让面试官看见取舍与路线，而不是把未实现能力包装成结果。

**追问 1：为什么不直接上 Redis 分布式锁？**

**第一人口播：** 当前项目的持久事实和执行协调都在单机 SQLite，新增 Redis 会引入部署、可用性、锁与数据库双写一致性问题，却不自动解决 Provider 调用的未知效果。我的优先目标是先在现有存储中把租约、单调 fence 和提交前态验证做对，并用 Checkpoint 处理外部副作用边界。如果未来真有多实例水平扩展需求，应评估中心化协调和数据库事务的组合、时钟与故障模型，再决定是否迁移。T06 的测试没有覆盖多机环境，所以不能把现有实现称为通用分布式锁服务。

**追问 2：真正的最终验收最容易暴露什么问题？**

**第一人口播：** 我会重点怀疑跨模块和真实时间行为：长 Provider 请求期间 heartbeat 与 SQLite 维护是否互相阻塞，进程强杀后过期恢复是否按预期再次触发，真实浏览器断线后页面是否从列表准确重建，取消命令的 ID 是否在网络重试中保持稳定，以及旧数据库在生产数据规模下升级是否安全。还要跑完整 App/Web 测试、构建、浏览器 E2E、Electron 打包和受控 Provider smoke test。阶段单元测试为这些验收提供可复现基线，但不能提前宣称它们已通过。
