# ADR 0026: Stage controlled Video generation without reusing the manual dispatch

Status: staged Owner approval, opt-in HTTP execution, and model proposal seam implemented; T17 Issue #73 and T21 acceptance incomplete.

## Context

The existing `startVideoGenerationBatch` validates Video Capability and Prompt Revision, creates Production Action and Generation Task records, then asynchronously calls the Vendor. Its error path marks provider failures as failed even when submission might have happened. Reusing it directly as a model Tool would give the Agent a billable side effect without a separate Owner decision or an unknown-result no-replay boundary.

## Decision

- Keep manual single/batch Video routes as compatibility paths. HTTP workbench callers cannot claim `requestedBy: "project-agent"`; trusted internal modules may use that provenance only after their own authority checks.
- The first controlled Video candidate is one existing Video Track, text-to-video only, with no external image/file reference. The Project-owned Script and Track, active Prompt Revision, current Track selection, and absence of an existing Video must agree. Its exact payload and relevant target state, including the Prompt Revision's structured brief/draft and rendered text, are hashed without writing a Production Action or contacting a Vendor.
- A later Owner approval must re-run this preflight in its commit transaction and compare target hashes. It must then record a durable submission intent and distinguish known failure from unknown Provider outcome before any Agent-facing Vendor Tool becomes available. Approval, dispatch, recovery, cancellation and late-result reconciliation are not implemented by this ADR's first slice.
- Image-to-video, keyframes, uploaded media and batches need separate Project-scoped media ownership and deduplication contracts; they are not silently accepted by this first slice.

## Consequences and evidence

`src/controlledTools/videoGenerationProposalContract.ts` is a no-effect preflight seam. `tests/videoGenerationProposalContract.test.ts` covers Project isolation, selected/already-generated Video rejection, unsupported media, exact Track selection, Prompt Revision drift and invalid persisted JSON. No model Tool or HTTP approval is exposed yet. Vendor capability inspection and true Provider semantics still belong to later controlled execution work and T21 final acceptance.

The second preparatory slice extracts `prepareVideoGenerationCommand` from the manual Video orchestration. Manual generation and future controlled dispatch now share one no-write command validation path for Track scope, configured Model/Capability, Prompt Profile and image inputs. `prepareControlledVideoProposal` combines that path with the frozen Track/Prompt state and checks the state again after asynchronous Vendor inspection; it returns hashes and a bounded preview, not media bytes or dispatch authority. Approval must later rerun preparation and compare both target and command hashes. Focused fake-Vendor tests prove no Production Action, Generation Task or Vendor submission occurs during preparation and detect target drift during inspection.

An Owner-configured `o_agentVideoQuotePolicy` stores a versioned local approval estimate keyed by the exact Project, Vendor, Model, text-to-video capability, output selection and audio selection. The server rejects absent, invalid or mismatched policy rows; an Owner-only compare-and-swap update prevents silent overwrites. Authenticated `/api/agentRuns/videoQuote/get` and `/set` routes expose only this configuration, never a dispatch action; Project deletion purges its policy rows in the authorized transaction. This is an upper-bound estimate for an Owner decision, **not** a Vendor quote, billing receipt, dispatch permit or assurance that a request will cost that amount. The Web workbench can configure the current no-image text-to-video selection, but browser behavior remains unverified. Approval binds the quote revision and exact selection and rechecks both before dispatch intent. Capability availability alone cannot invent a price.

`videoApprovalScope` now binds the prepared payload, target-state hash, command hash, exact quote target, revision and amount into one candidate scope hash. Its `recheck` rejects a changed quote revision, Track/Prompt target or prepared command. It is still an in-memory candidate: without a durable child Run and Owner decision, the hash does not authorize dispatch.

The next slice persists that exact scope in a dedicated `approved-billable-video-v1` child Run with Step, Attempt, pending ToolReceipt, Approval, Checkpoint and Trace. Authenticated Owner-only propose/inspect/list/decide routes are separate from the production model Tool catalog; no model adapter or Video dispatch endpoint is registered. Before an Owner approves, the runtime reruns command/capability and quote preparation and checks Track/Prompt plus quote again inside the decision transaction. Approval leaves the Run waiting with `video-dispatch-not-enabled`, only `inspect` allowed, pending receipt and no ToolCall, GenerationTask or Vendor request. Rejection and expiry close the local review without calling a Vendor; startup recovery expires stale pending/approved reviews. This intentionally stops at an approval record, not an authorized executable request. The future dispatch implementation must independently verify the scope, record a durable no-replay submission intent, and reconcile ambiguous or late Provider results before being exposed.

The internal `videoRequestLedger` now records a distinct Video ToolCall and `o_agentVideoVendorRequest` intent before any future external call; it does not reuse the image-specific ledger. Reservation is Owner-checked, exact-scope and target/quote-checked, with a unique request ID and checkpoint. A repeated reservation returns `newIntent: false`, and startup changes an unacknowledged intent to `unknown` with a reconciliation-required Trace and no replay. The ledger has no HTTP route, Vendor adapter, Provider task handling or Artifact commit yet. Therefore even though it creates an intent record in targeted tests, production approval remains non-executable and no request is sent. Future integration must only let the creator of a fresh intent cross the Provider boundary; an unknown result must never be retried as a new request without explicit reconciliation.

The ledger can now durably record a trusted Provider task identifier exactly once with a checkpoint; a different identifier conflicts. An explicit ambiguous-submission mark has the same no-replay posture as startup recovery, while a later verified task identifier may be attached to the unknown request. Neither operation claims an Artifact, creates a Video row, or makes the Provider adapter callable from HTTP/model tools. Task identity is observation evidence, not completion evidence.

Video bytes now enter a separate `o_agentVideoArtifact` media-intent/observation path, with a request-scoped deterministic path, MP4 header and size checks, SHA-256 verification after writing, and a `write_pending` record that can be recovered from local media without invoking a Provider. Trace links the Video Vendor request and Artifact to the same Run/ToolCall; legacy databases gain nullable Trace columns. A canceled Run labels later bytes `late` and never creates `o_video`. An `observed` Artifact is still evidence only; Project Video, GenerationTask and ArtifactRevision acceptance require a separate guarded commit transaction. No live Vendor adapter is connected.

`videoArtifactCommit` now provides that local acceptance transaction. It requires authenticated Project Owner, matching Run version/approval/scope, an observed non-late Artifact, unchanged Track/Prompt target and no cancellation. It atomically writes ProductionAction, GenerationTask, Video, ArtifactRevision, typed Tool output/receipt, checkpoint, Run status and linked Trace; duplicate commit returns the existing output. A changed target or local write failure rolls back Project adoption and leaves the media observation for review. The GenerationTask currently stores the redacted command hash and approval scope rather than raw Provider command data. This is not a Vendor execution path: no production composition or HTTP commit endpoint calls it yet, and a real Provider result has not been tested.

`videoGenerationExecution` is a pure internal orchestrator for one future dispatch: it reads the approved scope from the server, compares the freshly prepared command hash, records an intent, and only the newly reserved request invokes the Provider port. A duplicate reservation never invokes again. Exceptions from invocation become unknown; an observed artifact whose local commit conflicts remains awaiting review. Its deterministic fake-port unit tests cover this ordering, but no production adapter, external URL normalization, or HTTP execute route is composed. Direct MP4 base64 is the currently supported observation form; a Provider URL would require a separately constrained retrieval path before exposing execution.

The Video ledger now distinguishes local cancellation intent from confirmed Provider cancellation. An Owner can mark a dispatched/unknown/submitted request as `cancellation_requested`; an already observed Artifact becomes `late` atomically, and later bytes or task IDs attach to the same request without reopening the Run or being adopted. `stopWithoutReplay` closes local Run/Receipt/Step state for an unknown, cancellation-requested or late request while preserving request evidence and recording that Provider effect is not disproven. No Provider cancel API, refund or no-charge claim follows from either local transition. These operations remain internal (no HTTP or Web control yet), and a live Vendor callback race has not been exercised. Targeted SQLite tests cover cancellation before/after observation, late task ID and no second intent.

The Owner approval snapshot can now project a durable Video request, optional observed task ID and media status rather than assuming every approved Run remains waiting with a pending receipt. It validates the matching ToolCall, scope, receipt and accepted Artifact before reporting a succeeded Run; a locally stopped Run remains inspectable. Expiry recovery deliberately skips approvals that already have a ToolCall, even after the original review TTL: expiry must not erase an in-flight or unknown-effect request. This read model does not authorize replay, does not confirm remote completion, and is not yet a Web execution panel.

Generic startup checkpoint validation now distinguishes this Video approval scope from the existing image Vendor ledger. A Video `vendor-request-intent` or `provider-task-observed` checkpoint must resolve to its Video request and ToolCall; a committed Video output must resolve to an accepted media Artifact and matching Project Video, GenerationTask and ArtifactRevision. Previously the generic validator looked only in image tables, so a valid Video checkpoint could be falsely parked as corrupt. Startup tests exercise both a waiting Video intent and a locally committed Video Run, alongside the existing image recovery cases. These are in-process database recovery tests, not a real process-kill or cross-worker takeover exercise.

A separate controlled media resolver now defines the outbound URL boundary before any production adapter is composed. Raw MP4 base64 is checked locally; a remote result is eligible only when it is HTTPS on an exact operator-provided host allowlist, has no credentials, nonstandard port or fragment, and every selected IPv4 DNS answer is public. The fetch pins the vetted address for TLS, disables redirects by requiring a 200 response, bounds headers/time/body and verifies the MP4 header. The signed URL is not persisted as Run evidence. An empty allowlist rejects URL results; no default host is assumed from Vendor capability metadata. Fake-network unit tests cover accepted and rejected inputs, but there is still no production execution composition or real CDN compatibility evidence.

An internal execution composition now wires the approved-scope reader, shared command preparation, exact quote, Video intent ledger, configured Vendor port, constrained media resolver, Artifact observer and atomic Project commit. It is not registered with HTTP or model Tools; therefore normal application use cannot yet dispatch this path. The default URL allowlist comes only from an explicit operator environment setting and is empty otherwise. A deterministic fake Vendor/SQLite integration test proves one base64 result can reach a succeeded Video and that a timeout or untrusted URL parks the original request without replay. No paid Provider was called.

That composition exposed an idempotency ordering bug: after the first success, Track state necessarily contains a Video, so recomputing the original proposal before checking for an existing request rejected a harmless duplicate. The executor and ledger now first authenticate the Owner and verify the approved Run/ToolCall/request binding, returning the existing request before target recheck. A concurrent first caller may still win during recheck; the ledger re-reads the request before surfacing a preparation conflict, while the transactional reservation remains the only creator of a new intent. Existing requests remain readable after the approval review TTL, but a fresh intent cannot use an expired approval. This is local no-replay behavior, not a guarantee that a remote Provider implements exactly-once billing.

An isolated Owner HTTP control route now exposes execute, local cancel, stop-without-replay, guarded commit and pending-media recovery only when `TOONFLOW_CONTROLLED_VIDEO_EXECUTION=enabled` is explicitly configured; its default is disabled. Every command obtains the actor from authentication, while the underlying runtime rechecks Project ownership and expected Run version. Execute returns `succeeded`, `already-recorded`, `submission-unknown`, `artifact-awaiting-commit`, or `late-artifact` rather than presenting an uncertain or canceled Provider effect as success. A late Artifact is never described as awaiting adoption. The approval-review routes themselves still have no execute action, and no model Tool or Web button is wired. Route tests use injected fake runtimes only; real Provider cost, HTTP timeout, task callback and browser behavior remain unvalidated. Enabling this operator gate before those checks is a deliberate deployment decision, not implied by merging the draft code.

The Project grant model now has a separate default-deny `propose:track-video` capability. Only the authenticated Owner can version-set it; a production-harness Run and productionAgent role are both required to resolve proposal permission. This grant cannot satisfy the billable `generate:track-video` Tool policy. It provides the authorization seam for the model-to-Owner candidate handoff without broadening execution rights.

The production Harness now registers `propose_track_video_generation` only when its production proposal dependency is present. A published Skill must request this exact Tool and `propose:track-video`, the current Project grant must allow it, and the parent Run must have an active lease. The same transaction records the permission decision and a deterministic child approval Run bound to parent Run, operation ID, Skill and proposal contract. Owner inspection verifies that binding and its decision hash; `/effects` projects Video status from these persisted records, not model text. A repeated operation returns the same child, while a changed candidate conflicts. This model authority only proposes: Owner approval remains separate, approval itself does not dispatch, and the opt-in execute route remains Owner-only. The fake-model/SQLite test proves the local separation and zero Vendor requests after proposal and approval, but not actual Provider billing, browser operation or process-failure recovery.
