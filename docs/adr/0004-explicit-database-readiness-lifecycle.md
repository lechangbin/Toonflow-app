# Use one explicit database readiness lifecycle

The database is opened through a single readiness module whose opening operation resolves only after one fixed order succeeds: open local resources, ensure the current schema, apply known upgrades, reconcile required defaults, recover interrupted work, validate the database and required runtime invariants, and — in development only — generate database types. Callers reach the database through `DatabaseRuntime`, which grants ordinary work a shared lease on a Knex handle passed into a callback, routes typed maintenance commands through a writer-preferred exclusive runner that replays the whole lifecycle before access reopens, and exposes no raw handle. Development type generation runs through a development adapter after readiness and can never fail production startup; a failed maintenance or revalidation leaves the runtime unavailable rather than silently falling back. This replaces import-time filesystem and database side effects plus a global readiness promise, so no caller can observe or bypass a partially initialized database. Every call site now reaches the database through a `DatabaseRuntime` lease; the transitional `u.db(...)` bridge is deleted, and static contract guards reject new bypasses.
