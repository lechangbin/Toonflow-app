# Bind Derived Asset writes to durable approval and an atomic effect commit

Status: accepted

T08 adds `upsert_derived_asset` to the Controlled Tool Runtime without granting the read-only Script Agent scope production-write authority. The write Tool belongs to a distinct Production Agent scope. Its request is a strict, bounded Derived Asset payload: Project-scoped parent Asset ID, optional existing Derived Asset ID, expected target version, display name and description, and a `DerivedChangeInstruction`. The server, not model input, resolves Project, parent type, target ownership, and the effect preview. The proposed operation has one stable Run-scoped identity and one immutable normalized payload hash.

For an existing target, the expected version is its current Derived Change Instruction revision, accompanied by a server-computed hash of the Asset and instruction state. A target without a valid instruction is not silently normalized by this Tool. For a new target, expected version is zero and the parent relation is frozen in the proposal. A later legacy edit that fails to advance the instruction revision is still detected by the state hash at commit. Equivalent visual states under the same parent remain forbidden using the existing domain validator, rechecked at commit.

Preflight validates schema, Project and Script ownership, parent/target type and relation, expected version, visual-dimension compatibility, and evidence before offering approval. The durable `ToolApproval` record stores operation identity, ToolDefinition revision and contract hash, normalized payload hash, target identity/version/state hash, bounded effect preview, expiry, decision, and command identity. It never stores a credential or a free-form Provider payload. Approval/rejection commands are Project-scoped, version-checked, and idempotent. The UI renders the preview from the persisted proposal, not from an untrusted pending browser request; stale, expired, rejected, or modified proposals cannot be revived.

Approval is authority for exactly one local effect. In one SQLite transaction, the command rechecks the immutable proposal, current target and parent state, and approval validity; then writes the Asset, Derived Change Instruction and next target version, updates the ToolReceipt, appends a hash-linked Agent Checkpoint, advances the Run state/version, and appends a causal safe Trace. No external Model or Vendor call occurs inside that transaction. A duplicate approved operation returns the prior receipt with no second domain write. If preflight or commit encounters a mismatch, the Run retains inspectable safe failure/attention state and production rows stay unchanged. Approval state and pending operation are database-owned, so refresh, reconnect, or worker restart must reconstruct them through the same inspect interface.

This is the first supervised local write, not a migration of the legacy Socket-bound Production Agent Tool. Existing legacy write paths remain a documented compatibility risk until the later Agent migration ticket. Real Provider and full App/Web acceptance are deferred to the final milestone; T08 uses deterministic local unit and contract tests at its own seam.
