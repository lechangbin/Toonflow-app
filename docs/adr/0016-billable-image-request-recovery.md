# Recover billable image requests from durable intent, not image state

Status: accepted for the T09 single-Asset controlled slice (Issue #65); final end-to-end acceptance is deferred to T21.

T09 migrates one single-Asset image-generation operation into the Production Agent Controlled Tool scope. The existing `generateAssetImage` API remains the legacy path for single and batch callers until migration is explicit. Its `o_image` state describes the user-facing image lifecycle, but cannot prove whether an external request was accepted or charged. In particular, `生成失败` after a timeout is not evidence that retrying the same request is safe.

The controlled operation binds one approval to Project, Asset, configured Vendor and Model, resolution, a maximum of one submission, a declared estimated cost ceiling and currency. This is an estimate/authorization scope, not observed billing. The server verifies ownership, prompt freshness and reference readiness before presenting approval, and rechecks them immediately before dispatch. The approved scope and Tool revision are immutable; changing any dimension requires a new proposal and approval. Approval is consumed at most once and is never an implicit retry token.

Before crossing the external boundary, the executor atomically persists Run, Step, Attempt, ToolCall, ToolReceipt, VendorRequest identity and a versioned checkpoint. `dispatch_recorded` means the request **may** have crossed the boundary after that commit, even if the process stops before calling the Provider. Startup recovery must therefore never resubmit it. A Provider task identifier, when actually observed, is persisted in a separate checkpoint before polling or accepting completion callbacks. A timeout, connection reset, ambiguous HTTP error, or process interruption after dispatch yields `unknown`, not `failed_no_effect`. Only a verified Provider task identifier may be polled automatically; otherwise the operator can wait, manually reconcile evidence, or stop without replay. An explicitly known no-effect refusal may be retried only by creating a fresh operation and approval.

Provider output is first recorded as artifact evidence with an immutable content hash. A duplicate callback for the same request/artifact is idempotent; a conflicting artifact is attention-required. An observed artifact is not a successful Tool execution until local media and Asset linkage have been committed and correlated to the ToolReceipt. Cancellation records intent, not a claim that the Provider cancelled or refunded. A late artifact after cancellation remains inspectable and must not silently resurrect the cancelled image or mark the Run successful.

Media persistence uses a request-scoped `write_pending` artifact intent before writing the local object. A crash or local write failure leaves an inspectable intent and never claims a committed image. A repeated callback with identical bytes may complete that local write without another Vendor submission; conflicting bytes are rejected. A pending intent alone does not prove the media file exists. An owner-authorized operator may reinspect an existing local file, verify its content hash, and finish only the local observation; this never invokes the Vendor. Automatic startup reinspection remains a follow-up capability.

An operator may reattempt only the **local acceptance** of an already observed artifact; that path never re-invokes the Provider and rechecks approval, ownership, target state and cancellation. After cancellation or a late artifact, an operator may end local tracking without replay. This closes the Run while retaining request and artifact evidence and an explicit warning that Vendor effect or billing has not been disproven. A later callback still records evidence but cannot reopen that terminal Run.

The T09 single-Asset slice implements this decision through a pure state contract, durable ledger, approval/preflight runtime, configured Vendor composition, authenticated HTTP endpoints, and a Web approval/inspection panel. A Project owner configures a versioned local approval estimate; missing configuration fails closed. The estimate is authorization context, not a verified Vendor price or invoice guarantee. Dispatch atomically commits ToolCall, VendorRequest, image placeholder and request-intent checkpoint before any Provider invocation; duplicate or restarted dispatches do not regain submit authority. Artifact observation records a `write_pending` intent before local media bytes and requires a matching hash before acceptance. A separate transaction rechecks ownership, approval, target state and cancellation before linking Image, Asset, Receipt, Output, Checkpoint and Trace. Owner-authorized recovery may inspect pending local media, commit an already observed artifact, request cancellation, or stop tracking without replay; none of these actions resubmits the Provider request.

This is deliberately a **single-path** decision, not a claim that all image generation or Agent tools are migrated. The legacy batch API and old Production Agent tools remain separate until their migration stages. The current synchronous Image Vendor interface exposes no verified task ID, so unknown external outcomes cannot be automatically polled and must remain unresolved until external evidence is available; no-effect failure cannot be inferred from timeout. Automatic startup reinspection of pending media is not implemented. App/Web repository-wide tests, builds, browser E2E, real Provider and packaging acceptance remain deferred to T21 under the project testing policy. T09's focused tests validate only local contracts and fake-Provider behavior.
