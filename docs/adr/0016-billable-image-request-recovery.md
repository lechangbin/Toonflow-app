# Recover billable image requests from durable intent, not image state

Status: proposed (T09 Issue #65)

T09 migrates one single-Asset image-generation operation into the Production Agent Controlled Tool scope. The existing `generateAssetImage` API remains the legacy path for single and batch callers until migration is explicit. Its `o_image` state describes the user-facing image lifecycle, but cannot prove whether an external request was accepted or charged. In particular, `生成失败` after a timeout is not evidence that retrying the same request is safe.

The controlled operation binds one approval to Project, Asset, configured Vendor and Model, resolution, a maximum of one submission, a declared estimated cost ceiling and currency. This is an estimate/authorization scope, not observed billing. The server verifies ownership, prompt freshness and reference readiness before presenting approval, and rechecks them immediately before dispatch. The approved scope and Tool revision are immutable; changing any dimension requires a new proposal and approval. Approval is consumed at most once and is never an implicit retry token.

Before crossing the external boundary, the executor atomically persists Run, Step, Attempt, ToolCall, ToolReceipt, VendorRequest identity and a versioned checkpoint. `dispatch_recorded` means the request **may** have crossed the boundary after that commit, even if the process stops before calling the Provider. Startup recovery must therefore never resubmit it. A Provider task identifier, when actually observed, is persisted in a separate checkpoint before polling or accepting completion callbacks. A timeout, connection reset, ambiguous HTTP error, or process interruption after dispatch yields `unknown`, not `failed_no_effect`. Only a verified Provider task identifier may be polled automatically; otherwise the operator can wait, manually reconcile evidence, or stop without replay. An explicitly known no-effect refusal may be retried only by creating a fresh operation and approval.

Provider output is first recorded as artifact evidence with an immutable content hash. A duplicate callback for the same request/artifact is idempotent; a conflicting artifact is attention-required. An observed artifact is not a successful Tool execution until local media and Asset linkage have been committed and correlated to the ToolReceipt. Cancellation records intent, not a claim that the Provider cancelled or refunded. A late artifact after cancellation remains inspectable and must not silently resurrect the cancelled image or mark the Run successful.

The implementation currently has a pure transition and billable-scope contract, a partial durable ledger, and an injectable approval/preflight core. The ledger atomically commits ToolCall, VendorRequest, image placeholder and request-intent checkpoint before the caller may invoke the Provider. Duplicate or restarted dispatches return the existing request with no submit authority. A verified Provider task identifier is checkpointed before any poll; startup parks an unconfirmed dispatch as unknown. The approval core obtains an estimate from a server-side dependency and freezes current prompt, reference media and target configuration fingerprints. The estimate is not a verified Provider price; without a configured server quote the operation must fail closed. Internal artifact observation stores one content-hashed media evidence record per request, preserves late output after cancellation, and rejects conflicting callbacks. A separate acceptance transaction checks approval, target state and cancellation again before atomically linking Image, Asset, Receipt, Output, Checkpoint and Trace; duplicate commits return the prior outcome. This does **not** yet expose a complete production Tool: there is no default quote configuration or authenticated HTTP/Agent entry, no actual single-Asset Provider call under this ledger, and no operator UI. The next slices must connect those boundaries and test a fake Provider before this ADR can be accepted or Issue #65 closed. Full App/Web, browser, real Provider, and packaging tests remain deferred to final acceptance per project testing policy.
