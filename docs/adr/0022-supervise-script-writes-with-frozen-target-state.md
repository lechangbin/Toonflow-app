# Supervise Script writes with frozen target state

Status: accepted for the T16 write contract; approval execution is not yet implemented.

The Script Agent must not turn model text or a frontend `getPlanData` callback into implicit Project mutation. A candidate write is a strict, bounded Tool payload for exactly one Script workspace field or one Script create/update. It is not authority by itself. The backend resolves Project and target identity, derives the current target-state hash, and freezes payload, ToolDefinition revision, contract hash, operation identity, target-state hash, preview and expiry before asking the Project Owner to approve. A preview carries target identity, effect, content length and hash, but not creative text; privileged inspection may show the full frozen candidate to the Owner.

Approval is per exact payload and target state, not a blanket `write:script` grant. The command must derive actor identity from authentication, compare expected Run/approval version, verify immutable evidence, re-read the target and reject stale or cross-Project updates. One SQLite transaction then commits the Project mutation, ToolReceipt, Agent Step/Attempt outcome, Checkpoint and causal Trace. A duplicate command returns the prior durable result without writing again. Rejection, expiry or conflict leaves production data unchanged and an inspectable safe outcome. No Vendor call occurs inside that transaction.

The old `o_agentWorkData` JSON row and `o_script` rows have no reliable mutation revision. The initial adapter therefore uses a server-computed hash over the exact target state and rechecks it at commit; a later first-class revision column may be introduced only with migration and legacy-writer compatibility. The target-state reader refuses ambiguous workspace rows, treats absent rows explicitly, fingerprints the full relevant legacy row for updates, and refuses Project-external Script IDs. Script creation rejects a current same-name competitor; updates use Script ID as identity and reject a different Script with the proposed name. Workspace writes update one allowlisted field while preserving the other. Model and browser inputs cannot select a different Project via a row ID.

This decision favors small, independently approvable writes over the legacy `setPlanData` bulk overwrite. The current T16 code implements candidate validation, immutable payload hashing, content-free preview projection, distinct immutable ToolDefinition contracts, Project-scoped target-state readers, and a Runtime that atomically persists a waiting Run/Step/Attempt, pending ToolReceipt/ToolApproval, creation Checkpoint and causal Trace. Its Owner decision command rechecks target state and, on approval, commits the Project effect with ToolReceipt, final Output, terminal Checkpoint and Trace in one local transaction; rejection, expiry, conflict and an injected persistence failure leave Project rows unchanged in focused tests. An HTTP adapter exposes owner-scoped propose/inspect/list/decide commands and derives actor identity from authenticated middleware. Due pending approvals are settled once on inspect/list and during database readiness recovery, without applying a Project effect. Agent-originating Tool integration, App/Web presentation and cross-boundary acceptance remain required before the Script Agent migration can be marked complete.
